# Hwahap V3 기획안: Plan Freeze 기반 자율 구현 사이클

- 상태: 제안(설계 전용, 현재 Hwahap v2 동작을 변경하지 않음)
- 작성일: 2026-09-04
- 대상: ChatGPT Desktop의 Codex를 주 사용 화면으로 쓰는 로컬 개발자
- 구현 방향: Rust 단일 Hwahap 실행 파일 + Codex Skill/MCP + ACP 기반 worker runtime

## 1. 목적

Hwahap V3는 사용자가 구현 과정을 계속 감독하는 시스템이 아니다. 사용자가 먼저 제품·기술 결정을 집요하게 확정하고, 그 계약을 잠근 뒤, Agent가 독립적으로 구현·테스트·검토·통합·PR 생성을 완료하는 시스템이다. 사용자는 완성된 PR을 확인한 뒤 조정하거나 shipping을 승인한다.

```text
PLAN ──> FREEZE ──> AUTONOMOUS BUILD ──> DRAFT PR ──> ADJUST | SHIP
 ^                                                     |
 └──────────────────── selective feedback ─────────────┘
```

V3의 제품 약속은 다음과 같다.

1. 기획 중에는 중요한 결정을 숨기지 않는다.
2. Hwahap은 결정마다 근거가 있는 추천 선택지를 제시한다.
3. 추천은 기본값이 아니며 사용자의 명시적 선택이 없으면 확정되지 않는다.
4. Plan Freeze 이후 정상 경로의 사용자 개입은 0회다.
5. 값싼 사실 조사·반복 구현·기계적 검증은 Luna를 우선 사용한다.
6. 구현 중 새 제품 결정을 임의로 만들지 않는다.
7. 완료 결과는 draft PR과 추적 가능한 증거로 반환한다.
8. 사용자는 PR 확인 뒤 영향받는 부분만 조정하거나 shipping을 승인한다.

## 2. 범위와 비범위

### 2.1 V3 범위

- ChatGPT Desktop Codex에서 자연어로 Hwahap을 호출하는 Desktop-first UX
- repository reverse engineering과 사실 수집
- 12개 decision surface 기반의 재귀적 planning
- 질문 frontier와 추천 선택지
- hash-bound 사용자 답변과 Plan Freeze
- risk-aware, Luna-first model routing
- atomic unit DAG, worktree 격리, patch 기반 통합
- independent review, rework, full-suite, final review
- draft PR 생성
- PR 피드백 기반 selective replan/rebuild
- 명시적 shipping gate
- crash/restart 후 재개 가능한 durable state

### 2.2 V3 초기 비범위

- Hwahap이 PR을 자동 merge하거나 auto-merge를 켜는 기능
- ChatGPT Desktop의 private/internal App Server process에 attach하는 기능
- 사용자 대신 제품 결정을 자동 승인하는 기능
- 모든 runtime을 하나의 물리적 executable 안에 포함하는 True Single Binary
- Cron, heartbeat, 범용 personal memory, 범용 agent workspace
- Hwahap 외 일반 ChatGPT/Codex 대화를 오케스트레이션하는 기능
- v2의 미구현 auto-improve runner를 V3 핵심 경로에 포함하는 기능

## 3. 핵심 용어

### Fact

repository, 실행 환경, 문서, 테스트에서 확인 가능한 사실이다. Fact는 사용자에게 묻지 않고 Hwahap이 조사한다. 모든 material fact는 evidence 위치와 digest를 가진다.

### Material Decision

다음 중 하나라도 바꾸는 선택이다.

- 관찰 가능한 동작
- API, CLI, 이벤트, 파일 또는 데이터 계약
- 오류·부분 실패·retry·rollback 의미
- 식별자, 이름, 경로, 포맷, 스키마
- 상태 수명과 영속성
- 의존성 또는 모듈 경계
- 동시성, 순서, timeout, resource limit
- 보안, privacy, 권한, network
- 호환성, migration, rollout, downgrade
- 성능 또는 관측성 계약
- 검증 방법과 합격 기준

Material Decision은 반드시 사용자가 확정한다.

### Local Coding Decision

외부 동작과 위 계약을 바꾸지 않는 가역적 구현 세부사항이다. Worker가 독립적으로 결정할 수 있다.

### Recommendation

Hwahap이 fact, 기존 코드, scope, trade-off를 근거로 제안하는 선택지다. Recommendation은 사용자의 답변을 대신하지 않는다.

### Plan Freeze

사용자의 `CONFIRM PLAN`이 canonical plan digest와 recommendation digest를 승인한 상태다. Freeze 이후 plan을 바꾸려면 revision을 올리고 영향을 받는 결정만 다시 확정해야 한다.

### Plan Conflict

구현 중 확인된 사실이 frozen plan과 양립하지 않는 상태다. Agent는 임의로 plan을 수정하지 않고 영향받는 unit을 park한다.

### Ship

V3 초기 정의에서 Ship은 최종 freshness/CI/traceability gate를 다시 실행하고 draft PR을 ready 상태로 전환하는 것이다. Merge와 auto-merge는 수행하지 않는다.

## 4. 사용자 경험

### 4.1 시작

사용자는 ChatGPT Desktop의 Codex에서 평소처럼 요청한다.

```text
Hwahap으로 이 repository에 dry-run 기능을 추가해줘.
```

Skill은 구현 요청으로 분류한 뒤 Hwahap MCP를 사용한다. 정상 사용에서 별도 terminal 명령은 필요하지 않다.

### 4.2 Plan Cycle

Hwahap은 repository를 읽고 fact를 수집한 뒤, 현재 답할 수 있는 decision frontier 전체를 한 번에 제시한다.

```text
Planning round 1 — 8 decisions

C1. dry-run 중 admission webhook을 호출할 것인가?
  ALT1. 호출한다
  ALT2. 호출하지 않는다
  REC: ALT1
  이유: 실제 apply 경로와 validation parity를 유지한다.
  영향: API 결과, timeout, test fixture
  confidence: high

C2. webhook timeout은 어떻게 처리할 것인가?
  ...
```

사용자는 추천안을 그대로 고르거나 다른 선택을 한다.

```text
C1=REC
C2=ALT2
C3=OTHER: 10초 뒤 warning과 함께 성공 처리
```

답변이 새로운 implication을 만들면 다음 frontier가 생성된다. frontier가 빌 때까지 반복한다.

### 4.3 Plan Freeze

Hwahap은 다음을 포함하는 `.hwahap/plan.md`를 렌더링한다.

- 목표, non-goal, priority
- 현재 시스템 분석
- 확정한 모든 decision과 recommendation/선택 차이
- 정상·오류·부분 실패·복구 scenario
- API/data/state/security/compatibility contract
- acceptance criteria
- atomic unit과 dependency DAG
- unit별 test와 full-suite
- delivery plan
- 남은 assumption 0개
- open decision 0개

사용자는 문서를 확인하고 `CONFIRM PLAN`을 입력한다. 이 입력은 plan digest와 recommendation set digest에 결속된다.

### 4.4 Autonomous Coding Cycle

Freeze 뒤에는 Hwahap이 다음을 자율 수행한다.

```text
Design -> Implement -> Unit Test -> Review -> Rework
       -> Integrate -> Full Suite -> Final Review -> Draft PR
```

사용자는 Codex task를 열어 둔 채 다른 일을 할 수 있다. 정상 경로에서는 추가 질문이 없다. 구현이 끝나면 같은 task에 PR과 요약이 반환된다.

### 4.5 확인과 조정

완료 화면은 최소한 다음을 보여준다.

```text
Hwahap cycle completed

Units                 7/7 accepted
Unit tests             7/7 passed
Integration            passed
Full suite             passed
Final review           passed
Plan deviations        0
Unplanned decisions    0
Draft PR               #123
```

사용자는 다음 중 하나를 선택한다.

```text
ADJUST: retry 결과는 warning이 아니라 typed error로 바꿔줘.
SHIP
```

`ADJUST`는 impact analysis 후 필요한 decision과 unit만 다시 연다. `SHIP`은 final gate를 재실행하고 PR을 ready로 바꾼다.

## 5. Three-Cycle lifecycle

### Cycle A — PLAN

#### A0. Classification

Hwahap은 구현·수정·refactor 요청에만 동작한다. 질문, 문서-only, 아이디어 설명, 단순 review에는 시작하지 않는다.

#### A1. Workspace initialization

규칙 기반으로 repository root, base branch, language/toolchain, package manifests, test commands, AGENTS/CLAUDE 지침, CI를 찾는다. 이 단계는 LLM 판단보다 deterministic scanner를 우선한다.

#### A2. Reverse engineering

Luna fact workers가 다음을 병렬 조사한다.

- entry points와 observable surfaces
- 현재 behavior와 error semantics
- state/data ownership
- architecture/module boundaries
- concurrency/security/compatibility constraints
- tests와 CI gates
- 최근 변경에서 드러난 convention

출력은 fact record이며 제품 선택을 포함하지 않는다.

#### A3. Decision graph

Plan lead가 intent, facts, 기존 12개 surface를 바탕으로 material decision graph를 만든다. 질문은 prerequisite가 해결된 것만 frontier에 올라온다.

현재 v2의 12개 surface는 유지한다.

1. 목표·성공·실패·범위
2. 사용자 행동·기본값·원자성·멱등성
3. 오류·부분 실패·복구·rollback·retry
4. 명령·API·이벤트·설정·타입·경로·포맷
5. 데이터·상태 소유·수명·영속·삭제
6. API·파일·내부 계약·schema·version
7. architecture·module boundary·dependency
8. concurrency·timing·timeout·order·resource
9. compatibility·migration·rollout·downgrade
10. security·privacy·authorization·secret·side effect
11. performance·observability·operation
12. verification setup·input·action·observable·evidence

각 applicable surface에는 decision과 “이 상황에서 무엇이 일어나는가” scenario가 최소 하나 있어야 한다.

#### A4. Recommendation synthesis

모든 material decision은 다음 recommendation contract를 갖는다.

```json
{
  "choice": "ALT2",
  "status": "recommended",
  "rationale": ["현재 retry contract와 일치"],
  "evidence": ["F7", "src/client.rs:42-61"],
  "tradeoffs": ["일시 장애 자동 복구는 호출자 책임"],
  "impacts": ["error", "tests", "observability"],
  "confidence": "high"
}
```

가능한 상태는 세 개다.

- `recommended`: 한 선택을 추천할 근거가 충분함
- `no_recommendation`: 사용자 preference가 본질이며 객관 근거가 부족함
- `probe_required`: 말로 확정할 수 없고 prototype/experiment가 필요함

Recommendation은 option generation과 분리된 critic을 통과해야 한다. 같은 Agent가 options를 만들고 검증 없이 자기 option을 추천하는 구조를 금지한다.

#### A5. User rounds

답변 문법은 다음과 같다.

- `C<n>=REC`
- `C<n>=ALT<m>`
- `C<n>=OTHER: <value>`
- `C<n>=UNKNOWN`
- `S<n>=NA`
- `CP<k>=REVIEWED`
- `CONFIRM PLAN`

`REC`는 해당 revision의 recommendation hash가 가리키는 option을 명시적으로 선택한다. 답이 없으면 unresolved다. `ACCEPT_ALL`은 지원하지 않는다.

Hwahap은 friction을 줄이기 위해 copyable worksheet를 제공할 수 있다.

```text
C1=REC
C2=REC
C3=REC
C4=REC
```

사용자는 이를 검토·수정해 제출한다. 한 round에서 material decision 8개 이상을 모두 `REC`로 승인하거나 irreversible/high-risk decision을 모두 추천대로 승인하면, Hwahap은 top consequences를 다시 보여주고 `CP<k>=REVIEWED`를 요구한다. 사용자가 추천과 반드시 달라야 한다는 뜻은 아니다.

#### A6. Ungrillable decisions

말로만 결정할 수 없는 UX, 성능, protocol compatibility는 질문을 반복하지 않는다. `probe_required`로 전환해 가역적·비제품용 probe를 실행하고 결과를 fact로 가져온 뒤 새 recommendation을 만든다.

#### A7. Traceability construction

frontier가 빈 뒤 아래 graph를 완성한다.

```text
Intent
  -> Requirement
     -> Decision / Scenario
        -> Acceptance Criterion
           -> Unit
              -> Test
```

고아 requirement, acceptance, unit, test가 하나라도 있으면 Plan Freeze가 불가능하다.

#### A8. Adversarial plan review

서로 다른 역할이 독립적으로 검토한다.

- requirement/intent critic
- architecture/contract critic
- failure/security/compatibility critic
- testability/traceability critic
- recommendation critic
- cold implementer: plan만 보고 추가 제품 결정 없이 구현 가능한지 검사

모든 finding은 새 decision, fact, probe, acceptance 또는 unit으로 환원한다. 단순 문장 수정으로 finding을 숨기지 않는다.

#### A9. Plan completeness gate

Plan은 아래 식이 모두 참일 때만 complete다.

```text
all applicable surfaces covered
AND all decisions answered
AND all scenarios answered
AND no unresolved facts
AND no retained assumptions
AND no open items
AND all recommendations reviewed
AND requirements -> acceptance complete
AND acceptance -> units complete
AND units -> tests complete
AND DAG acyclic
AND adversarial reviews pass
AND cold implementer requires no new product decision
```

#### A10. Plan Freeze

`CONFIRM PLAN`은 다음 digest에 결속된다.

- canonical `goal.json` excluding runtime fields
- rendered `plan.md`
- recommendation set
- fact manifest
- revision

Freeze 이후 digest가 바뀌면 build를 시작하거나 계속할 수 없다.

### Cycle B — BUILD

#### B0. Run start

Hwahap은 frozen plan에서 immutable build manifest를 만든다. 각 unit에는 다음이 있어야 한다.

- paths
- dependencies
- input contracts
- required behavior
- acceptance
- test command
- risk score
- model route
- retry/review limit

#### B1. Scheduling

LLM이 worker 호출 순서를 정하지 않는다. Rust scheduler가 DAG와 `max_parallel`에 따라 ready unit을 실행한다.

#### B2. Worktree isolation

각 non-probe unit은 detached worktree 하나를 가진다. Worker가 만든 결과는 commit이 아니라 binary-safe patch로 capture한다.

```text
1 unit = 1 worktree = 1 patch = 1 evidence bundle
```

#### B3. Implementation

기본 implementer는 Luna다. Worker는 해당 unit의 필요한 contract만 받고 다른 unit의 전체 context를 받지 않는다. 외부 behavior를 바꾸는 새 결정을 발견하면 코드를 바꾸지 않고 structured `PlanConflict`를 제출한다.

#### B4. Deterministic verification

Hwahap host가 직접 다음을 확인한다.

- changed path가 unit scope 안인지
- forbidden git operation이 없었는지
- unit test exit status
- required artifacts 존재와 digest
- secret pattern
- patch apply 가능 여부

LLM의 “테스트 통과” 문장을 증거로 사용하지 않는다.

#### B5. Independent review

Review는 worker session과 분리한다. 저위험 unit은 Luna verification + deterministic tests를 기본으로 하고, contract/security/concurrency/compatibility risk가 일정 기준 이상이면 Terra review를 추가한다. 모든 unit은 최소 하나의 independent review 또는 더 강한 aggregate review 경로를 가져야 한다.

#### B6. Rework and escalation

기본 경로는 다음과 같다.

```text
Luna implementation
  -> verify/review
  -> Luna rework once
  -> Terra diagnosis when failure persists
  -> Sol replan only for plan-level conflict or repeated cross-unit failure
```

상위 모델은 routine retry에 사용하지 않는다.

#### B7. Plan conflict handling

PlanConflict가 발생하면 영향받는 unit과 dependent만 park한다. 독립 unit은 계속 수행한다. 가능한 작업을 모두 마친 뒤 conflict를 batch로 반환한다.

- Agent가 숨은 default를 고르지 않는다.
- 사용자를 즉시 여러 번 호출하지 않는다.
- conflict는 plan revision에서만 해결한다.
- 수정 후 affected unit만 무효화한다.

#### B8. Integration

accepted patch를 dependency topological order로 integration worktree에 적용한다. 각 patch는 `git apply --check` 후 적용한다. full-suite는 통합 상태에서 실행한다.

#### B9. Final review

Sol final reviewer가 frozen plan, integrated diff, deterministic receipts만 보고 다음을 검사한다.

- intent 충족
- scope drift 0
- unplanned material decision 0
- contract/acceptance coverage
- security/compatibility/performance regressions
- tests와 evidence sufficiency

Final reviewer는 직접 코드를 고치지 않는다. finding은 affected unit rework 또는 plan conflict로 돌아간다.

#### B10. Draft PR

모든 gate 통과 후 `hwahap/<goal-id>` branch와 draft PR을 만든다. PR에는 plan digest, unit table, tests, reviews, deviations, model/token usage, limitations가 포함된다.

### Cycle C — ADJUST OR SHIP

#### C0. User review

사용자는 draft PR의 code, test, report를 확인한다. Hwahap은 구현 과정을 모두 읽으라고 요구하지 않고 다음만 요약한다.

- 무엇을 결정했고 무엇을 구현했는가
- recommendation과 다르게 선택한 부분
- plan deviation/conflict 유무
- 위험 구간과 verification
- PR 링크

#### C1. Adjustment

사용자 feedback을 기존 decision/requirement/acceptance/unit에 매핑한다.

- contract 영향 없음: local amendment와 affected unit rebuild
- material decision 변경: revision + selective planning round + `CONFIRM PLAN`
- scope 확장: 별도 goal 분할을 우선 추천

유효한 기존 답변과 unaffected unit evidence는 유지한다. brief/contract digest가 같은 accepted unit은 다시 호출하지 않는다.

#### C2. Ship

사용자가 `SHIP`을 입력하면 다음을 재검사한다.

- PR head가 Hwahap이 검토한 head와 동일
- required CI가 성공
- plan/recommendation/fact digest가 최신
- open finding/conflict/decision 0
- final review가 현재 diff에 결속
- secret/scope gate 통과

통과하면 draft PR을 ready로 전환한다. merge와 auto-merge는 수행하지 않는다.

## 6. Blackbox-Zero contract

Blackbox Zero는 모델의 private reasoning을 노출한다는 뜻이 아니다. 사용자가 알아야 할 제품·기술 결정이 모델 내부에만 남지 않는다는 뜻이다.

Plan Freeze와 PR report는 다음 지표를 제공한다.

```text
Decision surfaces               12 / 12
Material decisions resolved     N / N
Scenario decisions resolved     N / N
Retained assumptions            0
Open questions                  0
Requirements mapped             N / N
Acceptance mapped               N / N
Units mapped                    N / N
Tests mapped                    N / N
Agent product decisions         0
Plan deviations                 0 or explicitly approved
```

`Agent product decisions`는 구현 과정에서 Plan에 없는 material behavior를 Agent가 선택한 횟수다. 목표값은 항상 0이다. 0이 아니면 successful terminal state를 만들 수 없다.

## 7. Model routing: Luna-first, risk-aware

### 7.1 Logical tiers

모델 이름을 코드 전체에 흩뿌리지 않는다. semantic role을 설정에 매핑한다.

```toml
[models]
economy = "gpt-5.6-luna"
critic = "gpt-5.6-terra"
deep = "gpt-5.6-sol"
```

기본 추천값은 위와 같지만 ACP가 광고한 모델 목록과 사용자 설정을 검증한 뒤 사용한다.

### 7.2 Role defaults

| 작업 | 기본 모델 | 기본 effort | 이유 |
|---|---|---:|---|
| repository inventory/scanning | Luna | medium | 반복적 사실 수집 |
| focused fact extraction | Luna | medium | 근거가 코드에 존재 |
| scenario expansion first pass | Luna | high | 병렬화 가능한 초안 |
| option generation first pass | Luna | high | critic 전 초안 |
| recommendation synthesis | Sol | high | trade-off와 숨은 implication 중요 |
| recommendation critic | Terra | high | 독립적인 반대 검토 |
| plan synthesis/freeze review | Sol | high | 가장 높은 기획 품질 필요 |
| routine implementation | Luna | high | frozen contract를 따라가는 작업 |
| test authoring/repair | Luna | high | 명시된 acceptance 기반 |
| mechanical verification triage | Luna | medium | deterministic receipt 기반 |
| low-risk unit review | Luna | high | 제한된 patch와 강한 tests |
| risky semantic unit review | Terra | high | security/concurrency/contract 판단 |
| persistent failure diagnosis | Terra | high | worker와 다른 관점 |
| final integrated review | Sol | high | cross-unit reasoning 필요 |
| plan conflict/replan | Sol | high | 사용자 의도와 architecture 영향 |

### 7.3 Risk score

각 unit은 다음 항목으로 risk를 계산한다.

- blast radius
- novelty
- contract materiality
- security/privacy
- concurrency/state
- migration/compatibility
- verification strength
- prior failure count

예시 routing:

```text
low    -> Luna implement + Luna review + deterministic tests
medium -> Luna implement + Terra review
high   -> Luna implementation attempt + Terra review + Sol final focus
critical planning change -> no code; Sol replan + user confirmation
```

### 7.4 Escalation rules

- Luna가 할 수 있는 작업을 시작부터 Sol에 주지 않는다.
- 단순 token budget 초과만으로 상위 모델에 올리지 않는다.
- 같은 원인으로 두 번 실패하거나 semantic finding이 반복되면 Terra로 올린다.
- Sol은 plan synthesis, replan, final aggregate review에 집중한다.
- 모델 변경은 receipt에 기록하며 해당 변경의 이유가 있어야 한다.

## 8. Desktop-first integration

### 8.1 User-facing package

사용자는 Hwahap을 하나의 capability로 인식해야 한다.

```text
Hwahap Desktop bundle
  ├─ Codex Skill
  ├─ MCP declaration
  └─ hwahap native binary
```

Plugin surface를 사용할 수 있는 계정에서는 `@hwahap`으로 선택한다. 그 surface가 없는 경우에도 local Codex Skill + MCP config가 같은 동작을 제공한다.

### 8.2 Protocol boundary

```text
ChatGPT Desktop Codex -> MCP -> Hwahap
Hwahap -> ACP v1 -> codex-acp -> Codex App Server
```

Desktop의 private process나 undocumented endpoint에는 의존하지 않는다.

### 8.3 Minimal MCP surface

Parent Codex에게 low-level orchestration tool을 노출하지 않는다. 최소 surface는 다음과 같다.

- `hwahap.plan`: plan state를 진행하고 현재 frontier/plan을 반환
- `hwahap.cycle`: frozen plan의 coding cycle을 완료하거나 terminal blocker까지 실행
- `hwahap.status`: durable run 상태와 PR을 반환
- `hwahap.adjust`: PR feedback을 impact analysis에 입력
- `hwahap.ship`: final gate 후 PR ready 전환

`create_unit`, `spawn_worker`, `retry`, `integrate` 같은 low-level tool은 Parent LLM에 제공하지 않는다. Rust engine이 결정한다.

### 8.4 Long-running task behavior

기본 경로에서 `hwahap.cycle`은 long-running MCP operation으로 실행되어 PR 또는 terminal blocker를 반환한다. 사용자는 ChatGPT Desktop의 다른 task나 외부 업무로 이동할 수 있다.

모든 transition은 durable checkpoint를 남긴다. Desktop 재시작이나 tool interruption 후 다음 `status`/`cycle` 호출이 자동 resume한다. Desktop이 장기 tool call을 안정적으로 유지하지 못하는 플랫폼에서만 동일 binary의 run-scoped supervisor mode를 fallback으로 사용한다. 상시 daemon은 V3 기본 요구사항이 아니다.

## 9. Process and installation budget

### 9.1 Idle

```text
ChatGPT Desktop
  -> optional idle MCP process controlled by Desktop host
```

Hwahap이 소유하는 별도 daemon, adapter, Codex worker, heartbeat는 상시 실행되지 않는다. Desktop이 설정된 stdio MCP process를 미리 띄우거나 유지하는지는 host 정책에 따르며, 그 process는 child runtime을 만들지 않고 idle해야 한다.

### 9.2 Planning

```text
ChatGPT Desktop
  -> hwahap MCP process
```

Fact/probe Agent가 필요할 때만 worker runtime을 시작한다.

### 9.3 Coding cycle

권장 기본 topology:

```text
ChatGPT Desktop
  -> hwahap (Rust, MCP + orchestration)
       -> codex-acp (one pinned adapter per run)
            -> Codex App Server
                 -> multiple isolated ACP sessions/worktrees
```

- worker마다 `codex exec`를 만들지 않는다.
- adapter process 하나가 여러 concurrent session을 안전하게 처리하는지는 P0 compatibility probe로 고정한다.
- 검증 실패 시에만 bounded adapter pool을 사용한다.
- cycle 종료 시 ACP session과 child process를 정리한다.
- 사용자가 설치·관리하는 Hwahap artifact는 native binary 하나다. `codex-acp`는 version-pinned managed companion이며 True Single Binary라고 표현하지 않는다.

## 10. Rust runtime design

초기 구현은 workspace를 과도하게 나누지 않고 하나의 Cargo package 안에서 module boundary를 유지한다.

```text
skills/hwahap/runtime/
  Cargo.toml
  src/
    main.rs
    mcp.rs
    contract.rs
    planning.rs
    state.rs
    scheduler.rs
    acp.rs
    model_router.rs
    policy.rs
    worktree.rs
    integrate.rs
    report.rs
```

주요 선택:

- stable ACP protocol v1
- official `agentclientprotocol/rust-sdk`
- `rmcp` 기반 MCP server
- Tokio concurrency
- SQLite runtime state
- Git CLI를 shell string이 아니라 structured argv로 실행
- `gh`를 draft PR/ready 전환에 사용하되 command allowlist와 receipts 적용
- `codex-acp` version pin

## 11. State and artifacts

### 11.1 Canonical product contract

파일은 계속 source of truth다.

```text
.hwahap/
  goal.json              schema: hwahap/v3
  plan.md                deterministic user-facing render
  answers.jsonl          human answer hash chain
  facts/
  probes/
  out/
  report.md
  summary.json
```

### 11.2 Runtime state

SQLite는 orchestration state를 저장한다.

```text
runs
units
sessions
transitions
artifacts
usage
findings
conflicts
```

SQLite는 사용자 결정의 source of truth가 아니다. `goal.json`, `answers.jsonl`, fact manifest의 digest를 참조한다.

### 11.3 State machines

Run:

```text
PLANNING -> PLAN_READY -> FROZEN -> BUILDING -> INTEGRATING
-> FINAL_REVIEW -> PR_DRAFTED -> ADJUSTING | READY_TO_SHIP -> SHIPPED
```

Unit:

```text
PENDING -> READY -> RUNNING -> VERIFIED -> REVIEWING -> ACCEPTED
                    |             |             |
                    v             v             v
                  FAILED       REWORK      PLAN_CONFLICT
```

불가능한 transition은 DB constraint와 Rust enum 양쪽에서 거부한다.

## 12. Sandbox and security contract

- Parent Desktop Codex가 nested `codex exec`를 실행하지 않는다.
- Worker는 unit worktree만 workspace-write다.
- Reviewer와 fact worker는 read-only가 기본이다.
- network는 default deny이며 plan에 명시된 unit만 별도 capability를 요청할 수 있다.
- `danger-full-access`는 V3 initial scope에서 금지한다.
- permission request는 Rust policy engine이 role, unit, cwd, requested operation에 따라 처리한다.
- permission interception만 신뢰하지 않고 완료 후 git diff path scope를 다시 검사한다.
- Hwahap은 ChatGPT credential 값을 읽거나 복사하지 않는다. adapter/Codex의 기존 auth flow만 사용한다.
- environment/config inheritance는 명시적으로 allowlist한다.
- child process 종료 시 process tree leak 검사를 수행한다.
- `.hwahap`과 durable state는 owner-only permission을 사용하고 atomic write한다.

## 13. v2에서 유지하고 교체할 것

### 유지

- 12 decision surfaces
- explicit answer grammar와 hash chain
- fact를 사용자에게 묻지 않는 원칙
- deterministic goal validation/render
- cold review와 final confirmation
- atomic unit DAG
- detached worktree per unit
- path scope와 patch capture
- unit test, independent review, topological integration
- full suite 한 번
- final review
- secret scan
- draft PR only
- usage/budget evidence
- unchanged unit cache

### 교체

| v2 | V3 |
|---|---|
| Parent LLM이 `codex exec` 문자열 생성 | Rust scheduler가 typed ACP session 생성 |
| nested sandbox escalation rule | Parent와 worker runtime boundary |
| command string parsing | typed `AgentProfile`과 ACP config |
| PostToolUse가 process supervisor | ACP events + Rust EventReducer |
| final-message 첫 줄 protocol | role-specific structured MCP/result contract |
| LLM이 parallel tool call 결정 | deterministic DAG scheduler |
| file-existence-only runtime state | explicit state machine + SQLite |
| plan 질문만 제시 | fact/evidence/trade-off 기반 recommendation 포함 |
| static role model | Luna-first risk-aware router |

## 14. Compatibility probes required before implementation lock

다음은 사용자 선택이 아니라 사실 확인이 필요한 P0 probe다.

1. ChatGPT Desktop local MCP의 process lifetime, long-running tool call, restart behavior
2. Desktop Codex sandbox와 local MCP process 사이의 실제 OS 경계
3. official Rust ACP SDK와 pinned `codex-acp`의 v1 handshake
4. 하나의 `codex-acp` process에서 concurrent multi-session 안전성
5. session별 cwd, sandbox mode, model, reasoning effort isolation
6. ChatGPT login auth 재사용과 Hwahap이 credential을 직접 다루지 않는 경로
7. `session/load`/resume 시 MCP manifest 재전달과 event replay
8. cancellation이 Codex/App Server/process tree까지 전달되는지
9. Desktop에서 long-running cycle 완료 결과가 같은 task에 표시되는지
10. macOS와 Windows에서 orphan process 0인지

probe 결과가 권장 topology와 다르면 사용자-facing lifecycle은 유지하되 host implementation만 수정한다.

## 15. V3 design decisions

- **V3-D1**: Hwahap은 `PLAN -> FREEZE -> BUILD -> PR -> ADJUST/SHIP` 세 cycle로 구성한다.
- **V3-D2**: Plan Cycle은 user-intensive, Build Cycle은 기본 human gate 0이다.
- **V3-D3**: 모든 material decision은 alternatives와 recommendation contract를 가진다.
- **V3-D4**: Recommendation은 implicit default가 아니며 `C<n>=REC`가 있어야 확정된다.
- **V3-D5**: `ACCEPT_ALL`은 제공하지 않는다. large/high-risk all-REC round는 checkpoint를 요구한다.
- **V3-D6**: Fact는 Hwahap이 조사하며 사용자에게 repository fact를 묻지 않는다.
- **V3-D7**: 말로 해결할 수 없는 decision은 반복 질문 대신 probe로 전환한다.
- **V3-D8**: Plan Freeze는 goal, render, recommendation, fact manifest digest에 결속된다.
- **V3-D9**: successful build에서 Agent product decision count는 0이어야 한다.
- **V3-D10**: 구현 중 plan conflict는 affected graph를 park하고 independent work는 계속한다.
- **V3-D11**: 기본 implementer와 cheap fact/verification worker는 Luna다.
- **V3-D12**: Terra는 independent semantic criticism과 persistent failure diagnosis에 집중한다.
- **V3-D13**: Sol은 recommendation/plan synthesis, replan, final aggregate review에 집중한다.
- **V3-D14**: model escalation에는 recorded reason이 필요하다.
- **V3-D15**: Parent Codex는 low-level worker orchestration을 수행하지 않는다.
- **V3-D16**: Desktop -> Hwahap은 MCP, Hwahap -> Worker는 ACP v1이다.
- **V3-D17**: Hwahap control plane은 Rust native binary 하나로 배포한다.
- **V3-D18**: `codex-acp`는 pinned managed companion이며 True Single Binary라고 주장하지 않는다.
- **V3-D19**: 상시 daemon은 기본이 아니다. long-running MCP + durable resume를 우선한다.
- **V3-D20**: worker별 nested `codex exec`는 0회다.
- **V3-D21**: adapter는 run당 하나를 우선하며 multi-session probe 실패 시 bounded pool로 degrade한다.
- **V3-D22**: canonical product contract는 파일, runtime lifecycle은 SQLite가 소유한다.
- **V3-D23**: unit별 detached worktree와 patch integration은 유지한다.
- **V3-D24**: final review는 코드를 수정하지 않고 unit rework 또는 replan으로 finding을 돌린다.
- **V3-D25**: 완료 산출물은 draft PR이다.
- **V3-D26**: `SHIP`은 final gate와 ready 전환이며 merge/auto-merge는 하지 않는다.
- **V3-D27**: adjustment는 affected decisions/units만 무효화하고 나머지 evidence를 재사용한다.
- **V3-D28**: Desktop private App Server endpoint/process topology에 의존하지 않는다.

## 16. Success metrics

제품 성공 기준:

- 사용자가 terminal 없이 ChatGPT Desktop에서 시작·답변·확인·조정·ship 가능
- Plan Freeze 뒤 정상 run의 사용자 질문 0회
- nested `codex exec` 0회

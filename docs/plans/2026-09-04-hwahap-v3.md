# Hwahap V3 기획안: 얇은 Skill과 단일 실행 루프

- 상태: 제안. 구현 완료 시 Hwahap v2를 호환성 없이 전면 교체한다.
- 작성일: 2026-09-04
- 대상: ChatGPT Desktop의 Codex를 주 사용 화면으로 쓰는 로컬 개발자
- 구현 방향: 하나의 설치 가능한 Hwahap plugin, 하나의 Rust binary, 로컬 STDIO MCP, stable ACP v1

## 1. 목표와 변경할 수 없는 원칙

Hwahap V3는 사용자가 구현 과정을 계속 감독하는 시스템이 아니다.

```text
PLAN -> PLAN FREEZE -> AUTONOMOUS CODING -> DRAFT PR -> ADJUST | SHIP
```

사용자는 PLAN에서 제품·기술 결정을 집요하게 확정한다. Hwahap은 각 결정에 추천안을 제시하지만 자동으로 선택하지 않는다. Plan Freeze 뒤에는 Agent가 구현·테스트·검토·PR 생성을 완료하고, 사용자는 결과를 확인해 조정하거나 shipping을 승인한다.

다음 원칙은 단순화를 위해 약화하지 않는다.

1. 모든 material decision은 사용자에게 보인다.
2. Fact는 Hwahap이 조사하고 preference/trade-off만 사용자에게 묻는다.
3. 모든 material decision은 alternatives, recommendation, evidence, trade-off, impact를 가진다.
4. 추천은 implicit default가 아니다. 사용자 답변이 없으면 unresolved다.
5. Plan Freeze 뒤 정상 coding cycle의 사용자 질문은 0회다.
6. Frozen plan에 없는 제품 결정을 Agent가 임의로 만들지 않는다.
7. 값싼 fact 조사, routine implementation, test 수선에는 Luna를 우선한다.
8. 테스트 성공은 LLM의 주장보다 실제 명령 결과와 Git 상태로 판정한다.
9. 완료 산출물은 traceable evidence가 포함된 draft PR이다.
10. V3 cutover 뒤 `hwahap`에는 V3 구현만 남는다.

## 2. 공식 자료에서 골라낸 최소 구조

Hwahap은 범용 agent platform이 아니라 한 가지 개발 workflow다. 따라서 각 프로젝트에서 필요한 부분만 가져온다.

| 출처 | 채택 | 의도적으로 제외 |
|---|---|---|
| OpenAI Skills/Plugins | progressive disclosure, 얇은 `SKILL.md`, Skill+MCP를 하나의 plugin으로 배포 | Skill 안의 runtime 절차, custom UI, hooks, connector |
| MCP | 로컬 STDIO, server `instructions`, 명확한 tool schema, read/write/consequential 분리 | Streamable HTTP, daemon, experimental Tasks, worker용 내부 MCP |
| ACP Rust SDK | stable v1 client와 `AcpAgent` process lifecycle | proxy, conductor, unstable protocol v2, unstable MCP-over-ACP |
| Kiro Crew TaskRunner | frozen spec, step별 fresh session, test/retry/checkpoint, crash 뒤 incomplete step 재실행 | gateway, channels, memory, cron, heartbeat, warm pool, provider registry |
| AI-DLC | 필요한 단계만 실행하는 adaptive depth, phase boundary verification, Construction 자율성 | 33-stage lifecycle, scope/profile matrix, 다수의 approval gate, agent mob/swarm |

이 선택의 결과는 다음과 같다.

- Hwahap Skill은 orchestration을 설명하지 않는다.
- Rust engine이 planning과 coding state machine을 소유한다.
- Desktop은 Hwahap을 호출하고 사용자 메시지를 전달하는 host다.
- V3 초기 버전은 병렬 실행보다 correctness와 process 단순성을 우선한다.

## 3. 사용자 경험

### 3.1 시작

사용자는 ChatGPT Desktop의 Codex에서 평소처럼 요청한다.

```text
@hwahap 이 repository에 dry-run 기능을 추가해줘.
```

명시적 `@hwahap` 선택이 없더라도 Skill description과 구현 요청이 일치하면 활성화할 수 있다. 정상 경로에서 terminal 명령이나 별도 Hwahap UI는 요구하지 않는다.

### 3.2 PLAN

Hwahap은 repository를 조사한 뒤 현재 답할 수 있는 decision frontier를 한 번에 제시한다.

```text
C1. dry-run 중 admission webhook을 호출할 것인가?

ALT1. 호출한다
ALT2. 호출하지 않는다

추천: ALT1
근거: 실제 apply 경로와 validation parity를 유지한다.
evidence: F7, src/apply/...
trade-off: webhook 실패가 dry-run 실패가 된다.
impact: API 결과, timeout, tests
confidence: high
```

사용자는 추천을 그대로 고르거나 다른 선택을 한다.

```text
C1=REC
C2=ALT2
C3=OTHER: 10초 뒤 typed error로 실패
```

답변이 새 implication을 만들면 다음 frontier를 만든다. frontier가 빌 때까지 반복한다.

### 3.3 PLAN FREEZE

Hwahap은 `.hwahap/plan.md`를 렌더링하고 다음과 같은 challenge를 반환한다.

```text
CONFIRM PLAN 7F3A91C2
```

사용자는 plan을 확인한 뒤 challenge를 그대로 입력한다. Challenge는 canonical plan digest에 결속된다. Skill은 confirmation을 생성하거나 보완해서는 안 되고 사용자의 정확한 메시지만 전달한다.

### 3.4 AUTONOMOUS CODING

Freeze 뒤에는 다음 루프를 자율 수행한다.

```text
Luna implement
  -> deterministic verification
  -> independent review
  -> accepted checkpoint
  -> next unit
  -> full suite
  -> Sol final review
  -> draft PR
```

사용자는 같은 ChatGPT Desktop task를 열어 둔 채 다른 일을 할 수 있다. 실행이 중단되면 다음 호출이 마지막 accepted checkpoint에서 재개한다.

### 3.5 ADJUST 또는 SHIP

완료 요약은 최소한 다음을 보여준다.

```text
Hwahap cycle completed

Units                 7/7 accepted
Unit tests             7/7 passed
Full suite             passed
Final review           passed
Plan deviations        0
Unplanned decisions    0
Draft PR               #123
```

사용자는 조정 내용을 자연어로 입력하거나 다음 challenge를 입력한다.

```text
SHIP 9D0C71A4
```

`SHIP`은 current PR head, CI, plan digest, final review freshness를 다시 확인한 뒤 draft PR을 ready로 전환한다. Merge와 auto-merge는 수행하지 않는다.

## 4. 가장 작은 배포 형태

OpenAI plugin이 설치 단위다.

```text
Hwahap plugin
├── .codex-plugin/plugin.json
├── skills/hwahap/SKILL.md
├── .mcp.json
└── hwahap native binary 또는 그 설치 정보
```

기본 runtime topology는 다음 하나다.

```text
ChatGPT Desktop Codex
  -> local STDIO MCP
       -> hwahap (Rust)
            -> one pinned codex-acp process while a run is active
                 -> one fresh ACP session at a time
```

초기 V3에는 다음을 만들지 않는다.

- 상시 daemon
- Streamable HTTP endpoint
- custom UI
- lifecycle hook
- worker별 MCP server
- worker별 `codex exec`
- ACP proxy/conductor
- multi-backend provider abstraction
- cross-project memory
- parallel worker pool

Desktop가 MCP process를 종료해도 durable files가 남는다. 새 process의 첫 호출이 active run을 읽고 현재 unit을 처음부터 다시 실행한다.

## 5. 얇은 Skill

OpenAI Skills의 progressive disclosure를 따른다. `SKILL.md`에는 trigger와 host behavior만 둔다. 목표는 40줄 이하이다.

개념적 내용은 다음이면 충분하다.

```markdown
Use Hwahap only for implementation or refactoring requests.
Call `hwahap_step`; do not implement, schedule workers, or run tests yourself.
Forward the user's exact answer or feedback without inventing confirmations.
When `next=continue`, call `hwahap_step` again without asking the user.
When `next=await_user`, show `message` and stop.
When `next=completed` or `blocked`, show the result.
Call `hwahap_ship` only after the user types the exact SHIP challenge.
```

Cross-tool workflow와 제한은 MCP initialize response의 `instructions`가 소유한다. 같은 규칙을 Skill과 여러 reference에 중복하지 않는다. `instructions`의 첫 512자는 독립적으로 이해 가능하게 작성한다.

## 6. MCP surface: 세 개의 tool

OpenAI tool 설계 지침에 따라 read, ordinary write, consequential write를 분리한다.

### `hwahap_step`

한 active run을 시작하거나 진행한다.

입력:

```json
{
  "cwd": "/repo",
  "request": "optional initial request",
  "user_input": "optional exact user message"
}
```

동작:

- active run이 없고 `request`가 있으면 PLAN을 시작한다.
- `await_user` 상태에서는 `user_input`을 검증하고 진행한다.
- `continue` 상태에서는 다음 사용자 경계, terminal state 또는 host deadline까지 Rust engine을 실행한다.
- Plan Freeze 뒤 승인된 범위에서 local branch와 draft PR을 만들 수 있다.

출력:

```json
{
  "run_id": "...",
  "phase": "plan|build|review",
  "state": "...",
  "next": "continue|await_user|completed|blocked",
  "message": "model-readable user message",
  "plan_digest": "optional",
  "pr_url": "optional"
}
```

### `hwahap_status`

현재 run을 변경하지 않고 읽는다. `readOnlyHint=true`다.

### `hwahap_ship`

Draft PR을 ready로 전환하는 별도 consequential action이다. 입력은 `run_id`와 사용자가 입력한 정확한 `SHIP <digest>` 문자열이다. Server-side freshness gate를 통과해야 한다.

그 밖의 `plan`, `cycle`, `adjust`, `retry`, `create_unit`, `spawn_worker`, `integrate` tool은 만들지 않는다. 해당 동작은 state와 `hwahap_step` 내부에서 결정된다.

## 7. PLAN engine: 네 단계

AI-DLC의 scope/depth 원칙은 user-visible profile이 아니라 “필요한 깊이만 실행”하는 내부 규칙으로 사용한다. Lifecycle은 항상 네 단계다.

### 7.1 Inspect

Luna가 repository fact를 수집한다.

- observable entry points
- current behavior와 error semantics
- state/data ownership
- module boundaries와 dependencies
- concurrency, security, compatibility constraints
- tests와 CI

Fact는 source location과 digest를 가진다. 확인 가능한 사실을 사용자에게 질문하지 않는다.

### 7.2 Decide

Sol이 12개 decision surface를 checklist로 모두 검사하되 material한 항목만 질문으로 만든다. Surface는 stage가 아니다.

1. 목표·성공·실패·범위
2. 사용자 행동·기본값·원자성·멱등성
3. 오류·부분 실패·복구·rollback·retry
4. 명령·API·이벤트·설정·타입·경로·포맷
5. 데이터·상태 소유·수명·영속·삭제
6. API·파일·내부 계약·schema·version
7. architecture·module boundary·dependency
8. concurrency·timing·timeout·order·resource
9. compatibility·migration·rollout·downgrade
10. security·privacy·authorization·secret·side effect
11. performance·observability·operation
12. verification setup·input·action·observable·evidence

각 material decision은 다음 필드를 가진다.

```json
{
  "id": "C7",
  "question": "...",
  "alternatives": ["ALT1", "ALT2"],
  "recommendation": {
    "choice": "ALT2",
    "rationale": ["..."],
    "evidence": ["F3"],
    "tradeoffs": ["..."],
    "impact": ["api", "tests"],
    "confidence": "high"
  }
}
```

추천할 객관적 근거가 없으면 `no_recommendation`, 실제 실험이 필요하면 `probe_required`를 사용한다.

### 7.3 Prove

추가 agent swarm을 만들지 않는다.

- Luna cold consumer가 plan만 보고 unit brief를 만들 수 있는지 검사한다.
- Terra가 requirement, contract, failure, security, compatibility, testability, recommendation을 하나의 checklist로 적대적 검토한다.
- Rust validator가 traceability와 graph를 검사한다.

Finding은 fact, decision, acceptance 또는 unit으로 환원한다. Finding을 문장 수정만으로 닫지 않는다.

### 7.4 Freeze

다음이 모두 참이어야 challenge를 발급한다.

```text
all applicable surfaces accounted for
AND all material decisions answered
AND all scenarios answered
AND no retained assumption
AND no open fact or probe
AND requirement -> acceptance -> unit -> test mapping complete
AND unit DAG acyclic
AND cold consumer needs no new product decision
AND Terra review passes
```

`CONFIRM PLAN <digest>`가 들어오면 `plan.json`과 `plan.md`를 frozen 상태로 만든다.

## 8. CODING engine: 하나의 worktree와 순차 unit loop

초기 V3는 parallelism을 correctness requirement로 보지 않는다. Unit DAG를 deterministic topological order로 순차 실행한다. 실제 측정에서 필요성이 확인되기 전에는 parallel scheduler를 추가하지 않는다.

### 8.1 Run worktree

Run마다 branch와 worktree를 하나만 만든다.

```text
branch:   hwahap/<goal-id>
worktree: .hwahap/worktree
```

Unit별 별도 worktree와 마지막 patch integration 단계는 제거한다.

### 8.2 Unit attempt

각 attempt는 fresh ACP session이다.

1. Last accepted commit에서 시작한다.
2. Luna worker가 frozen unit contract를 구현하고 test를 작성·수정한다.
3. Final agent message는 strict JSON result 하나여야 한다.
4. Rust host가 diff scope와 실제 test command를 검사한다.
5. Terra가 `last_checkpoint..working_tree` diff를 read-only review한다.
6. 통과하면 unit ID와 plan digest를 포함한 local checkpoint commit을 만든다.
7. 실패하면 last checkpoint로 reset하고 Luna rework를 한 번 수행한다.
8. 동일 failure가 지속되면 Terra diagnosis를 거쳐 재시도하거나 `blocked`로 끝낸다.

Worker result 예시:

```json
{
  "status": "completed|plan_conflict|failed",
  "summary": "...",
  "conflict": null
}
```

Reviewer result 예시:

```json
{
  "verdict": "pass|fail",
  "findings": []
}
```

이 JSON은 control metadata일 뿐이다. Test pass와 changed-path 판정은 Rust host가 실제 상태로 확인한다. Worker용 내부 MCP server는 만들지 않는다.

### 8.3 PlanConflict

Frozen plan과 양립하지 않는 사실을 발견하면 worker는 code change를 남기지 않고 `plan_conflict`를 반환한다. Rust host는 diff가 비어 있는지 확인한다.

- 영향받는 unit과 dependent를 park한다.
- 이미 accepted된 unit은 유지한다.
- 아직 실행 가능한 독립 unit은 순서대로 계속한다.
- 가능한 작업이 끝나면 conflict를 한 번에 사용자에게 반환한다.

### 8.4 Final verification과 PR

모든 unit이 accepted되면 같은 worktree에서 full suite를 한 번 실행한다. Sol은 frozen plan, complete branch diff, receipts를 최종 검토한다. Finding이 없으면 branch를 push하고 draft PR을 생성한다.

별도 integration worktree, patch ordering engine, integration lock은 필요하지 않다. Git commit order가 accepted unit order와 checkpoint를 표현한다.

## 9. 고정된 모델 역할

동적 risk score와 범용 model router를 제거한다. 세 역할만 둔다.

| 모델 역할 | 기본 모델 | 담당 |
|---|---|---|
| Economy | Luna | fact 조사, cold consumer, routine implementation, tests, 첫 rework |
| Critic | Terra | recommendation/plan 적대적 검토, unit review, persistent failure diagnosis |
| Deep | Sol | alternatives와 recommendation, final plan synthesis, PlanConflict replan, final integrated review |

모델 이름은 세 설정 키로만 교체할 수 있다.

```toml
[models]
economy = "gpt-5.6-luna"
critic = "gpt-5.6-terra"
deep = "gpt-5.6-sol"
```

상위 모델로의 자유로운 escalation은 없다. 위 역할 외 모델 변경은 unsupported다. 이 구조는 Luna 사용량을 높이면서 routing logic을 작게 유지한다.

## 10. 파일 기반 상태: SQLite 없음

Hwahap은 한 repository에서 active run 하나만 허용한다. 범용 gateway와 다중 사용자 scheduling이 없으므로 SQLite를 사용하지 않는다.

```text
.hwahap/
├── plan.json       canonical frozen contract
├── plan.md         deterministic user render
├── run.json        atomic current-state snapshot
├── events.jsonl    append-only hash-chained audit events
├── artifacts/      facts, tests, reviews, diagnostics
├── worktree/       one run worktree
└── report.md       final user report
```

규칙:

- `run.json`은 temp file + fsync + atomic rename으로 쓴다.
- 모든 material transition은 `events.jsonl`에 sequence와 previous hash를 남긴다.
- Snapshot과 journal이 불일치하면 fail-closed 후 journal의 마지막 complete transition으로 복구한다.
- In-flight unit attempt는 resume하지 않고 last accepted commit에서 새 session으로 다시 시작한다.
- 완료 또는 명시적 abort 전에는 같은 repository에서 새 run을 시작하지 않는다.

이 선택으로 DB schema, migration, connection pool, locking, async DB executor를 제거한다.

## 11. ACP와 process lifecycle

- Protocol은 stable ACP v1만 사용한다.
- Rust SDK의 core Client와 `AcpAgent` process lifecycle만 사용한다.
- `codex-acp` version은 고정하고 `@latest`를 사용하지 않는다.
- Active run 동안 adapter process 하나를 유지한다.
- 동시에 active한 ACP session은 하나다.
- Unit attempt와 review마다 fresh session을 만들고 완료 후 닫는다.
- Session ID나 hidden conversation state를 durable state로 사용하지 않는다.
- Crash 뒤 session/load 또는 resume를 하지 않고 current unit을 처음부터 재실행한다.
- ACP proxy, conductor, protocol v2, MCP-over-ACP는 사용하지 않는다.

이로써 multi-session concurrency, session replay, MCP manifest restoration, warm pool을 검증할 필요가 없다.

## 12. 고정된 security policy

범용 policy DSL을 만들지 않는다.

- Worker: run worktree만 workspace-write, network deny.
- Reviewer/fact/planner: read-only, network deny가 기본.
- `danger-full-access`: 항상 금지.
- 외부 network가 필수인 probe는 PLAN에서 별도 사용자 결정을 요구한다.
- ACP permission request는 role과 cwd를 기준으로 hard-coded policy가 처리한다.
- Permission callback이 호출되지 않는 경우를 고려해 완료 후 Git diff와 process exit를 다시 검사한다.
- Hwahap은 ChatGPT credential 값을 읽거나 복사하지 않는다.
- Child environment는 allowlist로 구성한다.
- Cycle 종료 시 adapter/Codex process tree가 남지 않아야 한다.

## 13. ADJUST의 단순한 규칙

PR feedback은 existing decision, acceptance, unit에 매핑한다.

- Material decision이 바뀌면 affected decision만 다시 질문하고 새 plan revision을 freeze한다.
- Existing branch 위에 correction commit을 추가한다.
- Unaffected accepted unit은 재실행하지 않는다.
- Affected unit과 그 dependent의 tests/review를 다시 실행한다.
- Full suite와 Sol final review는 항상 다시 실행한다.

Arbitrary commit replay, graph-wide branch 재구성, force-push 기반 history rewrite는 하지 않는다.

## 14. Breaking cutover

V3는 v2 compatibility layer를 두지 않는다.

제거 대상:

- v2 `codex exec` templates
- `PreToolUse`/`PostToolUse` orchestration
- v2 shell helper와 jq runtime 중 V3에서 불필요한 코드
- v2 schema와 artifact reader
- v2/v3 selector
- v2 session/run resume
- v2 전용 CI workflow와 tests

Cutover 뒤 지원하는 Hwahap contract는 `hwahap/v3` 하나다. 기존 v2 `.hwahap`을 발견하면 자동 변환하지 않고 삭제 후 새 run을 시작하라는 명확한 오류를 반환한다. Rollback은 compatibility mode가 아니라 cutover commit/PR의 Git revert다.

## 15. 핵심 결정

- **V3-D1**: Lifecycle은 PLAN, CODING, ADJUST/SHIP 세 cycle이다.
- **V3-D2**: Human gate는 `CONFIRM PLAN`과 `SHIP` 두 개뿐이다.
- **V3-D3**: 12개 surface는 checklist이며 별도 stage가 아니다.
- **V3-D4**: PLAN은 Inspect, Decide, Prove, Freeze 네 단계다.
- **V3-D5**: Recommendation은 필수지만 자동 선택되지 않는다.
- **V3-D6**: Skill은 40줄 이하의 thin dispatcher를 목표로 한다.
- **V3-D7**: MCP server `instructions`가 cross-tool protocol의 단일 source다.
- **V3-D8**: MCP tool은 `step`, `status`, `ship` 세 개다.
- **V3-D9**: Local STDIO만 지원하며 HTTP, daemon, MCP Tasks를 사용하지 않는다.
- **V3-D10**: Rust ACP core client + stable v1만 사용한다.
- **V3-D11**: One active run, one run worktree, one adapter, one active session이다.
- **V3-D12**: Unit은 순차 실행하며 accepted unit마다 checkpoint commit을 만든다.
- **V3-D13**: Crash 뒤 in-flight session은 resume하지 않고 unit을 재실행한다.
- **V3-D14**: Runtime state는 atomic JSON snapshot + hash-chained JSONL이다. SQLite는 사용하지 않는다.
- **V3-D15**: Worker/reviewer result는 strict JSON final response이며 내부 MCP server를 만들지 않는다.
- **V3-D16**: 모델 routing은 Luna/Terra/Sol 고정 역할 세 개뿐이다.
- **V3-D17**: V3는 v2를 전면 교체하며 compatibility code를 만들지 않는다.

## 16. 성공 기준

- ChatGPT Desktop에서 설치 후 `@hwahap` 또는 자연어로 사용 가능
- `SKILL.md` 40줄 이하
- MCP tool 정확히 3개
- 정상 사용에 terminal, hook, custom UI, daemon이 필요하지 않음
- Plan Freeze 뒤 정상 run 사용자 질문 0회
- nested `codex exec` 0회
- 한 run의 동시 worker session 1개
- unplanned material decision 0
- requirement -> acceptance -> unit -> test traceability 100%
- routine coding token의 대부분을 Luna가 처리
- crash 뒤 accepted work 손실 없이 current unit 재실행
- out-of-scope path 0
- full suite와 final review가 current PR head에 결속
- cycle 종료 후 orphan process 0
- cutover 후 v2 production code path 0

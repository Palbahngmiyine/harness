# Hwahap V3 기획안: Plan Freeze 기반 자율 구현 사이클

- 상태: 제안. 구현 완료 시 Hwahap v2를 호환성 없이 전면 교체한다.
- 작성일: 2026-09-04
- 대상: ChatGPT Desktop의 Codex를 주 사용 화면으로 쓰는 로컬 개발자
- 구현 방향: Rust 단일 Hwahap 실행 파일 + Codex Skill/MCP + ACP 기반 worker runtime

## 1. 목적

Hwahap V3는 사용자가 구현 과정을 계속 감독하는 시스템이 아니다. 사용자가 먼저 제품·기술 결정을 집요하게 확정하고, 그 계약을 잠근 뒤, Agent가 독립적으로 구현·테스트·검토·통합·PR 생성을 완료하는 시스템이다. 사용자는 완성된 PR을 확인한 뒤 조정하거나 shipping을 승인한다.

```text
PLAN ──> FREEZE ──> AUTONOMOUS BUILD ──> DRAFT PR ──> ADJUST | SHIP
 ^                                                     |
 └──────────────────── selective feedback ─────────────┘
```

V3는 v2의 차기 호환 버전이 아니라 **breaking full replacement**다. 현재 v2 사용자를 위한 schema, hook, 파일 레이아웃, runtime, 설치 방식, 진행 중 run 호환성은 보장하지 않는다. v2에서 검증된 아이디어는 invariant로 다시 구현할 수 있지만 v2 code path, dual-mode selector, compatibility adapter는 유지하지 않는다.

V3의 제품 약속은 다음과 같다.

1. 기획 중에는 중요한 결정을 숨기지 않는다.
2. Hwahap은 모든 material decision에 근거가 있는 추천 선택지를 제시한다.
3. 추천은 기본값이 아니며 사용자의 명시적 선택이 없으면 확정되지 않는다.
4. Plan Freeze 이후 정상 coding cycle의 사용자 개입은 0회다.
5. 값싼 사실 조사·반복 구현·테스트 수선·기계적 검증은 Luna를 우선 사용한다.
6. 구현 중 frozen plan에 없는 제품 결정을 임의로 만들지 않는다.
7. 완료 결과는 draft PR과 traceable evidence로 반환한다.
8. 사용자는 PR 확인 뒤 영향받는 부분만 조정하거나 shipping을 승인한다.
9. V3 cutover가 끝나면 `hwahap`에는 V3 구현만 남는다.

## 2. 범위와 비범위

### 2.1 V3 범위

- ChatGPT Desktop Codex에서 자연어로 호출하는 Desktop-first UX
- repository reverse engineering과 사실 수집
- 12개 decision surface 기반 재귀적 planning
- dependency frontier와 recommendation-first 질문
- hash-bound 사용자 답변과 Plan Freeze
- risk-aware, Luna-first model routing
- atomic unit DAG, worktree 격리, patch 기반 통합
- independent review, rework, full-suite, final review
- draft PR 생성
- PR 피드백 기반 selective replan/rebuild
- 명시적 `SHIP` gate
- crash/restart 후 재개 가능한 durable state
- 기존 `skills/hwahap` v2 runtime/hook/shell orchestration의 전면 제거와 V3 교체

### 2.2 V3 초기 비범위

- 자동 merge 또는 auto-merge
- ChatGPT Desktop의 private/internal App Server process에 attach
- 사용자 대신 material decision 자동 승인
- Hwahap + ACP adapter + Codex까지 하나의 물리적 executable로 묶는 True Single Binary
- Cron, heartbeat, 범용 personal memory, 범용 agent workspace
- Hwahap 외 일반 ChatGPT/Codex 대화 orchestration
- Hwahap v2 schema/artifact/run/config의 backward compatibility 또는 자동 migration
- v2의 미구현 auto-improve runner 이식

## 3. 핵심 계약

### Fact

repository, 실행 환경, 문서, 테스트에서 확인 가능한 사실이다. Fact는 사용자에게 묻지 않고 Hwahap이 조사한다. 모든 material fact는 evidence 위치와 digest를 가진다.

### Material Decision

다음 중 하나라도 바꾸는 선택이다.

- 관찰 가능한 동작
- API, CLI, 이벤트, 파일 또는 데이터 계약
- 오류·부분 실패·retry·rollback 의미
- 식별자, 이름, 경로, 포맷, schema
- 상태 수명과 영속성
- dependency 또는 module boundary
- concurrency, 순서, timeout, resource limit
- security, privacy, 권한, network
- compatibility, migration, rollout, downgrade
- performance 또는 observability contract
- 검증 방법과 합격 기준

Material Decision은 반드시 사용자가 확정한다.

### Local Coding Decision

외부 동작과 위 계약을 바꾸지 않는 가역적 구현 세부사항이다. Worker가 독립적으로 결정할 수 있다.

### Recommendation

Hwahap이 fact, 기존 코드, scope, trade-off를 근거로 제안하는 선택이다. Recommendation은 사용자의 답변을 대신하지 않는다.

### Plan Freeze

사용자의 `CONFIRM PLAN`이 canonical goal, rendered plan, recommendation set, fact manifest의 digest를 승인한 상태다. Freeze 이후 material plan을 바꾸려면 revision을 올리고 영향을 받는 decision만 다시 확정해야 한다.

### Plan Conflict

구현 중 확인된 사실이 frozen plan과 양립하지 않는 상태다. Agent는 임의로 plan을 수정하지 않고 영향받는 unit을 park한다.

### Ship

V3 초기 정의의 `SHIP`은 final freshness/CI/traceability gate를 다시 실행하고 draft PR을 ready 상태로 전환하는 것이다. Merge와 auto-merge는 수행하지 않는다.

## 4. 사용자 경험

### 4.1 시작

사용자는 ChatGPT Desktop의 Codex에서 평소처럼 요청한다.

```text
Hwahap으로 이 repository에 dry-run 기능을 추가해줘.
```

Skill은 구현 요청으로 분류하고 Hwahap MCP를 사용한다. 정상 경로에서 별도 terminal 명령은 요구하지 않는다.

### 4.2 Plan Cycle

Hwahap은 repository fact를 먼저 수집한 뒤 현재 답할 수 있는 decision frontier 전체를 한 번에 제시한다.

```text
Planning round 1 — 8 decisions

C1. dry-run 중 admission webhook을 호출할 것인가?
  ALT1. 호출한다
  ALT2. 호출하지 않는다
  REC: ALT1
  이유: 실제 apply 경로와 validation parity를 유지한다.
  evidence: F7, src/apply/...
  trade-off: webhook failure가 dry-run failure가 된다.
  영향: API 결과, timeout, tests
  confidence: high
```

사용자는 추천을 그대로 고르거나 다른 선택을 한다.

```text
C1=REC
C2=ALT2
C3=OTHER: 10초 뒤 typed error로 실패
```

답변이 새 implication을 만들면 다음 frontier를 만든다. frontier가 빌 때까지 반복한다.

### 4.3 Plan Freeze

Hwahap은 `.hwahap/plan.md`를 결정적으로 렌더링한다.

- 목표, non-goal, priority
- 현재 시스템 분석
- 확정 decision과 recommendation/선택 차이
- 정상·오류·부분 실패·복구 scenario
- API/data/state/security/compatibility contract
- acceptance criteria
- atomic unit과 dependency DAG
- unit별 tests와 full-suite
- delivery plan
- retained assumption 0
- open decision 0

사용자는 `CONFIRM PLAN`을 입력한다. 이 입력은 current plan/recommendation/fact digest에 결속된다.

### 4.4 Autonomous Coding Cycle

Freeze 뒤에는 Hwahap이 다음을 자율 수행한다.

```text
Design -> Implement -> Unit Test -> Review -> Rework
       -> Integrate -> Full Suite -> Final Review -> Draft PR
```

정상 경로에서는 추가 질문이 없다. 사용자는 다른 task 또는 다른 일을 수행하고, cycle 완료 후 같은 ChatGPT Desktop task에서 PR 결과를 확인한다.

### 4.5 확인, 조정, shipping

완료 요약은 최소한 다음을 보여준다.

```text
Hwahap cycle completed

Units                 7/7 accepted
Unit tests             7/7 passed
Integration            passed
Full suite             passed
Final review           passed
Plan deviations        0
Unplanned decisions    0
Draft PR               #123
```

사용자는 다음 중 하나를 선택한다.

```text
ADJUST: retry 결과를 warning이 아니라 typed error로 바꿔줘.
SHIP
```

`ADJUST`는 impact analysis 후 필요한 decision과 unit만 다시 연다. `SHIP`은 final gate를 재실행하고 PR을 ready로 바꾼다.

## 5. Cycle A — PLAN

### A0. Classification

Hwahap은 구현·수정·refactor 요청에만 시작한다. 질문, 문서-only, 아이디어 설명, 단순 review는 대상이 아니다.

### A1. Workspace initialization

규칙 기반 scanner를 LLM보다 먼저 사용해 repository root, base branch, language/toolchain, manifests, tests, AGENTS/CLAUDE 지침, CI를 찾는다.

### A2. Reverse engineering

Luna fact workers가 다음을 병렬 조사한다.

- entry points와 observable surfaces
- 현재 behavior와 error semantics
- state/data ownership
- architecture/module boundaries
- concurrency/security/compatibility constraints
- tests와 CI gates
- 최근 변경에서 드러난 conventions

출력은 fact record이며 제품 선택을 포함하지 않는다.

### A3. Decision graph

Plan lead는 intent와 facts를 바탕으로 material decision graph를 만든다. 질문은 prerequisite가 해결된 것만 frontier에 올린다.

V3는 v2에서 유효성이 확인된 12개 decision surface 개념을 새 contract에서 재구현한다.

1. 목표·성공·실패·범위
2. 사용자 행동·기본값·원자성·멱등성
3. 오류·부분 실패·복구·rollback·retry
4. 명령·API·이벤트·설정·타입·경로·포맷
5. 데이터·상태 소유·수명·영속·삭제
6. API·파일·내부 계약·schema·version
7. architecture·module boundary·dependency
8. concurrency·timing·timeout·order·resource
9. compatibility·migration·rollout·downgrade
10. security·privacy·authorization·secret·side effect
11. performance·observability·operation
12. verification setup·input·action·observable·evidence

각 applicable surface에는 최소 하나의 decision과 “이 상황에서 무엇이 일어나는가” scenario가 있어야 한다.

### A4. Recommendation synthesis

모든 material decision은 다음 recommendation contract를 갖는다.

```json
{
  "choice": "ALT2",
  "status": "recommended",
  "rationale": ["현재 retry contract와 일치"],
  "evidence": ["F7", "src/client.rs:42-61"],
  "tradeoffs": ["일시 장애 복구는 호출자 책임"],
  "impacts": ["error", "tests", "observability"],
  "confidence": "high"
}
```

상태는 `recommended`, `no_recommendation`, `probe_required` 중 하나다. Recommendation은 option generator와 분리된 critic을 통과해야 한다.

### A5. User rounds

답변 문법:

- `C<n>=REC`
- `C<n>=ALT<m>`
- `C<n>=OTHER: <value>`
- `C<n>=UNKNOWN`
- `S<n>=NA`
- `CP<k>=REVIEWED`
- `CONFIRM PLAN`

`REC`는 해당 revision의 recommendation hash가 가리키는 option을 선택한다. 답이 없으면 unresolved다. `ACCEPT_ALL`은 제공하지 않는다.

한 round에서 material decision 8개 이상을 모두 `REC`로 승인하거나 high-risk/irreversible decision을 모두 추천대로 승인하면 top consequences를 다시 보여주고 checkpoint를 요구한다.

### A6. Probe-required decisions

말로만 결정하기 어려운 UX, 성능, protocol compatibility는 질문을 반복하지 않는다. 가역적 probe를 실행하고 결과를 fact로 가져온 뒤 새 recommendation을 만든다.

### A7. Traceability

frontier가 빈 뒤 다음 graph를 완성한다.

```text
Intent -> Requirement -> Decision/Scenario -> Acceptance -> Unit -> Test
```

고아 node가 하나라도 있으면 Plan Freeze가 불가능하다.

### A8. Adversarial plan review

서로 다른 역할이 독립적으로 검토한다.

- requirement/intent critic
- architecture/contract critic
- failure/security/compatibility critic
- testability/traceability critic
- recommendation critic
- cold implementer: plan만 보고 추가 제품 결정 없이 구현 가능한지 검사

finding은 decision, fact, probe, acceptance, unit 중 하나로 환원한다. 단순 문장 수정으로 finding을 숨기지 않는다.

### A9. Plan completeness gate

Plan은 다음이 모두 참일 때만 complete다.

```text
all applicable surfaces covered
AND all material decisions answered
AND all scenarios answered
AND no unresolved fact
AND no retained assumption
AND no open item
AND all recommendations reviewed
AND requirements -> acceptance complete
AND acceptance -> units complete
AND units -> tests complete
AND DAG acyclic
AND adversarial reviews pass
AND cold implementer requires no new product decision
```

### A10. Plan Freeze

`CONFIRM PLAN`은 canonical goal, rendered plan, recommendation set, fact manifest, revision digest를 잠근다. digest가 바뀌면 build를 시작하거나 재개할 수 없다.

## 6. Cycle B — BUILD

### B0. Immutable build manifest

각 unit은 paths, dependencies, input contracts, required behavior, acceptance, test, risk score, model route, retry/review limit를 가진다.

### B1. Deterministic scheduling

Parent LLM이 worker 호출 순서를 정하지 않는다. Rust scheduler가 DAG와 `max_parallel`에 따라 ready unit을 실행한다.

### B2. Worktree isolation

```text
1 unit = 1 detached worktree = 1 patch = 1 evidence bundle
```

Worker 결과는 build 중 commit하지 않고 binary-safe patch로 capture한다.

### B3. Implementation

기본 implementer는 Luna다. Worker는 해당 unit의 frozen contract만 받고, material decision이 필요한 새 사실을 발견하면 코드를 바꾸지 않고 structured `PlanConflict`를 반환한다.

### B4. Deterministic verification

Hwahap host가 직접 확인한다.

- changed path가 unit scope 안인지
- forbidden git operation이 없었는지
- unit test exit status
- required artifacts와 digest
- secret pattern
- patch apply 가능 여부

LLM의 “테스트 통과” 문장은 증거가 아니다.

### B5. Independent review

저위험 unit은 Luna review + deterministic tests를 기본으로 한다. contract/security/concurrency/compatibility risk가 임계값 이상이면 Terra review를 사용한다.

### B6. Rework and escalation

```text
Luna implementation
  -> verify/review
  -> Luna rework once
  -> Terra diagnosis when failure persists
  -> Sol replan only for plan-level conflict or repeated cross-unit failure
```

상위 모델은 routine retry에 사용하지 않는다.

### B7. Plan conflict handling

PlanConflict가 발생하면 affected unit과 dependent만 park하고 독립 unit은 계속한다. 가능한 작업을 마친 뒤 conflict를 batch로 반환한다. Agent가 hidden default를 선택하지 않는다.

### B8. Integration

accepted patch를 topological order로 integration worktree에 적용한다. 각 patch는 `git apply --check` 후 적용한다. full-suite는 통합 상태에서 실행한다.

### B9. Final review

Sol final reviewer는 frozen plan, integrated diff, deterministic receipts만 보고 intent, scope, contract, security, compatibility, performance, evidence sufficiency를 검사한다. 직접 코드를 고치지 않고 finding을 unit rework 또는 replan으로 돌린다.

### B10. Draft PR

모든 gate 통과 후 `hwahap/<goal-id>` branch와 draft PR을 만든다. PR에는 plan digest, units, tests, reviews, deviations, model/token usage, limitations를 포함한다.

## 7. Cycle C — ADJUST OR SHIP

### C0. User review

사용자는 draft PR을 확인한다. Hwahap은 결정/구현 요약, recommendation과 다른 선택, plan deviations/conflicts, 위험 구간과 verification, PR 링크를 제공한다.

### C1. Adjustment

feedback을 기존 decision/requirement/acceptance/unit에 매핑한다.

- material contract 영향 없음: local amendment + affected unit rebuild
- material decision 변경: revision + selective planning + `CONFIRM PLAN`
- scope 확장: 별도 goal 분할 우선 추천

unaffected accepted unit은 다시 실행하지 않는다.

### C2. Ship

`SHIP` 시 다음을 재검사한다.

- PR head freshness
- required CI success
- plan/recommendation/fact digest freshness
- open finding/conflict/decision 0
- final review가 current diff에 결속
- secret/scope gate

통과하면 draft PR을 ready로 전환한다. Merge와 auto-merge는 하지 않는다.

## 8. Blackbox-Zero contract

Blackbox Zero는 private reasoning 공개가 아니라, 사용자가 알아야 할 제품·기술 결정이 모델 내부에만 남지 않는다는 뜻이다.

```text
Decision surfaces               12 / 12
Material decisions resolved     N / N
Scenario decisions resolved     N / N
Retained assumptions            0
Open questions                  0
Requirements mapped             N / N
Acceptance mapped               N / N
Units mapped                    N / N
Tests mapped                    N / N
Agent product decisions         0
Plan deviations                 0 or explicitly approved
```

`Agent product decisions`가 0이 아니면 successful terminal state를 만들 수 없다.

## 9. Model routing: Luna-first, risk-aware

모델 이름을 orchestration logic에 흩뿌리지 않고 semantic tier로 관리한다.

```toml
[models]
economy = "gpt-5.6-luna"
critic = "gpt-5.6-terra"
deep = "gpt-5.6-sol"
```

| 작업 | 기본 모델 | effort |
|---|---|---:|
| repository inventory/fact extraction | Luna | medium |
| scenario/option first pass | Luna | high |
| recommendation synthesis | Sol | high |
| recommendation critic | Terra | high |
| plan synthesis/freeze review | Sol | high |
| routine implementation | Luna | high |
| test authoring/repair | Luna | high |
| low-risk unit review | Luna | high |
| risky semantic review | Terra | high |
| persistent failure diagnosis | Terra | high |
| final integrated review | Sol | high |
| plan conflict/replan | Sol | high |

Risk는 blast radius, novelty, contract materiality, security/privacy, concurrency/state, compatibility, verification strength, prior failures로 계산한다.

```text
low    -> Luna implement + Luna review + deterministic tests
medium -> Luna implement + Terra review
high   -> Luna implementation attempt + Terra review + Sol final focus
critical planning change -> no code; Sol replan + user confirmation
```

모델 escalation에는 recorded reason이 필요하다. Luna로 충분한 작업을 시작부터 Sol에 주지 않는다.

## 10. Desktop-first integration

### 10.1 User-facing package

사용자는 Hwahap을 하나의 capability로 인식한다.

```text
Hwahap Desktop bundle
  ├─ Codex Skill
  ├─ MCP declaration
  └─ hwahap native binary
```

Plugin surface가 가용하면 `@hwahap` 같은 선택 UX를 사용할 수 있지만 baseline은 local Codex Skill + MCP다.

### 10.2 Protocol boundary

```text
ChatGPT Desktop Codex -> MCP -> Hwahap
Hwahap -> ACP v1 -> codex-acp -> Codex App Server
```

Desktop private process나 undocumented endpoint에는 의존하지 않는다.

### 10.3 Minimal MCP surface

Parent Codex에는 high-level tools만 노출한다.

- `hwahap.plan`
- `hwahap.cycle`
- `hwahap.status`
- `hwahap.adjust`
- `hwahap.ship`

`create_unit`, `spawn_worker`, `retry`, `integrate` 같은 low-level tool은 Rust engine 내부에 둔다.

### 10.4 Long-running task

기본적으로 `hwahap.cycle`은 PR 또는 terminal blocker까지 실행되는 long-running operation이다. 모든 transition은 durable checkpoint를 남긴다. Desktop/tool interruption 후 `status`/`cycle`이 자동 resume한다. 상시 daemon은 기본 요구사항이 아니다.

## 11. Process and installation budget

Idle에는 Hwahap-owned adapter/worker/heartbeat를 상시 실행하지 않는다. Desktop host가 stdio MCP process를 미리 띄우더라도 그 process는 child runtime을 만들지 않고 idle해야 한다.

Coding cycle의 권장 topology:

```text
ChatGPT Desktop
  -> hwahap (Rust: MCP + orchestration)
       -> codex-acp (one pinned adapter per run)
            -> Codex App Server
                 -> multiple isolated sessions/worktrees
```

- worker마다 `codex exec`를 만들지 않는다.
- adapter 하나의 concurrent multi-session 안전성은 P0 probe로 확인한다.
- 실패 시에만 bounded adapter pool로 degrade한다.
- cycle 종료 시 child sessions/process를 정리한다.
- 사용자가 관리하는 Hwahap artifact는 native binary 하나다.
- `codex-acp`는 pinned managed companion이며 True Single Binary라고 표현하지 않는다.

## 12. Rust runtime, state, security

초기 구현은 하나의 Cargo package 안에서 module boundary를 유지한다.

```text
skills/hwahap/runtime/
  Cargo.toml
  src/
    main.rs
    mcp.rs
    contract.rs
    planning.rs
    state.rs
    scheduler.rs
    acp.rs
    model_router.rs
    policy.rs
    worktree.rs
    integrate.rs
    report.rs
```

기본 선택:

- stable ACP protocol v1
- official `agentclientprotocol/rust-sdk`
- `rmcp` MCP server
- Tokio concurrency
- SQLite runtime state
- Git command를 shell string이 아닌 structured argv로 실행
- pinned `codex-acp`

Canonical product contract는 파일에 남긴다.

```text
.hwahap/
  goal.json              schema: hwahap/v3
  plan.md
  answers.jsonl
  facts/
  probes/
  out/
  report.md
  summary.json
```

SQLite는 `runs`, `units`, `sessions`, `transitions`, `artifacts`, `usage`, `findings`, `conflicts`를 저장한다. 사용자 결정 source of truth는 파일과 digest다.

Run/Unit transition은 Rust enum과 DB constraint 양쪽에서 검증한다.

Security contract:

- Parent Desktop Codex가 nested `codex exec`를 실행하지 않는다.
- Worker는 unit worktree만 workspace-write다.
- Reviewer/fact worker는 read-only 기본이다.
- network default deny.
- `danger-full-access` 금지.
- ACP permission request는 Rust policy engine이 처리한다.
- permission interception만 믿지 않고 완료 후 git diff path scope를 재검사한다.
- Hwahap은 ChatGPT credential 값을 읽거나 복사하지 않는다.
- environment/config inheritance를 allowlist한다.
- cycle 종료 후 process tree leak을 검사한다.
- `.hwahap`과 durable state는 owner-only permission + atomic write를 사용한다.

## 13. v2에서 계승할 불변식과 제거할 구현

V3는 v2와의 runtime/API/artifact 호환성을 목표로 하지 않는다. 아래 “계승”은 기존 파일·script·schema를 유지한다는 뜻이 아니라, 검증된 설계 불변식을 V3 contract와 Rust runtime에서 새로 구현한다는 뜻이다.

### 계승할 불변식

- 12 decision surfaces
- explicit answer grammar와 hash-bound confirmation
- fact를 사용자에게 묻지 않는 원칙
- deterministic goal validation/render
- cold/adversarial review와 final confirmation
- atomic unit DAG
- detached worktree per unit
- path scope와 patch capture
- unit test, independent review, topological integration
- full suite 한 번
- final review
- secret scan
- draft PR first
- usage/budget evidence
- unchanged unit cache

### 삭제하거나 전면 교체할 구현

| v2 | V3 |
|---|---|
| Parent LLM이 `codex exec` 문자열 생성 | Rust scheduler가 typed ACP session 생성 |
| nested sandbox escalation rule | Parent/worker runtime boundary |
| command string parsing | typed AgentProfile + ACP config |
| PreToolUse/PostToolUse orchestration | ACP events + Rust policy/EventReducer |
| final-message 첫 줄 protocol | role-specific structured result |
| LLM이 parallel tool call 결정 | deterministic DAG scheduler |
| file-existence-only runtime state | explicit state machine + SQLite |
| 질문만 제시 | evidence/trade-off 기반 recommendation |
| static model role | Luna-first risk-aware router |
| v2 shell/jq runtime layout | V3 Rust contract/planning/runtime |
| `hwahap/v2` artifact schema | `hwahap/v3` only; v2 artifact reject |
| v2 install/hook configuration | Desktop Skill + MCP + native binary |

Cutover에서 `skills/hwahap`은 V3 기준으로 다시 구성한다. v2 전용 hooks, shell helpers, `codex exec` templates, v2 tests/workflow는 유지하지 않는다. Hwahap-owned legacy 설정은 정리할 수 있지만 unrelated user Codex/MCP 설정은 손대지 않는다.

## 14. Compatibility probes required before implementation lock

다음은 사용자 preference가 아니라 사실 확인이 필요한 P0 probe다.

1. ChatGPT Desktop local MCP process lifetime, long-running call, restart behavior
2. Desktop Codex sandbox와 local MCP process의 OS 경계
3. official Rust ACP SDK와 pinned `codex-acp` v1 handshake
4. 하나의 `codex-acp`에서 concurrent multi-session 안전성
5. session별 cwd, sandbox mode, model, effort isolation
6. ChatGPT login auth 재사용과 credential 비접근 경로
7. session load/resume 시 MCP manifest와 event replay
8. cancellation의 App Server/process tree 전달
9. Desktop에서 long-running cycle 결과가 같은 task에 표시되는지
10. macOS/Windows orphan process 0

probe 결과가 권장 topology와 다르면 user-facing lifecycle은 유지하되 host implementation만 수정한다.

## 15. V3 design decisions

- **V3-D1**: `PLAN -> FREEZE -> BUILD -> PR -> ADJUST/SHIP` 세 cycle.
- **V3-D2**: Plan은 user-intensive, Build는 정상 경로 human gate 0.
- **V3-D3**: 모든 material decision은 alternatives와 recommendation contract를 가짐.
- **V3-D4**: Recommendation은 implicit default가 아니며 `C<n>=REC`가 있어야 확정.
- **V3-D5**: `ACCEPT_ALL` 금지; large/high-risk all-REC round는 checkpoint 필요.
- **V3-D6**: repository fact는 Hwahap이 조사.
- **V3-D7**: 말로 해결 못 하는 decision은 probe로 전환.
- **V3-D8**: Plan Freeze는 goal/render/recommendation/fact digest에 결속.
- **V3-D9**: successful build의 Agent product decision count는 0.
- **V3-D10**: PlanConflict는 affected graph만 park하고 독립 work 계속.
- **V3-D11**: cheap fact/implementation/verification은 Luna 우선.
- **V3-D12**: Terra는 semantic criticism과 persistent failure diagnosis 중심.
- **V3-D13**: Sol은 recommendation/plan synthesis, replan, final aggregate review 중심.
- **V3-D14**: model escalation은 recorded reason 필요.
- **V3-D15**: Parent Codex는 low-level orchestration을 수행하지 않음.
- **V3-D16**: Desktop -> Hwahap은 MCP, Hwahap -> Worker는 ACP v1.
- **V3-D17**: Hwahap control plane은 Rust native binary 하나로 배포.
- **V3-D18**: `codex-acp`는 pinned managed companion; True Single Binary라고 주장하지 않음.
- **V3-D19**: 상시 daemon은 기본이 아님.
- **V3-D20**: worker별 nested `codex exec` 0회.
- **V3-D21**: adapter는 run당 하나 우선; probe 실패 시 bounded pool.
- **V3-D22**: product contract는 파일, runtime lifecycle은 SQLite가 소유.
- **V3-D23**: unit별 detached worktree와 patch integration.
- **V3-D24**: final review는 직접 수정하지 않고 rework/replan으로 finding 반환.
- **V3-D25**: 완료 산출물은 draft PR.
- **V3-D26**: `SHIP`은 final gate + ready 전환; merge/auto-merge 없음.
- **V3-D27**: adjustment는 affected decisions/units만 무효화.
- **V3-D28**: Desktop private App Server topology에 의존하지 않음.
- **V3-D29**: V3는 v2를 호환성 없이 전면 교체하며 v2 schema/runtime/hook/artifact contract를 지원하지 않음.
- **V3-D30**: v2/v3 dual-mode selector, automatic v2 artifact import, compatibility adapter를 만들지 않음.

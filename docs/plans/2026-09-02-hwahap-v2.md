# hwahap v2 통합 기획안: align → build → improve

작성일: 2026-09-02. 상태: 기획 확정. 개정 1 (2026-09-02): build 성공 시 자동 draft PR과 신호 기반 자동 improve를 추가했다 (§3.5, D21~D27, §7.5). 이 문서는 Codex가 그대로 구현할 수 있도록 모든 결정을 고정했다. 구현자는 §9의 실행 단위를 순서대로 진행하고, §11의 확인 항목 외에는 새 결정을 만들지 않는다. 새 결정이 필요해지면 구현을 멈추고 사용자에게 묻는다.

## 0. 이 문서를 읽는 방법

- §1 결론과 §4 고정 결정만 읽어도 무엇을 만드는지 알 수 있다.
- §5 파일 구성, §6 데이터 형식, §7 단계별 프로토콜, §8 hook 계약은 구현 명세다.
- §9 실행 단위는 Codex가 따라야 할 작업 순서다. 각 단위는 200줄 이내의 변경, 테스트, 수용 기준을 가진다.
- §10 테스트 계획은 SQLite의 테스트 관행을 이 프로젝트 규모에 맞게 옮긴 것이다. 구현 코드는 단순하게, 테스트는 엄격하게 한다.
- §3 4원칙 검수는 이 설계가 원칙을 어디서 충족하고 어디서 조건부인지 기록한다.

용어는 §2에서 한 번만 정의한다. 문서 안에서 비유는 쓰지 않는다.

## 1. 결론

hwahap v2는 하나의 스킬이며 세 단계로 운영된다.

1. `align`: 사용자와 구현 방향을 확정해 `goal.json` 하나를 만든다. 기존 align-goal 스킬의 역할이다.
2. `build`: `goal.json`의 unit을 worktree에서 병렬로 구현하고 기계 검증과 의미 검토를 거친다. 모든 gate를 통과하면 생성 branch에 commit 하고 draft PR을 자동으로 연다. 기존 hwahap 스킬의 역할이다.
3. `improve`: 과거 실행 기록을 benchmark로 삼아 하네스 설정 변경을 측정 뒤 채택하거나 되돌린다. build가 끝난 뒤 개선 신호가 있을 때만 자동으로 시작하며, 결과는 harness 저장소의 draft PR이다.

없애는 것은 다음과 같다. Python 코드 전부, Codex Goal 도구 연동, `.codex/agents` 프로필과 installer, 세션 subagent 스폰, `.hwahap` 상태 기계와 영수증 명령, HTML 보고서, Ultra 최종 검토, Luna verifier, Sol planner, grill-prfaq. 남는 코드는 shell 스크립트 7개와 jq 프로그램이며 각 파일은 80줄 이하다.

기존 PR #4, #5, #6은 2026-09-02에 닫았다. v1 스킬은 §9 U10까지 저장소에 그대로 둔다.

## 2. 용어

| 용어 | 정의 |
|---|---|
| root | 사용자가 `codex --profile hwahap`으로 연 대화형 세션. Sol 모델. 오케스트레이션과 align 질문을 담당한다. |
| worker | root의 shell에서 `codex exec`로 띄우는 비대화형 프로세스. unit 하나를 구현한다. Luna 모델. |
| reviewer | `codex exec`로 띄우는 읽기 전용 프로세스. unit 또는 통합 결과의 의미를 검토한다. Terra 모델. |
| proposer | improve 단계에서 `codex exec`로 띄우는 읽기 전용 프로세스. 하네스 설정 변경 하나를 patch로 제안한다. Sol 모델. |
| unit | 독립적으로 테스트할 수 있는 최소 변경. `paths`, `test`, `depends_on`을 가진다. |
| worktree | `git worktree add --detach`로 만든 checkout. unit마다 하나, 통합용 하나. |
| patch | unit worktree의 `git diff HEAD` 출력. unit의 유일한 산출물이자 증거. |
| brief | worker, reviewer, proposer에게 넘기는 지시문. `goal.json`에서 스크립트가 생성한다. |
| gate | 다음 단계로 넘어가도 되는지를 판정하는 결정적 검사. 스크립트가 수행하며 모델의 주장을 입력으로 쓰지 않는다. |
| deliver | gate 통과 뒤 통합 결과를 생성 branch에 commit 하고 push 한 뒤 draft PR을 여는 절차. |
| base branch | align 시작 시 사용자 checkout의 branch. deliver의 PR base다. |
| draft PR | GitHub의 draft 상태 PR. 사람이 ready로 바꾸기 전에는 merge 대상이 아니다. |
| hook | Codex가 정해진 이벤트에 실행하는 외부 명령. sandbox 밖에서 실행된다. |
| budget | 한 run에서 worker와 reviewer가 쓸 수 있는 토큰 총량. improve는 별도 budget을 가진다. |
| benchmark | 과거 run의 `goal.json`과 `summary.json` 묶음. improve 단계의 측정 대상. |
| ruler | benchmark 위에서 계산하는 지표. 통과 unit당 비용과 첫 시도 gate 통과율. |
| noise band | 같은 설정으로 반복 실행했을 때 ruler가 흔들리는 폭. `max(2σ, floor)`. |
| canary | 결과를 아는 변경. ruler가 그 변경을 noise band 밖에서 감지해야 측정을 신뢰한다. |
| signal | 방금 끝난 run에서 improve를 시작할 근거. §7.5에 정의한다. |
| diary | root가 실행 중 적는 관찰 기록. Interpretations, Deviations, Tradeoffs, Open questions 네 제목. |
| lesson | 다음 run의 규칙 후보. 사용자가 확인해야만 규칙이 된다. |

## 3. 4원칙 검수

### 3.1 단순함 (KISS)

기준: 구현체는 요구를 만족하는 가장 단순한 설계를 고르고, 요구가 아닌 것을 위한 복잡성을 두지 않는다. `general/CLAUDE.md`의 규칙이다.

| 항목 | v1 | v2 |
|---|---|---|
| 언어 | Python 6,131줄, 245파일 | shell 7개, jq. 각 80줄 이하 |
| 역할 | 6개 프로필 설치 | 3개 실행 역할. root, worker, reviewer. improve의 proposer는 reviewer와 같은 방식이다. 설치 없음 |
| 상태 | contract, run, events, units, report 5종 | `goal.json`과 `out/` 산출물 파일 |
| 플랫폼 결합 | Goal 도구, subagent, 프로필 | `codex exec`, `gh`, 파일. 플랫폼 기능이 바뀌어도 영향 없음 |
| 문서 | 1,706줄 | SKILL.md 80줄 이하 |

판정: 충족. 조건은 §4 D12의 줄 수 상한과 D13의 방어 코드 금지를 지키는 것이다. shell은 조건이 늘면 빠르게 복잡해지므로, `if`에 복합 조건을 쓰지 않고 한 스크립트가 한 결정만 내리게 한다.

### 3.2 엄격함 (SQLite 방식 테스트)

기준: https://www.sqlite.org/testing.html 의 관행이다. 독립 harness 여러 개, 100% branch와 MC/DC coverage, anomaly 테스트(OOM, I/O 오류, crash, 복합 실패), fuzz, boundary, 모든 버그의 regression 테스트, 자동 자원 누수 검출, mutation 검사, undefined behavior 검사, 최적화 끄고 재실행, 사람이 수행하는 checklist, 정적 분석. SQLite는 라이브러리 코드의 590배 테스트 코드를 가진다.

| SQLite 관행 | v2 대응 | 상태 |
|---|---|---|
| 독립 harness 여러 개 | (1) bats fixture 테스트, (2) `codex`와 `gh` shim으로 API 없이 도는 결정적 E2E, (3) 실제 모델로 도는 수동 smoke | §10.1 |
| 100% branch coverage | kcov로 shell 분기 측정, CI에서 100% 미만이면 실패 | §10.4 |
| MC/DC | 도구가 없으므로 구조로 보장. `if`에 단일 조건만 허용하면 branch coverage가 MC/DC와 같아진다 | §4 D14, §10.4 |
| mutation 검사 | `tests/mutate.sh`가 각 `if`의 조건을 뒤집고 테스트가 실패하는지 확인 | §10.5 |
| anomaly: OOM, I/O 오류, crash | worker 비정상 종료, 잘못된 JSONL, 테스트 timeout, `git apply` 충돌, 쓰기 불가 디렉터리, jq 부재, hook 입력 손상, push 거부, `gh` 실패 | §10.2 |
| 복합 실패 | 재시도 중 budget 초과, retry 실패 뒤 skip, 통합 중 충돌 뒤 abort, PR 생성 뒤 improve 실패 | §10.2 |
| fuzz | jq로 `goal.json`을 변형해 gate가 거부하는지 검사. patch 파일 fuzz | §10.3 |
| boundary | unit 0개, 1개, `max_parallel` 1과 N, budget 0, 정확히 80%와 100% | §10.3 |
| regression | 버그마다 `regress-<id>` fixture. fixture 없이 버그를 닫지 않는다 | §10.6 |
| 자원 누수 검출 | 모든 테스트 끝에 남은 worktree, codex 프로세스, 임시 branch가 0인지 검사 | §10.7 |
| undefined behavior 검사 | `bash -u -e -o pipefail`과 shellcheck. `shasum`과 `sha256sum` 양쪽 환경 | §10.8 |
| 최적화 끄고 재실행 | `max_parallel=1`과 `=N`의 산출물이 동일한지 비교 | §10.8 |
| checklist | `hwahap doctor`와 `tests/CHECKLIST.md`. 사람이 수행 | §10.9 |
| 정적 분석 | shellcheck 경고 0, 모든 jq 프로그램 파싱 검사 | §10.8 |

판정: 조건부 충족. 조건은 §10을 §9의 U8로 실제 구현하는 것과, 테스트 코드가 스크립트 코드의 3배 이상이 되는 것이다. 구현 코드를 줄이려고 테스트를 줄이지 않는다.

### 3.3 최적화 (Uber Efficient Software Factory)

기준: https://www.uber.com/us/en/blog/efficient-software-factory/. 비용은 `Users × Sessions/User × Turns/Session × Requests/Turn × Tokens/Request × Price/Token`이며 가운데 세 항을 줄인다. 서브에이전트는 약한 모델과 낮은 effort를 기본으로 한다. MCP 스키마를 컨텍스트에서 제거한다. 하위 프로세스 안에서 반복하고 요약만 돌려받는다. 비용은 결과 단위로 잰다. 새 agent마다 outcome metric, benchmark, Pareto 모델 순서로 정한다.

| Uber 항목 | v2 대응 |
|---|---|
| Turns/Session | root의 턴은 unit 묶음당 두 번. 스크립트가 worker 실행과 기록을 맡는다 |
| Requests/Turn | worker는 `codex exec` 하위 프로세스. root에는 마지막 메시지 파일만 돌아온다 |
| Tokens/Request | worker는 `--ignore-user-config`로 MCP 서버 4개, web_search, priority tier 없이 시작. root는 `tool_output_token_limit` 4000 |
| 약한 모델 기본 | worker Luna high, reviewer Terra high, root Sol medium. unit별 override는 `goal.json`에서 |
| 캐시 | brief 앞부분을 고정해 같은 goal의 worker끼리 prefix를 공유. effort는 run 중 바꾸지 않는다 |
| 비용 표시와 nudge | budget 80%에서 경고, 100%에서 새 unit 중단 뒤 사용자에게 질문. hard cap 없음 |
| 결과 단위 비용 | `summary.json`에 통과 unit당 비용, 첫 시도 통과율, 소요 시간 |
| benchmark 우선 | improve 단계는 benchmark 없이는 설정을 바꾸지 않는다 |
| managed agent는 별도 tier | 자동 improve는 사람 세션과 분리된 자체 budget을 가지며 그 budget은 hard cap이다 |
| anti-pattern | 시스템 지시 선적재는 SKILL.md 80줄로, MCP 잔류는 worker 격리로, 캐시 만료는 effort 고정으로 막는다 |

근거 자료: 2026-08-30 PR #5 세션 rollout의 마지막 `token_count`는 total 381,088,447, cached 376,223,744였다. 한 세션이 3억 8천만 토큰을 썼고 대부분이 매 턴 다시 보낸 컨텍스트였다. v2는 root 컨텍스트에 worker 대화가 들어오지 않게 하는 것으로 이 구조를 끊는다.

판정: 충족. 다만 측정 없이는 최적화를 주장할 수 없으므로 §10.1의 실제 모델 smoke에서 v1과 같은 goal을 돌려 `summary.json`을 비교하는 것을 U9 수용 기준에 넣는다.

### 3.4 재귀적 개선 (KiroCrew auto-improvement)

기준: https://github.com/kirodotdev/KiroCrew 의 `auto_improvement` 앱. 측정 시스템이 먼저다. ruler를 보정하고 canary로 증명한 뒤에만 변경한다. agent는 제안만 하고 결정은 결정적 코드가 한다. 후보는 worktree마다 격리한다. edit allowlist를 측정 전에 검사한다. keep-or-revert. 비용 상한과 quiescence 정지. 산출물은 draft PR뿐이다. 학습은 검토를 통과해 배포된 결함처럼 허용된 출처에서만 하고, 일반화하며, staging 뒤 사람이 consolidation을 트리거한다.

| KiroCrew 항목 | v2 대응 |
|---|---|
| 측정 먼저 | benchmark 5개 이상, 같은 goal 3회 반복으로 noise band, canary 통과 전에는 변경 없음 |
| 제안은 agent, 결정은 코드 | proposer가 설정 변경 하나를 patch로 제안. `improve.sh`가 benchmark 재실행 결과로 keep/revert |
| 후보 격리 | harness 저장소의 worktree에서 제안 |
| edit allowlist | 바꿀 수 있는 것은 `skills/hwahap/` 안의 effort, 모델, brief 문안, `max_parallel`, `tool_output_token_limit`뿐 |
| 정지 | improve 자체 budget, 3 cycle 무성과 정지, 무성과 3회 뒤 자동 improve 비활성화 |
| draft PR | keep된 변경은 harness 저장소의 생성 branch에 commit 하고 draft PR로 연다. merge와 ready 전환은 사람이 한다 |
| 허용 출처 | gate 실패, 사용자 수정, 사용자가 되돌린 patch. reviewer 자신의 의견은 출처가 아니다 |
| staging | `lessons.candidates.md`에 쌓고 사용자가 AGENTS.md나 SKILL.md에 옮긴다 |

판정: 조건부 충족. 조건은 benchmark 실행이 실제 토큰을 쓰므로 자동 improve를 신호와 budget으로 묶는 것이다 (§3.5). 자동 학습 수집은 두지 않는다. 사용자가 2026-08-18에 recursive-learning 자동화를 걷어내고 의도적 작업 기반 루프로 바꾼 결정을 따른다.

### 3.5 자동 인도와 자동 improve 검수

사용자 제안: build가 끝나고 LLM 차원의 문제가 없으면 PR을 자동으로 올리고, 이어서 improve를 자동으로 진행한다.

| 원칙 | 판정 | 조건 |
|---|---|---|
| 단순함 | 충족 | 새 hook 없이 `gate.sh`가 통과 뒤 `deliver.sh`를 부르고 `improve.sh`를 백그라운드로 띄운다. 스크립트 하나가 늘어 7개가 된다 |
| 엄격함 | 조건부 충족 | `gh`와 push 실패, 중복 PR, protected branch, improve 비동기 실패가 fixture로 고정돼야 한다. §10.2에 추가했다 |
| 최적화 | 조건부 충족 | 무조건 자동 improve는 신호 없이 토큰을 쓰므로 Uber의 "zero-value token 제거" 원칙에 어긋난다. 신호가 있을 때만, 주 1회 이하, 별도 hard budget으로 돌리면 충족한다 |
| 재귀적 개선 | 조건부 충족 | KiroCrew의 안전 모델을 그대로 가져와야 한다. 생성 branch, draft PR만, protected branch 금지, ruler 미증명 시 정지, quiescence 뒤 자동 비활성화 |

결론: 제안은 4원칙에 위배되지 않으며 위 조건을 D21~D27로 고정해 반영했다. 사람의 검토 지점은 `CONFIRM BUILD`에서 draft PR 검토로 옮겨진다. 무인 실행(`HWAHAP_UNATTENDED=1`)에서는 자동 인도를 하지 않는다.

## 4. 고정 결정

- D1. Python을 쓰지 않는다. 언어는 POSIX shell(bash 3.2 이상 호환), jq, git이다.
- D2. Codex Goal 도구(`get_goal`, `create_goal`, `update_goal`)를 호출하지 않는다.
- D3. `.codex/agents` 프로필을 만들거나 설치하지 않는다. worker와 reviewer는 `codex exec`의 `-m`, `-c` 플래그로 정의한다.
- D4. worker와 reviewer는 root 세션의 shell에서 띄우는 `codex exec` 하위 프로세스다. 세션 subagent 도구는 쓰지 않는다.
- D5. build 중에는 `git commit`, `git add`, `git stash`를 실행하지 않는다. 허용하는 git 명령은 `worktree add/remove/list`, `diff`, `apply`, `hash-object`, `rev-parse`, `status`, `ls-files`다. commit, push, branch 생성은 `deliver.sh`와 `improve.sh`의 인도 절차에서만, 생성 branch에 대해서만 실행한다.
- D6. worktree는 대상 저장소의 `.hwahap/wt/<unit>`과 `.hwahap/wt/integration`에 만든다. `.hwahap/`은 gitignore 대상이며 없으면 `hwahap doctor`가 실패한다.
- D7. 모델과 effort의 기본값은 root Sol medium, worker Luna high, reviewer Terra high, proposer Sol medium이다. `goal.json`의 unit 항목에서 `model`과 `effort`를 override할 수 있다. Ultra는 쓰지 않는다.
- D8. root 세션은 `~/.codex/hwahap.config.toml` profile로 연다. 내용은 `model_reasoning_effort = "medium"`, `service_tier` 미설정, `sandbox_workspace_write.network_access = true`, `tool_output_token_limit = 4000`이다.
- D9. hook은 `~/.codex/hooks.json`에 한 번 등록한다. 등록되는 것은 `UserPromptSubmit`의 `prompt.sh`와 `Stop`의 `gate.sh` 둘뿐이다. 두 스크립트는 현재 디렉터리에 `.hwahap/goal.json`이 없으면 아무것도 하지 않고 exit 0 한다.
- D10. 상태 파일은 `goal.json`과 `out/` 산출물뿐이다. 이벤트 로그, 상태 기계, 영수증 명령은 없다. 현재 상태는 산출물 파일의 존재와 내용에서 계산한다.
- D11. 사용자 답변은 `prompt.sh`가 기록한다. 모델은 답변 파일을 쓰지 않는다. gate는 workspace 밖 사본과 대조한다.
- D12. 스크립트 하나는 80줄 이하, SKILL.md는 80줄 이하다. 넘으면 책임 단위로 나누되 스크립트 수는 8개를 넘지 않는다. 테스트와 fixture는 상한이 없다.
- D13. 방어 코드를 두지 않는다. 입력이 잘못되면 첫 검사에서 이유를 출력하고 exit 1 한다. 같은 조건을 두 번 검사하지 않는다.
- D14. `if`와 `[ ]`에 `&&`, `||`로 묶인 복합 조건을 쓰지 않는다. 조건 하나가 결정 하나다.
- D15. 시간에 의존하는 테스트를 두지 않는다. `sleep`으로 순서를 맞추지 않는다. 시각은 `HWAHAP_NOW` 환경변수로 주입할 수 있다.
- D16. 보고서는 markdown 하나이며 순서는 결론, 근거, 확인 과정, 한계, 비용이다. HTML은 만들지 않는다.
- D17. budget은 worker와 reviewer 토큰의 합에만 적용한다. root 토큰은 따로 측정해 보고한다.
- D18. unit당 worker 시도는 2회, reviewer 라운드는 2회가 상한이다. 초과하면 사용자에게 retry, skip, abort를 묻는다.
- D19. 문서-only 요청, 질문, 아이디어 탐색에는 hwahap을 쓰지 않는다. SKILL.md의 첫 규칙이다.
- D20. 대상 플랫폼은 Codex CLI 0.151 이상이다. Claude Code 어댑터는 범위 밖이다.
- D21. `CONFIRM ALIGN` 뒤 build는 자율로 진행한다. 사람에게 묻는 경우는 D18의 실패, budget 100%, 통합 충돌뿐이다. `CONFIRM BUILD`는 없다.
- D22. gate 통과 시 `deliver.sh`가 통합 결과를 `hwahap/<goal_id>` branch에 commit 하고 push 한 뒤 `gh pr create --draft`로 PR을 연다. base는 `goal.json`의 `base_branch`다. PR 본문은 `report.md`다.
- D23. head branch는 항상 `hwahap/` 또는 `hwahap-improve/` 접두사를 가진다. `main`, `master`, `develop`, `release/*`, 그리고 `base_branch` 자체에는 push 하지 않는다. 이 목록은 스크립트 상수이며 설정으로 넓힐 수 없다.
- D24. 하네스는 PR을 ready로 바꾸거나 merge 하거나 auto-merge를 켜지 않는다. 같은 이름의 branch나 열린 PR이 이미 있으면 새 것을 만들지 않고 사용자에게 묻는다.
- D25. `HWAHAP_UNATTENDED=1`이면 gate는 판정만 하고 인도하지 않는다.
- D26. 자동 improve는 §7.5의 신호가 있고, 마지막 자동 improve로부터 7일이 지났고, benchmark가 5개 이상이고, `~/.codex/hwahap/config.json`에 `improve.auto = true`와 `improve.budget_tokens`가 있을 때만 시작한다. budget은 hard cap이다. 신호가 없으면 `summary.json`에 이유를 적고 토큰을 쓰지 않는다.
- D27. 자동 improve가 3회 연속 무성과이면 `improve.auto`를 `false`로 바꾸고 이유를 기록한다. 다시 켜는 것은 사용자다. 수동 `hwahap improve`는 이 제한을 받지 않는다.

## 6. 데이터 형식

### 6.1 goal.json

```json
{
  "schema": "hwahap/v2",
  "goal_id": "2026-09-02-example",
  "base_branch": "main",
  "goal": {"statement": "한 문장", "success": ["관찰 가능한 조건"], "non_goals": ["하지 않는 것"]},
  "surfaces": {"applicable": ["S1", "S3"], "not_applicable": {"S8": "단일 프로세스라 동시성 없음"}},
  "choices": [
    {"id": "C1", "surface": "S3", "question": "질문",
     "alternatives": [{"id": "ALT1", "value": "정확한 값"}, {"id": "ALT2", "value": "다른 값"}],
     "recommendation": "ALT1", "evidence": ["src/a.py:10 관찰"],
     "answer": {"text": "C1=ALT1", "ts": "2026-09-02T10:00:00+09:00", "choice_sha256": "sha256:..."}}
  ],
  "specs": [{"id": "SP1", "statement": "구현 계약", "choice_ids": ["C1"]}],
  "acceptance": [{"id": "A1", "spec_ids": ["SP1"], "test": "pytest tests/test_a.py -k create"}],
  "units": [
    {"id": "U1", "title": "Create 구현", "paths": ["src/a.py", "tests/test_a.py"],
     "test": "pytest tests/test_a.py -k create", "acceptance_ids": ["A1"], "depends_on": [],
     "model": null, "effort": null}
  ],
  "open_items": [{"id": "O1", "text": "미확정", "status": "open"}],
  "review": {"cold": {"ts": "...", "goal_sha256": "sha256:...", "required_user_choices": [], "underspecified": [], "unmapped_spec_ids": []}},
  "confirm": {"text": "CONFIRM ALIGN", "ts": "...", "goal_sha256": "sha256:..."},
  "budget": {"tokens": 3000000, "max_parallel": 3},
  "final_review": "terra",
  "full_suite": "pytest"
}
```

규칙:

- `base_branch`는 align 시작 시 `git rev-parse --abbrev-ref HEAD`다. detached면 `gh repo view --json defaultBranchRef`의 값이다.
- `surfaces`의 키는 SKILL.md에 적힌 12개 결정 표면 ID다. 모든 표면은 `applicable`에 있거나 `not_applicable`에 이유와 함께 있어야 한다. `applicable` 표면마다 `surface`가 그 값인 choice가 하나 이상 있어야 한다.
- `alternatives`는 2개 이상이고 `value`는 서로 달라야 한다.
- `answer.text`는 `C<n>=<ALT id>` 또는 `C<n>=OTHER: <값>` 형식이다. `OTHER:`이면 그 값을 가진 alternative를 `origin: "user"`로 추가한다.
- `answer.choice_sha256`은 `{id, question, alternatives}`를 `jq -S -c`로 직렬화한 바이트의 sha256이다. `prompt.sh`가 계산한다. 답변 뒤 alternatives를 바꾸면 이 값이 달라져 gate가 거부한다.
- `review.cold.goal_sha256`과 `confirm.goal_sha256`은 `goal.json`에서 `review`와 `confirm`을 뺀 문서의 `jq -S -c` sha256이다.
- 모든 `spec`은 하나 이상의 `acceptance`에, 모든 `acceptance`는 하나 이상의 `unit`에 속해야 한다.
- `units[].test`는 비어 있을 수 없다. `paths`는 저장소 상대 경로이며 `..`, 절대 경로, `.hwahap/`을 포함할 수 없다.
- `depends_on`은 DAG여야 한다. 순환이 있으면 gate가 거부한다.
- `budget.tokens`의 기본값은 unit 수 × 500,000이다.

### 6.2 answers.jsonl

한 줄에 하나. `prompt.sh`가 쓴다.

```json
{"ts": "2026-09-02T10:00:00+09:00", "text": "C1=ALT1", "choice_id": "C1", "choice_sha256": "sha256:...", "prev": "sha256:...|null", "hash": "sha256:..."}
```

`hash`는 `{ts, text, choice_id, choice_sha256, prev}`의 `jq -S -c` sha256이다. `CONFIRM ALIGN`은 `choice_id`가 `null`이고 `choice_sha256` 자리에 `goal_sha256`이 들어간다.

### 6.3 out/<unit>.usage.json

`unit.sh`가 `events.jsonl`의 `turn.completed` 이벤트를 합산한다.

```json
{"unit": "U1", "attempt": 1, "model": "gpt-5.6-luna", "effort": "high",
 "input_tokens": 0, "cached_input_tokens": 0, "output_tokens": 0, "reasoning_output_tokens": 0,
 "cost_usd": 0.0, "started": "...", "ended": "...", "seconds": 0}
```

`cost_usd`는 `prices.json`의 단가로 계산한다. 단가는 input, cached_input, output 세 가지이고 reasoning은 output에 포함된다.

### 6.4 out/review/<unit>.md

reviewer의 마지막 메시지를 그대로 저장한다. 첫 줄은 반드시 `verdict: pass` 또는 `verdict: fail`이다. 그 아래에 finding을 `- [paths|intent|test] 설명` 형식으로 적는다. `review.sh`는 첫 줄 형식이 맞지 않으면 exit 1 한다.

### 6.5 report.md

```
# hwahap 보고서: <goal_id>
## 결론          통과 unit 수 / 전체, 통합 결과, PR URL 또는 미인도 이유

## 확인 과정     gate 검사 목록과 각 결과
## 한계          diary의 Deviations와 Open questions, 실행하지 않은 검사, 측정 불가 항목
## 비용          worker·reviewer 합계, root 토큰, 통과 unit당 비용, improve 시작 여부와 이유
```

## 7. 단계별 프로토콜

### 7.1 doctor

`hwahap doctor`는 다음을 검사하고 하나라도 실패하면 이유와 함께 exit 1 한다.

1. `codex --version`이 0.151 이상.
2. `jq`, `git`, `gh`, `shasum` 또는 `sha256sum`이 PATH에 있음. `gh auth status`가 성공함.
3. 현재 디렉터리가 git 저장소이고 `.hwahap/`이 ignore 대상이며 `origin` remote가 있음.
4. `~/.codex/hooks.json`에 `prompt.sh`와 `gate.sh`가 등록됨.
5. `~/.codex/hwahap.config.toml`이 존재함.
6. sandbox 안에서 `codex exec`가 네트워크에 닿음. 검사 방법은 §11.1.

### 7.2 align

1. root가 사용자의 요청을 읽고 `goal.json`의 `goal`과 `base_branch`를 쓴다. 기술 스택을 먼저 묻는다.
2. root가 12개 결정 표면을 순서대로 검토해 `surfaces`를 채운다. 표면마다 저장소를 조사한 근거를 `evidence`에 적는다.
3. 의존성 없는 choice를 한 라운드에 최대 8개 질문한다. 답에 의존하는 choice는 다음 라운드로 넘긴다. 라운드 수 상한은 없다.
4. 사용자는 채팅에 `C1=ALT2` 형식으로 답한다. `prompt.sh`가 기록하고 root가 `goal.json`의 `answer`에 옮긴다. `ok`, `추천대로` 같은 문장은 기록되지 않으므로 root는 같은 choice를 다시 묻는다.
5. 모든 choice가 답변되고 open item이 없으면 root가 `specs`, `acceptance`, `units`를 쓴다.
6. `hwahap review cold`가 Terra reviewer를 읽기 전용으로 띄운다. brief는 `goal.json` 전문과 "선택 없이 구현 계획을 쓰고, 새 사용자 결정이 필요한 곳과 명세가 부족한 곳을 나열하라"는 지시다. 결과는 `review.cold`에 기록되고 `required_user_choices`, `underspecified`, `unmapped_spec_ids`가 모두 비어야 한다. 비어 있지 않으면 3단계로 돌아간다.
7. root가 요약을 보여주고, build가 자율로 진행되며 성공 시 draft PR이 자동으로 열린다는 것을 알린 뒤 사용자가 `CONFIRM ALIGN`을 친다. `prompt.sh`가 현재 `goal_sha256`과 함께 기록한다.
8. `hwahap align-check`가 §6.1 규칙 전부와 답변 사본 대조를 수행한다. 통과해야 build로 넘어간다.

align 단계는 `goal.json`을 바꾸는 유일한 단계다. build 시작 뒤 `goal.json`이 바뀌면 gate가 `confirm.goal_sha256` 불일치로 거부한다.

### 7.3 build

1. `hwahap unit U1 U2 ...`가 의존성이 해결된 unit을 `max_parallel`까지 동시에 시작한다. unit마다:
   - `.hwahap/wt/<unit>`이 없으면 `git worktree add --detach .hwahap/wt/<unit> HEAD`. `depends_on`이 있으면 선행 unit의 patch를 먼저 `git apply` 한다.
   - brief를 생성한다. 순서는 `brief.head.md`의 고정 머리말, AGENTS.md 경로, unit의 `title`, `paths`, `test`, 관련 spec과 acceptance 전문, "commit과 stage 금지, `paths` 밖 수정 금지, 끝나면 변경 요약 한 문단" 순이다. 머리말이 고정이므로 prefix 캐시가 공유된다.
   - 다음 명령으로 worker를 띄운다.

```sh
HWAHAP_UNIT=U1 codex exec -C .hwahap/wt/U1 -s workspace-write \
  --ignore-user-config -m gpt-5.6-luna -c model_reasoning_effort=high \
  -c tool_output_token_limit=4000 --ephemeral --json \
  -o .hwahap/out/U1.last.md "$(cat .hwahap/out/U1.brief.md)" > .hwahap/out/U1.events.jsonl
```

   - 종료 뒤 `git -C .hwahap/wt/U1 diff HEAD > out/U1.patch`, `git diff --name-only`가 `paths` 안인지 검사, `test`를 worktree에서 실행해 `out/U1.test.txt`에 기록, `events.jsonl`에서 usage 합산.
   - 테스트 실패면 `attempt`를 올리고 같은 worktree에서 한 번 더 띄운다. brief에 테스트 출력을 덧붙인다. 두 번째도 실패면 멈추고 한 줄 요약을 출력한다.
2. 시작 전 budget 검사. `out/*.usage.json` 합이 80% 이상이면 `out/budget.warn`을 쓰고 요약 줄에 경고를 붙인다. 100% 이상이면 새 unit을 시작하지 않고 `HW_BUDGET`을 출력한다.
3. `hwahap review U1`이 Terra reviewer를 `-s read-only`로 같은 worktree에서 띄운다. brief는 goal의 spec과 acceptance, unit 정의, patch 전문, "계약 이탈과 의도 불일치만 보고하라"는 지시다. `verdict: fail`이면 finding을 덧붙여 1단계의 재시도로 돌아간다. 라운드 상한은 2회다.
4. root는 unit 요약 줄만 읽는다. 실패한 unit은 사용자에게 retry, skip, abort를 묻는다. skip한 unit에 의존하는 unit은 시작하지 않는다.
5. 모든 unit이 pass면 `hwahap integrate`가 `.hwahap/wt/integration`에 patch를 위상 순서로 `git apply --check` 뒤 `git apply` 하고 `full_suite`를 실행한다. 충돌이나 실패는 사용자에게 묻는다.
6. `hwahap review integration`이 통합 diff를 검토한다. `final_review`가 `sol`이면 `-m gpt-5.6-sol`을 쓴다.
7. root가 diary를 마무리하고 종료한다. 사용자에게 추가 확인을 요청하지 않는다.
8. root가 종료하면 `gate.sh`가 실행된다. §8.2의 검사를 모두 통과하면 `report.md`와 `summary.json`을 만들고 §7.4의 deliver를 부른 뒤 §7.5의 improve 판정을 한다. 하나라도 실패하면 종료를 막고 이유를 root에게 돌려준다.

### 7.4 deliver

`deliver.sh`는 gate 통과 뒤 `gate.sh`가 부른다. 수동 `hwahap deliver`도 같은 스크립트다.

1. `HWAHAP_UNATTENDED=1`이면 `out/deliver.txt`에 `skipped:unattended`를 쓰고 끝낸다.
2. head branch 이름은 `hwahap/<goal_id>`다. D23의 금지 목록과 대조한다. `git ls-remote --heads origin hwahap/<goal_id>`에 결과가 있거나 `gh pr list --head hwahap/<goal_id> --state open`에 결과가 있으면 `skipped:exists`를 쓰고 사용자에게 알린다.
3. `.hwahap/wt/integration`에서 `git switch -c hwahap/<goal_id>` 뒤 모든 unit `paths`의 합집합만 `git add -- <paths>` 한다. 합집합 밖 변경이 있으면 실패다. 이 검사는 §8.2의 7번과 같은 조건이므로 다시 검사하지 않고 그 결과를 신뢰한다.
4. commit 메시지는 첫 줄 `hwahap: <goal.statement>`, 본문에 통과 unit 목록, trailer `Hwahap-Goal: <goal_id>`다. 작성자는 사용자의 git 설정을 그대로 쓴다.
5. `git push -u origin hwahap/<goal_id>` 뒤 `gh pr create --draft --base <base_branch> --head hwahap/<goal_id> --title "hwahap: <goal.statement>" --body-file .hwahap/report.md`.
6. PR URL을 `out/deliver.txt`와 `summary.json`의 `pr_url`에 쓴다. push나 `gh`가 실패하면 `failed:<명령>`을 쓰고 branch는 남긴다. 재시도하지 않는다.
7. worktree는 지우지 않는다. 사용자가 PR을 처리한 뒤 `hwahap clean <goal_id>`로 지운다.

### 7.5 improve

자동 시작 판정은 `gate.sh`가 deliver 뒤에 한다. 순서는 다음과 같고 하나라도 아니면 `summary.json`의 `improve.reason`에 이유를 적고 끝낸다.

1. `~/.codex/hwahap/config.json`에 `improve.auto`가 `true`이고 `improve.budget_tokens`가 있다.
2. `harness_repo`가 git 저장소다.
3. 신호가 있다. 신호는 둘 중 하나다. 방금 run의 `cost_per_passed_unit`이 같은 저장소 benchmark의 중앙값보다 크거나, `first_try_pass`가 `units_passed`보다 작다.
4. `improve.state.json`의 마지막 자동 실행이 7일 이전이다.
5. benchmark가 5개 이상이다.
6. deliver가 `done`이다. PR 없이 improve를 돌리지 않는다.

조건을 모두 만족하면 `gate.sh`는 `improve.sh --auto --budget <improve.budget_tokens>`를 백그라운드로 띄우고 exit 0 한다. hook 자체는 improve를 기다리지 않는다. `improve.sh`는 `~/.codex/hwahap/improve/<date>.log`에 진행을 쓰고, 끝나면 `improve.state.json`을 갱신한다.

`improve.sh`의 절차는 자동과 수동이 같다.

1. `harness_repo`에 `git worktree add --detach <tmp> HEAD`로 작업 공간을 만든다.
2. ruler 보정. 가장 작은 benchmark goal 하나를 현재 설정으로 3회 재실행해 `cost_per_passed_unit`의 평균과 표준편차를 구한다. noise band는 `max(2σ, 평균의 10%)`다.
3. canary. worker effort를 `medium`으로 낮춘 설정으로 같은 goal을 1회 실행한다. 비용 차이가 band 밖이어야 한다. 아니면 "ruler 미증명"으로 종료하고 무성과 1회로 센다.
4. proposer를 `codex exec -C <tmp> -s read-only --ignore-user-config -m gpt-5.6-sol -c model_reasoning_effort=medium --ephemeral`로 띄운다. brief는 benchmark summary 전부, 방금 run의 `summary.json`, 허용 변경 범위(worker effort, reviewer 모델, `brief.head.md` 문안, `max_parallel`, `tool_output_token_limit`), "변경 하나를 unified diff로만 출력하라"는 지시다. 출력이 diff가 아니거나 허용 범위 밖 파일을 건드리면 무성과 1회로 센다.
5. diff를 `<tmp>`에 `git apply` 하고 benchmark goal 전부를 그 설정으로 실행해 ruler를 계산한다. `cost_per_passed_unit`이 band 이상 개선되고 `first_try_pass` 비율이 떨어지지 않으면 keep, 아니면 revert다.
6. keep이면 `<tmp>`에서 `git switch -c hwahap-improve/<date>`, 허용 범위 파일만 `git add`, commit, push, `gh pr create --draft` 한다. 본문은 benchmark 전후 표와 noise band다. revert이면 worktree를 지운다.
7. 3회 연속 무성과이면 종료하고, 자동 실행이었으면 D27대로 `improve.auto`를 `false`로 바꾼다. budget을 넘어도 종료한다.

lesson은 별도 명령이다. `hwahap lesson "<한두 문장>"`은 `lessons.candidates.md`에 날짜와 함께 append 한다. 허용 출처는 gate 실패, 사용자의 수정, 사용자가 되돌린 patch다. root는 사용자가 이 셋 중 하나를 말했을 때만 lesson을 제안한다. 규칙으로 옮기는 것은 사용자가 한다.

## 8. hook 계약

### 8.1 prompt.sh (UserPromptSubmit)

- 입력: stdin JSON. 사용할 필드는 프롬프트 텍스트와 세션 식별자다. 정확한 필드명은 U1에서 확인해 `hwahap-v2-verification.md`에 기록하고 스크립트 상수로 둔다.
- `.hwahap/goal.json`이 없으면 exit 0.
- `.hwahap/human.turn`에 현재 시각을 쓴다.
- 텍스트가 `^C[0-9]+=`이면 해당 choice의 `choice_sha256`을 계산해 §6.2 형식으로 `answers.jsonl`과 workspace 밖 사본에 같은 줄을 append 한다. `^CONFIRM ALIGN$`이면 `goal_sha256`으로 같은 처리를 한다.
- 실패해도 사용자의 턴을 막지 않는다. 오류는 stderr에 쓰고 exit 0 한다.
- 무인 실행 표시 `HWAHAP_UNATTENDED=1`이면 답변과 human.turn을 쓰지 않는다.

### 8.2 gate.sh (Stop)

- `.hwahap/goal.json`이 없으면 exit 0.
- 다음을 순서대로 검사하고, 실패하면 이유를 stderr에 쓰고 Codex의 Stop 차단 규약대로 종료를 막는다. 규약의 정확한 형식은 U1에서 확인한다.
  1. `confirm.goal_sha256`이 현재 `goal.json` 해시와 같다.
  2. 모든 `answer`가 workspace 밖 `answers.jsonl` 사본에 같은 줄로 존재하고 `choice_sha256`이 현재 alternatives 해시와 같다.
  3. `answers.jsonl`의 hash chain이 연속이다.
  4. 모든 unit에 `out/<unit>.patch`, `out/<unit>.test.txt`가 있고 test.txt의 마지막 줄이 `exit 0`이다. skip된 unit은 `out/<unit>.skipped`가 있다.
  5. 각 patch의 변경 경로가 unit `paths` 안이다.
  6. `out/review/<unit>.md` 첫 줄이 `verdict: pass`다.
  7. `out/integration.test.txt` 마지막 줄이 `exit 0`이고 통합 diff의 변경 경로가 모든 unit `paths` 합집합 안이다.
  8. `out/review/integration.md` 첫 줄이 `verdict: pass`다.
  9. `.hwahap/human.turn`의 시각이 `confirm.ts` 이상이다. 사람이 `CONFIRM ALIGN`을 친 세션에서 시작된 build만 인도한다.
  10. 통합 diff에 `secrets.regex`의 패턴이 없다.
- 모두 통과하면 `report.md`와 `summary.json`을 쓰고 `~/.codex/hwahap/<repo-id>/runs/<goal-id>/`에 복사한 뒤 `deliver.sh`를 부른다. deliver 결과를 `summary.json`에 반영한 뒤 §7.5의 판정을 하고, 조건이 맞으면 `improve.sh --auto`를 백그라운드로 띄운다. 그 뒤 exit 0 한다.
- deliver 실패는 종료를 막지 않는다. 사용자가 `report.md`와 `out/deliver.txt`에서 이유를 본다.
- root 토큰은 세션 rollout 파일의 마지막 `token_count.info.total_token_usage`에서 읽는다. 파일을 못 찾으면 보고서에 "측정 불가"로 적고 게이트를 막지 않는다.
- 모든 검사는 단일 조건이다. 검사 하나가 실패하면 그 자리에서 멈춘다.

### 8.3 공통

- 두 hook은 `HWAHAP_DISABLE_HOOKS=1`이면 즉시 exit 0 한다. 오탐이 사용자를 막을 때의 탈출구다.
- hook은 stdout에 아무것도 쓰지 않는다. 진단은 stderr다.
- worker와 proposer 프로세스 안에서도 전역 hook이 실행된다. 그 cwd에는 `.hwahap/goal.json`이 없으므로 두 hook은 즉시 종료한다.

- `deliver.sh`와 `improve.sh`의 git과 gh 호출은 전부 shim으로 테스트한다. 테스트가 실제 remote에 push 하는 일은 없어야 한다.

## 10. 테스트 계획

### 10.1 harness 세 개

1. fixture 테스트. bats로 스크립트 하나씩 실행하고 stdout, stderr, exit code, 생성 파일을 검사한다. fixture는 `tests/fixtures/<script>/<case>/` 아래 입력과 기대 출력이다.
2. 결정적 E2E. `tests/shim/codex`와 `tests/shim/gh`가 PATH 앞에 놓인다. `codex` shim은 인자로 받은 `-o` 경로에 fixture의 마지막 메시지를 쓰고, stdout에 fixture의 JSONL 이벤트를 출력하고, `-C` worktree에 fixture의 파일 변경을 적용한다. `gh` shim은 호출 인자를 기록하고 fixture의 응답을 돌려준다. push는 로컬 bare 저장소를 origin으로 둔다. API 없이 align, build, gate, deliver, improve 전체를 돈다.
3. 실제 모델 smoke. `tests/CHECKLIST.md`의 항목이며 사람이 실행한다. 작은 goal 하나를 v1과 v2로 돌려 `summary.json`을 비교하고 결과를 기록한다.

### 10.2 anomaly

| 상황 | 주입 방법 | 기대 |
|---|---|---|
| worker 비정상 종료 | shim이 exit 2 | attempt 증가, 두 번째 실패 뒤 요약 줄에 fail |
| 잘못된 JSONL | shim이 깨진 줄 출력 | usage 합산 실패를 이유로 exit 1, patch는 보존 |
| 테스트 timeout | test 명령이 exit 124 | test.txt 마지막 줄 `exit 124`, gate 거부 |
| apply 충돌 | 두 unit이 같은 줄 수정 | integrate가 `--check` 단계에서 exit 1, 사용자 질문 |
| 쓰기 불가 | `out/`을 읽기 전용으로 | 첫 쓰기에서 exit 1, 이유 출력 |
| jq 부재 | PATH에서 제거 | doctor exit 1, gate는 종료를 막고 이유 출력 |
| hook 입력 손상 | stdin에 비JSON | prompt.sh exit 0, gate.sh는 이유 출력 뒤 차단 |
| push 거부 | bare origin에 pre-receive hook으로 거부 | `deliver.txt`에 `failed:push`, branch 보존, gate는 종료 허용 |
| gh 인증 실패 | gh shim이 exit 4 | `failed:gh pr create`, branch와 push 보존 |
| branch 또는 PR 중복 | bare origin에 같은 branch 선생성 | `skipped:exists`, commit 없음 |
| 금지 branch | `base_branch`를 `main`으로 두고 goal_id를 `main`으로 | D23 위반으로 exit 1, git 호출 없음 |
| 복합: 재시도 중 budget 초과 | shim usage를 크게 | 두 번째 시도를 시작하지 않고 HW_BUDGET |
| 복합: retry 실패 뒤 skip | fixture 시퀀스 | skipped 파일 생성, 의존 unit 미시작, gate 통과 |
| 복합: 통합 충돌 뒤 abort | fixture 시퀀스 | worktree 보존, report에 abort 기록 |
| 복합: PR 생성 뒤 improve 실패 | proposer shim이 diff 아닌 출력 | 무성과 1회, `improve.state.json` 갱신, PR은 영향 없음 |
| 복합: improve 중 budget 초과 | benchmark shim usage를 크게 | 즉시 종료, worktree 삭제, log에 이유 |

### 10.3 fuzz와 boundary

- `tests/fuzz/goal.sh`가 유효한 `goal.json`에서 jq로 변형을 만든다. 키 삭제, 타입 변경, 중복 id, `..`와 절대 경로, 빈 alternatives, 동일 value, 순환 depends_on, unit 10,000개, 비ASCII 경로, `base_branch`에 금지 이름. 각 변형에 대해 `align-check`가 exit 1과 이유를 내야 한다. 유효한 원본은 exit 0이어야 한다.
- patch fuzz. 바이너리 파일, CRLF, 1 MB 단일 파일, 빈 patch. `integrate.sh`의 동작이 fixture로 고정된다.
- boundary. unit 0개는 align-check 거부, unit 1개 통과, `max_parallel` 1과 4에서 산출물 동일, budget 0은 첫 unit부터 HW_BUDGET, 정확히 80%와 100%. improve는 benchmark 4개와 5개, 7일 경계, 연속 무성과 2회와 3회.

### 10.4 coverage

- Linux CI에서 kcov로 각 스크립트의 branch coverage를 측정한다. 100% 미만이면 실패한다.
- D14에 따라 모든 조건이 단일 조건이므로 branch coverage 100%가 MC/DC 100%와 같다. `tests/lint-conditions.sh`가 `if`와 `[ ]` 안의 `&&`, `||`를 찾아 실패시킨다.

### 10.5 mutation

`tests/mutate.sh`는 스크립트의 각 `if` 조건에 `!`를 붙인 사본을 만들어 fixture 테스트를 돌린다. 한 변형이라도 모든 테스트를 통과하면 실패한다. 의도적으로 제외할 조건은 같은 줄 끝에 `# MUTATION-IGNORE`와 이유를 적는다.

### 10.6 regression

버그가 보고되면 `tests/fixtures/regress/<id>/`를 먼저 만들고 실패를 확인한 뒤 고친다. fixture 없는 수정은 PR에서 거부한다.

### 10.7 자원 누수

모든 bats 파일의 teardown이 `git worktree list --porcelain`의 항목 수, `pgrep -f "codex exec"`의 결과, 임시 bare origin의 branch 수가 테스트 시작 전과 같은지 확인한다. 다르면 실패한다.

### 10.8 실행 환경 변형

- 모든 스크립트는 `set -euo pipefail`로 실행되며 shellcheck 경고가 0이어야 한다.
- `shasum -a 256`만 있는 환경과 `sha256sum`만 있는 환경 양쪽에서 fixture 테스트를 돌린다.
- `max_parallel=1`과 `=4`로 같은 E2E fixture를 돌려 `out/`의 산출물이 usage의 시각 필드를 제외하고 동일한지 비교한다.
- macOS와 ubuntu CI matrix.

### 10.9 checklist

`tests/CHECKLIST.md`는 사람이 릴리스 전에 수행하는 항목이다. 최소 항목: doctor 통과, 실제 모델 smoke, `--ignore-user-config` 범위 재확인, hook 등록 확인, 실제 remote에 대한 deliver 1회와 draft 상태 확인, 자동 improve가 신호 없을 때 토큰을 쓰지 않는지 확인, 이전 버전 run 디렉터리와의 호환 여부, 단가표 갱신일.

## 11. 플랫폼 확인 항목

U1에서 실제로 실행해 결과를 기록한다. 각 항목에는 실패 시 대안이 정해져 있으므로 새 결정이 필요 없다.

1. **sandbox 안 네트워크.** root profile로 세션을 열고 shell에서 `codex exec --ephemeral -m gpt-5.6-luna "print ok"`를 실행한다. 성공하면 D8 그대로다. 실패하면 profile에 `sandbox_workspace_write.network_access = true`가 적용됐는지 확인하고, 그래도 실패하면 root 세션을 `-s danger-full-access`가 아닌 `--add-dir`로 worktree만 열되 `codex exec`를 `approval_policy = "on-request"`로 승인받아 띄운다. 이 경우 unit당 승인 1회가 비용이며 문서에 기록한다.
2. **`--ignore-user-config` 범위.** worker에게 "사용 가능한 MCP 도구 목록과 web_search 가능 여부를 출력하라"고 지시해 결과를 기록한다. MCP가 남아 있으면 `-c mcp_servers.<id>.enabled=false`를 서버마다 추가한다. 전역 `~/.codex/AGENTS.md`가 로드되는지도 기록한다. 로드되면 brief의 commit 금지 문장이 안전장치다.
3. **hook payload 필드.** `prompt.sh`에 stdin 전체를 임시 파일로 저장하는 버전을 넣고 한 번 실행해 프롬프트 텍스트와 세션 식별자 필드명을 기록한다.
4. **Stop hook 차단 규약.** 공식 문서의 Stop hook 출력 형식을 확인하고 `gate.sh`의 차단 출력을 그 형식으로 고정한다. 차단이 불가능한 플랫폼 버전이면 gate.sh는 차단 대신 `report.md` 첫 줄에 `GATE FAILED`를 쓰고 SKILL.md가 root에게 그 줄을 확인하도록 지시한다.
5. **rollout 경로.** 세션 식별자로 `~/.codex/sessions/*/*/*/rollout-*-<id>.jsonl`을 찾아 마지막 `token_count` 줄을 읽을 수 있는지 확인한다. 못 찾으면 root 토큰은 "측정 불가"다.
6. **Stop hook에서의 백그라운드 실행.** `gate.sh`가 `nohup improve.sh &`로 프로세스를 남기고 exit 0 했을 때 Codex가 hook 종료를 기다리지 않고 세션을 닫는지, 남은 프로세스가 살아 있는지 확인한다. 기다리면 hooks.json의 `async` 옵션을 쓰고, 그것도 안 되면 자동 improve 대신 `hwahap improve`를 실행하라는 안내를 `report.md`에 쓴다.
7. **`gh`와 push.** root profile 세션의 shell에서 `gh auth status`와 `git ls-remote origin`이 성공하는지 확인한다. 실패하면 deliver는 hook이 아니라 사용자가 `hwahap deliver`를 직접 실행하는 방식으로 후퇴하고 그 사실을 기록한다.

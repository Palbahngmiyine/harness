# hwahap v2 통합 기획안: align → build → improve

작성일: 2026-09-02. 상태: 기획 확정. 개정 1: build 성공 시 자동 draft PR과 신호 기반 자동 improve (§3.5, D21~D27, §7.4, §7.5). 개정 2: align 단계의 블랙박스 통로 봉쇄와 grilling 장치 추가, build 단계의 토큰 최적화 강화 (§3.6, D28~D48, §7.2, §7.3). 이 문서는 Codex가 그대로 구현할 수 있도록 모든 결정을 고정했다. 구현자는 §9의 실행 단위를 순서대로 진행하고, §11의 확인 항목 외에는 새 결정을 만들지 않는다. 새 결정이 필요해지면 구현을 멈추고 사용자에게 묻는다.

## 0. 이 문서를 읽는 방법

- §1 결론과 §4 고정 결정만 읽어도 무엇을 만드는지 알 수 있다.
- §5 파일 구성, §6 데이터 형식, §7 단계별 프로토콜, §8 hook 계약은 구현 명세다.
- §9 실행 단위는 Codex가 따라야 할 작업 순서다. 각 단위는 200줄 이내의 변경, 테스트, 수용 기준을 가진다.
- §10 테스트 계획은 SQLite의 테스트 관행을 이 프로젝트 규모에 맞게 옮긴 것이다. 구현 코드는 단순하게, 테스트는 엄격하게 한다.
- §3 4원칙 검수는 이 설계가 원칙을 어디서 충족하고 어디서 조건부인지 기록한다.

용어는 §2에서 한 번만 정의한다. 문서 안에서 비유는 쓰지 않는다.

## 1. 결론

hwahap v2는 하나의 스킬이며 세 단계로 운영된다.

1. `align`: 사용자와 구현 방향을 확정해 `goal.json` 하나를 만든다. 모든 결정은 사용자가 채팅에 친 답으로만 확정되고 hook이 그 답을 기록한다. 해당 없음 판정, 4 round마다의 checkpoint, 최종 확인까지 전부 같은 방식이다. 사실 조회는 읽기 전용 worker가 하고, 모르는 답은 `UNKNOWN`으로 남겨 조사나 시제품으로 풀며, 구현 중 새 결정이 필요하면 worker가 멈추고 align으로 돌아온다. 이것이 "사람이 모르는 기획 0"을 구조로 보장하는 범위다.
2. `build`: `goal.json`의 unit을 worktree에서 병렬로 구현하고 기계 검증과 의미 검토를 거친다. 한 번 통과한 unit은 입력이 바뀌지 않는 한 다시 실행하지 않는다. 모든 gate를 통과하면 생성 branch에 commit 하고 draft PR을 자동으로 연다.
3. `improve`: 과거 실행 기록을 benchmark로 삼아 하네스 설정 변경을 측정 뒤 채택하거나 되돌린다. build가 끝난 뒤 개선 신호가 있을 때만 자동으로 시작하며, 결과는 harness 저장소의 draft PR이다.

없애는 것은 다음과 같다. Python 코드 전부, Codex Goal 도구 연동, `.codex/agents` 프로필과 installer, 세션 subagent 스폰, `.hwahap` 상태 기계와 영수증 명령, HTML 보고서, Ultra 최종 검토, Luna verifier, Sol planner, grill-prfaq. 남는 코드는 shell 스크립트 8개와 jq 프로그램 4개 이하이며 각 파일은 80줄 이하다.

기존 PR #4, #5, #6은 2026-09-02에 닫았다. v1 스킬은 §9 U10까지 저장소에 그대로 둔다.

## 2. 용어

| 용어 | 정의 |
|---|---|
| root | 사용자가 연 대화형 세션. align은 `--profile hwahap-align`(Sol high), build는 `--profile hwahap`(Sol medium)으로 연다. |
| worker | root의 shell에서 `codex exec`로 띄우는 비대화형 프로세스. unit 하나를 구현한다. Luna 모델. |
| reviewer | `codex exec`로 띄우는 읽기 전용 프로세스. unit 또는 통합 결과의 의미를 검토한다. Terra 모델. |
| fact worker | `codex exec`로 띄우는 읽기 전용 프로세스. align 중 저장소나 환경의 사실 하나를 조회한다. Luna 모델. |
| proposer | improve 단계에서 `codex exec`로 띄우는 읽기 전용 프로세스. 하네스 설정 변경 하나를 patch로 제안한다. Sol 모델. |
| surface | 결정 표면. §7.2의 12개 영역. 각 표면은 결정으로 닫히거나 사용자가 해당 없음을 확정한다. |
| choice | 사용자가 답해야 확정되는 질문. 대안 2개 이상과 추천을 가진다. |
| frontier | 선행 choice가 모두 답변되어 지금 물을 수 있는 choice의 집합. |
| round | frontier 전체를 한 번에 묻고 답을 받는 단위. |
| scenario question | "이 상황에서 무엇이 일어나야 하는가"를 묻는 choice. `kind`가 `scenario`다. |
| checkpoint | 4 round마다 추천과 같은 답만 고른 choice를 다시 확인하는 절차. |
| fact | fact worker가 조회해 파일로 남긴 관찰. choice의 `evidence`가 참조한다. |
| term | 용어 정의. 사용자 발화와 코드의 용어가 충돌할 때 choice로 확정한다. |
| probe | 사용자가 반응해야 답할 수 있는 choice를 위해 만드는 시제품 unit. 인도하지 않는다. |
| unit | 독립적으로 테스트할 수 있는 최소 변경. `paths`, `test`, `depends_on`을 가진다. |
| worktree | `git worktree add --detach`로 만든 checkout. unit마다 하나, 통합용 하나. |
| patch | unit worktree의 `git diff HEAD` 출력. unit의 유일한 산출물이자 증거. |
| brief | worker, reviewer, fact worker, proposer에게 넘기는 지시문. 스크립트가 생성한다. |
| cached unit | brief 해시가 같고 이미 통과한 unit. 다시 실행하지 않는다. |
| NEEDS_DECISION | worker가 스스로 정할 수 없는 결정을 만났을 때 마지막 메시지 첫 줄에 쓰는 표시. |
| revision | `goal.json`의 개정 번호. 구현 중 새 choice가 생기면 1 오른다. |
| gate | 다음 단계로 넘어가도 되는지를 판정하는 결정적 검사. 스크립트가 수행하며 모델의 주장을 입력으로 쓰지 않는다. |
| deliver | gate 통과 뒤 통합 결과를 생성 branch에 commit 하고 push 한 뒤 draft PR을 여는 절차. |
| base branch | align 시작 시 사용자 checkout의 branch. deliver의 PR base다. |
| draft PR | GitHub의 draft 상태 PR. 사람이 ready로 바꾸기 전에는 merge 대상이 아니다. |
| hook | Codex가 정해진 이벤트에 실행하는 외부 명령. sandbox 밖에서 실행된다. |
| budget | 한 run에서 worker, reviewer, fact worker가 쓸 수 있는 토큰 총량. improve는 별도 budget을 가진다. |
| benchmark | 과거 run의 `goal.json`과 `summary.json` 묶음. improve 단계의 측정 대상. |
| ruler | benchmark 위에서 계산하는 지표. 통과 unit당 비용과 첫 시도 gate 통과율. |
| noise band | 같은 설정으로 반복 실행했을 때 ruler가 흔들리는 폭. `max(2σ, floor)`. |
| canary | 결과를 아는 변경. ruler가 그 변경을 noise band 밖에서 감지해야 측정을 신뢰한다. |
| signal | 방금 끝난 run에서 improve를 시작할 근거. §7.5에 정의한다. |
| diary | root가 실행 중 적는 관찰 기록. Interpretations, Deviations, Tradeoffs, Open questions 네 제목. |
| lesson | 다음 run의 규칙 후보. 사용자가 확인해야만 규칙이 된다. |

## 3. 4원칙 검수

### 3.1 단순함 (KISS)

기준: 구현체는 요구를 만족하는 가장 단순한 설계를 고르고, 요구가 아닌 것을 위한 복잡성을 두지 않는다. `general/CLAUDE.md`의 규칙이다.

| 항목 | v1 | v2 |
|---|---|---|
| 언어 | Python 6,131줄, 245파일 | shell 8개, jq 4개 이하. 각 80줄 이하 |
| 역할 | 6개 프로필 설치 | 3개 실행 역할. root, worker, reviewer. fact worker와 proposer는 reviewer와 같은 실행 방식이다. 설치 없음 |
| 상태 | contract, run, events, units, report 5종 | `goal.json`과 `out/` 산출물 파일 |
| 플랫폼 결합 | Goal 도구, subagent, 프로필 | `codex exec`, `gh`, 파일. 플랫폼 기능이 바뀌어도 영향 없음 |
| 문서 | 1,706줄 | SKILL.md 80줄 이하와 참조 문서 `SURFACES.md` 40줄 이하 |

판정: 충족. 조건은 §4 D12의 줄 수 상한과 D13의 방어 코드 금지를 지키는 것이다. shell은 조건이 늘면 빠르게 복잡해지므로, `if`에 복합 조건을 쓰지 않고 한 스크립트가 한 결정만 내리게 한다.

### 3.2 엄격함 (SQLite 방식 테스트)

기준: https://www.sqlite.org/testing.html 의 관행이다. 독립 harness 여러 개, 100% branch와 MC/DC coverage, anomaly 테스트(OOM, I/O 오류, crash, 복합 실패), fuzz, boundary, 모든 버그의 regression 테스트, 자동 자원 누수 검출, mutation 검사, undefined behavior 검사, 최적화 끄고 재실행, 사람이 수행하는 checklist, 정적 분석. SQLite는 라이브러리 코드의 590배 테스트 코드를 가진다.

| SQLite 관행 | v2 대응 | 상태 |
|---|---|---|
| 독립 harness 여러 개 | (1) bats fixture 테스트, (2) `codex`와 `gh` shim으로 API 없이 도는 결정적 E2E, (3) 실제 모델로 도는 수동 smoke | §10.1 |
| 100% branch coverage | kcov로 shell 분기 측정, CI에서 100% 미만이면 실패 | §10.4 |
| MC/DC | 도구가 없으므로 구조로 보장. `if`에 단일 조건만 허용하면 branch coverage가 MC/DC와 같아진다 | §4 D14, §10.4 |
| mutation 검사 | `tests/mutate.sh`가 각 `if`의 조건을 뒤집고 테스트가 실패하는지 확인 | §10.5 |
| anomaly: OOM, I/O 오류, crash | worker 비정상 종료, 잘못된 JSONL, 테스트 timeout, `git apply` 충돌, 쓰기 불가 디렉터리, jq 부재, hook 입력 손상, push 거부, `gh` 실패, NEEDS_DECISION 손상 | §10.2 |
| 복합 실패 | 재시도 중 budget 초과, retry 실패 뒤 skip, 통합 중 충돌 뒤 abort, PR 생성 뒤 improve 실패, revision 중 cached unit 무효화 | §10.2 |
| fuzz | jq로 `goal.json`과 답변 문법을 변형해 gate가 거부하는지 검사. patch 파일 fuzz | §10.3 |
| boundary | unit 0개, 1개, `max_parallel` 1과 N, budget 0, 정확히 50%, 80%, 100%, round 4의 배수 | §10.3 |
| regression | 버그마다 `regress-<id>` fixture. fixture 없이 버그를 닫지 않는다 | §10.6 |
| 자원 누수 검출 | 모든 테스트 끝에 남은 worktree, codex 프로세스, 임시 branch가 0인지 검사 | §10.7 |
| undefined behavior 검사 | `bash -u -e -o pipefail`과 shellcheck. `shasum`과 `sha256sum` 양쪽 환경 | §10.8 |
| 최적화 끄고 재실행 | `max_parallel=1`과 `=N`의 산출물이 동일한지, cached skip을 끄고 켠 결과가 동일한지 비교 | §10.8 |
| checklist | `hwahap doctor`와 `tests/CHECKLIST.md`. 사람이 수행 | §10.9 |
| 정적 분석 | shellcheck 경고 0, 모든 jq 프로그램 파싱 검사 | §10.8 |

판정: 조건부 충족. 조건은 §10을 §9의 U8로 실제 구현하는 것과, 테스트 코드가 스크립트 코드의 3배 이상이 되는 것이다. 구현 코드를 줄이려고 테스트를 줄이지 않는다.

### 3.3 최적화 (Uber Efficient Software Factory)

기준: https://www.uber.com/us/en/blog/efficient-software-factory/. 비용은 `Users × Sessions/User × Turns/Session × Requests/Turn × Tokens/Request × Price/Token`이며 가운데 세 항을 줄인다. 서브에이전트는 약한 모델과 낮은 effort를 기본으로 한다. MCP 스키마를 컨텍스트에서 제거한다. 하위 프로세스 안에서 반복하고 요약만 돌려받는다. 비용은 결과 단위로 잰다. 새 agent마다 outcome metric, benchmark, Pareto 모델 순서로 정한다.

| Uber 항목 | v2 대응 |
|---|---|
| Turns/Session | build root의 턴은 unit 묶음당 두 번. 스크립트가 worker 실행과 기록을 맡는다. root가 읽을 수 있는 파일은 D44의 목록뿐이다 |
| Requests/Turn | worker는 `codex exec` 하위 프로세스. root에는 마지막 메시지 파일만 돌아온다. 통과한 unit은 다시 실행하지 않는다(D37) |
| Tokens/Request | worker는 `--ignore-user-config`, `web_search=disabled`, `model_verbosity=low`, `model_reasoning_summary=none`, `tool_output_token_limit=4000`으로 시작. brief에는 그 unit의 spec과 acceptance만 들어간다 |
| 약한 모델 기본 | worker Luna high, reviewer Terra high, fact worker Luna medium. root는 build에서 Sol medium, align에서만 Sol high |
| 캐시 | 한 batch의 worker를 동시에 띄워 고정 머리말의 cache write를 한 번만 내고 나머지는 hit(0.1배)로 받는다. effort는 run 중 바꾸지 않는다 |
| 비용 표시와 nudge | budget 50%에서 알림, 80%에서 경고, 100%에서 새 unit 중단 뒤 사용자에게 질문. hard cap 없음 |
| 결과 단위 비용 | `summary.json`에 통과 unit당 비용, 첫 시도 통과율, 소요 시간, unit별 cache hit 비율과 reasoning 비율 |
| benchmark 우선 | improve 단계는 benchmark 없이는 설정을 바꾸지 않는다 |
| managed agent는 별도 tier | 자동 improve는 사람 세션과 분리된 자체 budget을 가지며 그 budget은 hard cap이다 |
| anti-pattern | 시스템 지시 선적재는 SKILL.md 80줄로, MCP 잔류는 worker 격리로, 캐시 만료는 effort 고정과 batch 동시 실행으로, 잘못된 routing은 역할별 모델로 막는다. cache hit 비율이 낮은 run은 improve의 신호가 된다 |

근거 자료: 2026-08-30 PR #5 세션 rollout의 마지막 `token_count`는 total 381,088,447, cached 376,223,744였다. 한 세션이 3억 8천만 토큰을 썼고 대부분이 매 턴 다시 보낸 컨텍스트였다. v2는 root 컨텍스트에 worker 대화가 들어오지 않게 하는 것으로 이 구조를 끊는다.

판정: 충족. 다만 측정 없이는 최적화를 주장할 수 없으므로 §10.1의 실제 모델 smoke에서 v1과 같은 goal을 돌려 `summary.json`을 비교하는 것을 U9 수용 기준에 넣는다.

### 3.4 재귀적 개선 (KiroCrew auto-improvement)

기준: https://github.com/kirodotdev/KiroCrew 의 `auto_improvement` 앱. 측정 시스템이 먼저다. ruler를 보정하고 canary로 증명한 뒤에만 변경한다. agent는 제안만 하고 결정은 결정적 코드가 한다. 후보는 worktree마다 격리한다. edit allowlist를 측정 전에 검사한다. keep-or-revert. 비용 상한과 quiescence 정지. 산출물은 draft PR뿐이다. 학습은 검토를 통과해 배포된 결함처럼 허용된 출처에서만 하고, 일반화하며, staging 뒤 사람이 consolidation을 트리거한다.

| KiroCrew 항목 | v2 대응 |
|---|---|
| 측정 먼저 | benchmark 5개 이상, 같은 goal 3회 반복으로 noise band, canary 통과 전에는 변경 없음 |
| 제안은 agent, 결정은 코드 | proposer가 설정 변경 하나를 patch로 제안. `improve.sh`가 benchmark 재실행 결과로 keep/revert |
| 후보 격리 | harness 저장소의 worktree에서 제안 |
| edit allowlist | 바꿀 수 있는 것은 `skills/hwahap/` 안의 effort, 모델, brief 문안, `max_parallel`, `tool_output_token_limit`뿐 |
| 정지 | improve 자체 budget, 3 cycle 무성과 정지, 무성과 3회 뒤 자동 improve 비활성화 |
| draft PR | keep된 변경은 harness 저장소의 생성 branch에 commit 하고 draft PR로 연다. merge와 ready 전환은 사람이 한다 |
| 허용 출처 | gate 실패, 사용자 수정, 사용자가 되돌린 patch. reviewer 자신의 의견은 출처가 아니다 |
| staging | `lessons.candidates.md`에 쌓고 사용자가 AGENTS.md나 SKILL.md에 옮긴다 |

판정: 조건부 충족. 조건은 benchmark 실행이 실제 토큰을 쓰므로 자동 improve를 신호와 budget으로 묶는 것이다 (§3.5). 자동 학습 수집은 두지 않는다. 사용자가 2026-08-18에 recursive-learning 자동화를 걷어내고 의도적 작업 기반 루프로 바꾼 결정을 따른다.

### 3.5 자동 인도와 자동 improve 검수

사용자 제안: build가 끝나고 LLM 차원의 문제가 없으면 PR을 자동으로 올리고, 이어서 improve를 자동으로 진행한다.

| 원칙 | 판정 | 조건 |
|---|---|---|
| 단순함 | 충족 | 새 hook 없이 `gate.sh`가 통과 뒤 `deliver.sh`를 부르고 `improve.sh`를 백그라운드로 띄운다 |
| 엄격함 | 조건부 충족 | `gh`와 push 실패, 중복 PR, protected branch, improve 비동기 실패가 fixture로 고정돼야 한다. §10.2에 있다 |
| 최적화 | 조건부 충족 | 무조건 자동 improve는 신호 없이 토큰을 쓰므로 Uber의 "zero-value token 제거" 원칙에 어긋난다. 신호가 있을 때만, 주 1회 이하, 별도 hard budget으로 돌리면 충족한다 |
| 재귀적 개선 | 조건부 충족 | KiroCrew의 안전 모델을 그대로 가져와야 한다. 생성 branch, draft PR만, protected branch 금지, ruler 미증명 시 정지, quiescence 뒤 자동 비활성화 |

결론: 제안은 4원칙에 위배되지 않으며 위 조건을 D21~D27로 고정해 반영했다. 사람의 검토 지점은 `CONFIRM BUILD`에서 draft PR 검토로 옮겨진다. 무인 실행(`HWAHAP_UNATTENDED=1`)에서는 자동 인도를 하지 않는다.

### 3.6 개정 2 검수: 블랙박스 봉쇄와 build 최적화

근거 자료: https://github.com/mattpocock/skills 의 `skills/productivity/grilling/SKILL.md`, `docs/productivity/grill-me.md`, `docs/productivity/grilling.md`, `.out-of-scope/question-limits.md`, `skills/engineering/domain-modeling/SKILL.md`, `skills/engineering/to-spec/SKILL.md`. 핵심 문장은 다음이다. "Finding facts is your job, never the user's." "An agent running grilling that answers its own decisions has broken the skill." "The session is done when the frontier is empty: every branch of the design tree visited, nothing left silently assumed." "Some plans need three questions and some need fifty." "'I don't know' is a real answer, and a question you can't answer is usually a sign to prototype rather than to guess."

개정 1까지의 align에는 사람이 모르는 결정이 남는 통로가 두 개 있었다. 첫째, 해당 없음 판정을 root가 이유만 적고 끝냈다. 둘째, 확인 전에 보여주는 요약이 `goal.json`과 같다는 보장이 없었다. 개정 2는 둘 다 사용자의 답과 결정적 렌더링으로 닫는다 (D28, D29). 그리고 grilling이 실제로 집요함을 만드는 장치 여섯 개를 넣었다. 사실 조회 위임 (D30), 답에서 파생되는 choice의 재계산 (D31), `UNKNOWN` 답과 probe (D32), 범위 분할 규칙 (D33), 용어와 시나리오와 코드 대조 (D34), align 전용 세션과 모델 (D35). 구현 중 새 결정이 생기면 worker가 추측하지 않고 멈추는 규칙 (D36)이 build 쪽의 마지막 통로를 닫는다.

| 원칙 | 판정 | 근거 |
|---|---|---|
| 단순함 | 충족 | 새 스크립트는 없다. fact worker는 `review.sh`의 모드 하나, 렌더링은 jq 프로그램 하나, 답변 문법은 세 형태가 늘었다. build의 cached unit은 조건 하나다 |
| 엄격함 | 조건부 충족 | 새 gate 검사 7개(§8.2의 2b, 2c, 2d, 4b, 11, 12, 13)마다 실패 fixture, 렌더링 결정성 테스트, cached unit의 zero-call 테스트, 답변 문법 fuzz가 U8에 들어간다 |
| 최적화 | 충족 | 사실 조회를 Luna medium에 위임해 Sol high인 align root의 턴이 줄고, cached unit과 batch 동시 실행으로 build의 zero-value 토큰이 사라진다. 렌더링은 토큰을 쓰지 않는다 |
| 재귀적 개선 | 충족 | `UNKNOWN`과 probe는 KiroCrew의 "측정 먼저"와 같은 태도다. 답을 만들지 않고 관찰을 만든다. cache hit 비율이 improve의 신호로 들어간다 |

남는 한계는 셋이다. frontier는 root의 판단이라 두 질문을 한 round에 넣었다가 뒤늦게 의존성을 발견할 수 있다. 사용자가 `C1=ALT1`을 기계적으로 반복하는 수동성은 checkpoint가 한 번 더 걸러줄 뿐 막지 못한다. worker가 `NEEDS_DECISION`을 쓰지 않고 추측하는 것은 reviewer가 계약 이탈로 잡는 것 외에 막을 방법이 없다. 세 한계는 §7.2와 §7.3에 그대로 적는다.

## 4. 고정 결정

- D1. Python을 쓰지 않는다. 언어는 POSIX shell(bash 3.2 이상 호환), jq, git이다.
- D2. Codex Goal 도구(`get_goal`, `create_goal`, `update_goal`)를 호출하지 않는다.
- D3. `.codex/agents` 프로필을 만들거나 설치하지 않는다. worker와 reviewer는 `codex exec`의 `-m`, `-c` 플래그로 정의한다.
- D4. worker, reviewer, fact worker, proposer는 root 세션의 shell에서 띄우는 `codex exec` 하위 프로세스다. 세션 subagent 도구는 쓰지 않는다.
- D5. build 중에는 `git commit`, `git add`, `git stash`를 실행하지 않는다. 허용하는 git 명령은 `worktree add/remove/list`, `diff`, `apply`, `hash-object`, `rev-parse`, `status`, `ls-files`다. commit, push, branch 생성은 `deliver.sh`와 `improve.sh`의 인도 절차에서만, 생성 branch에 대해서만 실행한다.
- D6. worktree는 대상 저장소의 `.hwahap/wt/<unit>`과 `.hwahap/wt/integration`에 만든다. `.hwahap/`은 gitignore 대상이며 없으면 `hwahap doctor`가 실패한다.
- D7. 모델과 effort의 기본값은 align root Sol high, build root Sol medium, worker Luna high, reviewer Terra high, fact worker Luna medium, proposer Sol medium이다. `goal.json`의 unit 항목에서 `model`과 `effort`를 override할 수 있다. Ultra는 쓰지 않는다.
- D8. root 세션은 두 profile 중 하나로 연다. `~/.codex/hwahap-align.config.toml`은 `model_reasoning_effort = "high"`, `~/.codex/hwahap.config.toml`은 `model_reasoning_effort = "medium"`이며, 둘 다 `service_tier` 미설정, `sandbox_workspace_write.network_access = true`, `tool_output_token_limit = 4000`이다. align과 build는 서로 다른 세션이다.
- D9. hook은 `~/.codex/hooks.json`에 한 번 등록한다. 등록되는 것은 `UserPromptSubmit`의 `prompt.sh`와 `Stop`의 `gate.sh` 둘뿐이다. 두 스크립트는 현재 디렉터리에 `.hwahap/goal.json`이 없으면 아무것도 하지 않고 exit 0 한다.
- D10. 상태 파일은 `goal.json`과 `out/`, `facts/` 산출물뿐이다. 이벤트 로그, 상태 기계, 영수증 명령은 없다. 현재 상태는 산출물 파일의 존재와 내용에서 계산한다.
- D11. 사용자 답변은 `prompt.sh`가 기록한다. 모델은 답변 파일을 쓰지 않는다. gate는 workspace 밖 사본과 대조한다.
- D12. shell 스크립트 하나는 80줄 이하, jq 프로그램 하나는 80줄 이하, SKILL.md는 80줄 이하, `SURFACES.md`는 40줄 이하다. shell 스크립트는 8개, jq 프로그램은 4개를 넘지 않는다. 테스트와 fixture는 상한이 없다.
- D13. 방어 코드를 두지 않는다. 입력이 잘못되면 첫 검사에서 이유를 출력하고 exit 1 한다. 같은 조건을 두 번 검사하지 않는다.
- D14. `if`와 `[ ]`에 `&&`, `||`로 묶인 복합 조건을 쓰지 않는다. 조건 하나가 결정 하나다.
- D15. 시간에 의존하는 테스트를 두지 않는다. `sleep`으로 순서를 맞추지 않는다. 시각은 `HWAHAP_NOW` 환경변수로 주입할 수 있다.
- D16. 보고서는 markdown 하나이며 순서는 결론, 근거, 확인 과정, 한계, 비용이다. HTML은 만들지 않는다.
- D17. budget은 worker, reviewer, fact worker 토큰의 합에만 적용한다. root 토큰은 따로 측정해 보고한다.
- D18. unit당 worker 시도는 2회, reviewer 라운드는 2회가 상한이다. 초과하면 사용자에게 retry, skip, abort를 묻는다.
- D19. 문서-only 요청, 질문, 아이디어 탐색에는 hwahap을 쓰지 않는다. SKILL.md의 첫 규칙이다.
- D20. 대상 플랫폼은 Codex CLI 0.151 이상이다. Claude Code 어댑터는 범위 밖이다.
- D21. `CONFIRM ALIGN` 뒤 build는 자율로 진행한다. 사람에게 묻는 경우는 D18의 실패, budget 100%, 통합 충돌, D36의 NEEDS_DECISION뿐이다. `CONFIRM BUILD`는 없다.
- D22. gate 통과 시 `deliver.sh`가 통합 결과를 `hwahap/<goal_id>` branch에 commit 하고 push 한 뒤 `gh pr create --draft`로 PR을 연다. base는 `goal.json`의 `base_branch`다. PR 본문은 `report.md`다.
- D23. head branch는 항상 `hwahap/` 또는 `hwahap-improve/` 접두사를 가진다. `main`, `master`, `develop`, `release/*`, 그리고 `base_branch` 자체에는 push 하지 않는다. 이 목록은 스크립트 상수이며 설정으로 넓힐 수 없다.
- D24. 하네스는 PR을 ready로 바꾸거나 merge 하거나 auto-merge를 켜지 않는다. 같은 이름의 branch나 열린 PR이 이미 있으면 새 것을 만들지 않고 사용자에게 묻는다.
- D25. `HWAHAP_UNATTENDED=1`이면 gate는 판정만 하고 인도하지 않는다.
- D26. 자동 improve는 §7.5의 신호가 있고, 마지막 자동 improve로부터 7일이 지났고, benchmark가 5개 이상이고, `~/.codex/hwahap/config.json`에 `improve.auto = true`와 `improve.budget_tokens`가 있을 때만 시작한다. budget은 hard cap이다. 신호가 없으면 `summary.json`에 이유를 적고 토큰을 쓰지 않는다.
- D27. 자동 improve가 3회 연속 무성과이면 `improve.auto`를 `false`로 바꾸고 이유를 기록한다. 다시 켜는 것은 사용자다. 수동 `hwahap improve`는 이 제한을 받지 않는다.
- D28. 표면의 해당 없음 판정은 사용자만 확정한다. root는 이유를 적은 뒤 `S<n>` 질문으로 내고, 사용자가 `S<n>=NA`를 쳐서 hook이 기록해야 해당 없음이 된다. 답이 없는 표면은 gate가 미완료로 본다.
- D29. `CONFIRM ALIGN` 직전에 `hwahap render`가 `goal.json`을 jq로 `align.md`에 결정적으로 펼친다. `prompt.sh`는 `CONFIRM ALIGN`에 `goal_sha256`과 `render_sha256`을 함께 stamp 하고, gate는 다시 렌더링한 결과의 해시와 대조한다. root가 손으로 쓴 요약은 확인 대상이 아니다.
- D30. 사실은 사용자에게 묻지 않는다. 저장소, 실행 환경, 문서에서 알 수 있는 것은 `hwahap fact "<질문>"`으로 fact worker에게 맡기고, 결과 파일 `facts/F<n>.md`를 choice의 `evidence`에서 `F<n>`으로 인용한다. root는 fact worker를 기다리지 않고 그 사실에 의존하지 않는 질문을 먼저 낸다.
- D31. round가 끝나면 root는 답에서 파생되는 새 choice를 `choices`에 추가하고 `derived_from`에 출처 답을 적는다. frontier가 비었다고 선언하려면 마지막 round에서 새 choice가 0개였고, 모든 applicable 표면에 답변된 choice와 답변된 scenario question이 하나 이상 있어야 한다. round 수 상한은 없다.
- D32. 사용자는 `C<n>=UNKNOWN`으로 답할 수 있다. root는 그 choice를 open item으로 바꾸고 둘 중 하나를 제안한다. 사실로 풀리면 D30의 fact worker, 반응이 필요하면 `probe: true` unit이다. probe unit은 build의 worker와 같은 방식으로 실행되지만 통합과 인도에서 제외되며, 결과를 본 뒤 같은 choice를 다시 묻는다. open item이 남아 있으면 `CONFIRM ALIGN`을 받을 수 없다.
- D33. applicable choice가 40개를 넘거나 round가 6을 넘으면 root는 goal 분할을 제안한다. 분할된 각 goal은 별도 `goal_id`와 별도 run이다. 사용자가 분할을 거부하면 계속 진행하고 그 사실을 diary에 적는다.
- D34. 용어, 시나리오, 코드 대조의 세 규칙을 SKILL.md에 둔다. 사용자 발화의 용어가 코드나 앞선 발화와 다르게 쓰이면 canonical 용어를 제안하는 `kind: term` choice로 확정하고 `terms[]`에 기록한다. applicable 표면마다 "이 상황에서 무엇이 일어나야 하는가"를 묻는 `kind: scenario` choice를 하나 이상 낸다. 사용자 진술이 코드의 현재 동작과 다르면 fact로 기록하고 그 자리에서 choice로 낸다.
- D35. align은 `--profile hwahap-align`의 새 세션에서 돌린다. build 세션은 `goal.json`만 읽고 시작하며 align 대화를 이어받지 않는다. align 세션에서 plan 모드를 쓰지 않는다.
- D36. worker가 스스로 정할 수 있는 것은 관찰 가능한 동작, 테스트 결과, 이름 붙은 식별자, 파일 간 심볼, 경로, 포맷, 스키마, 저장 필드, 의존성, 동시성, 보안, 성능, 호환성에 영향이 없고 한 unit 안에서 되돌릴 수 있는 것뿐이다. 그 밖의 결정을 만나면 worker는 코드를 바꾸지 않고 마지막 메시지 첫 줄에 `NEEDS_DECISION: <질문>`을 쓰고 끝낸다. `unit.sh`는 이것을 실패가 아닌 별도 결과로 기록하고 재시도하지 않는다. root는 그 질문을 새 choice로 align 세션에 넘긴다. build는 인도하지 않는다.
- D37. 통과한 unit은 입력이 바뀌지 않는 한 다시 실행하지 않는다. `unit.sh`는 brief의 sha256을 `out/<unit>.brief.sha256`에 남기고, patch, 통과한 test.txt, `verdict: pass`, 같은 brief 해시가 모두 있으면 `cached`를 출력하고 codex를 호출하지 않는다. revision으로 spec이 바뀐 unit만 brief 해시가 달라져 다시 실행된다.
- D38. worker는 `-c model_verbosity=low -c model_reasoning_summary=none -c web_search=disabled`로 띄운다. 마지막 메시지는 변경 요약 한 문단이거나 `NEEDS_DECISION` 한 줄이다.
- D39. worker brief에는 그 unit의 `paths`, `test`, 연결된 spec과 acceptance, 관련 term만 들어간다. `goal.json` 전문과 다른 unit의 내용은 넣지 않는다. AGENTS.md는 경로만 적는다.
- D40. reviewer brief에는 patch 전문과 그 unit의 spec, acceptance, term만 들어간다. reviewer는 저장소를 탐색하지 않고 patch를 읽는다. 저장소 확인이 필요하면 `paths` 안의 파일만 연다.
- D41. unit별 테스트는 그 unit의 `test`만 실행한다. `full_suite`는 통합 뒤 한 번 실행한다. probe unit은 `full_suite`를 실행하지 않는다.
- D42. 한 batch의 worker는 같은 명령으로 동시에 시작한다. brief 머리말이 같으므로 첫 worker가 cache를 쓰고 나머지는 hit로 받는다. batch 사이에 5분 이상 비면 머리말 cache가 만료되므로 batch를 쪼개지 않는다.
- D43. budget 알림은 50%, 80%, 100%다. 50%는 요약 줄에 `budget 50%`를 붙이고, 80%는 `out/budget.warn`을 쓰고, 100%는 새 unit을 시작하지 않는다.
- D44. build root가 읽을 수 있는 파일은 `hwahap unit`, `hwahap review`, `hwahap integrate`의 요약 줄, `out/review/*.md`의 첫 줄, `out/*.needs_decision`, `report.md`뿐이다. `out/*.events.jsonl`, `out/*.patch`, `out/*.last.md`는 읽지 않는다. SKILL.md가 이 목록을 명시한다.
- D45. `summary.json`은 unit마다 `cache_hit_ratio`(cached_input / input)와 `reasoning_ratio`(reasoning_output / output)를 기록한다. run 전체 cache hit 비율이 0.5 미만이면 improve의 `cache_miss` 신호다.
- D46. probe unit의 산출물은 `out/<unit>.patch`로 남기되 `deliver.sh`와 `integrate.sh`는 `probe: true` unit을 건너뛴다. probe의 토큰은 align 비용으로 집계한다.
- D47. revision이 오르면 새 `CONFIRM ALIGN`이 필요하다. 이전 답변과 stamp는 그대로 유효하다. `confirm.revision`이 `goal.json`의 `revision`과 같아야 gate가 통과한다.
- D48. 답변 문법은 `C<n>=<ALT id>`, `C<n>=OTHER: <값>`, `C<n>=UNKNOWN`, `S<n>=NA`, `CP<k>=OK`, `CONFIRM ALIGN` 여섯 가지뿐이다. `ok`, `추천대로`, `전부 동의` 같은 문장은 기록되지 않으며 root는 같은 질문을 다시 낸다.

규칙은 `check.jq`가 검사한다.

- `base_branch`는 align 시작 시 `git rev-parse --abbrev-ref HEAD`다. detached면 `gh repo view --json defaultBranchRef`의 값이다.
- `surfaces`의 키는 `SURFACES.md`의 12개 ID다. 모든 표면은 `applicable`에 있거나 `not_applicable`에 이유와 stamp 된 `S<n>=NA` 답과 함께 있어야 한다.
- `applicable` 표면마다 `kind: decision` choice와 `kind: scenario` choice가 각각 하나 이상 있고 모두 답변돼야 한다.
- `alternatives`는 2개 이상이고 `value`는 서로 달라야 한다.
- `answer.text`는 D48의 문법이다. `OTHER:`이면 그 값을 가진 alternative를 `origin: "user"`로 추가한다. `UNKNOWN`이면 `open_items`에 같은 `choice_id`의 항목이 있어야 한다.
- `answer.choice_sha256`은 `{id, question, alternatives}`를 `jq -S -c`로 직렬화한 바이트의 sha256이다. `prompt.sh`가 계산한다. 답변 뒤 alternatives를 바꾸면 이 값이 달라져 gate가 거부한다.
- `evidence`의 `F<n>`은 `facts[]`에 있어야 하고 그 `path`의 sha256이 기록값과 같아야 한다.
- 답변된 choice는 정확히 하나의 round에 속한다. `derived_from`의 choice는 더 이른 round에 속해야 한다. `n`이 4의 배수인 round는 stamp 된 `CP<k>=OK` checkpoint를 가져야 하고, 그 밖의 round는 `checkpoint`가 null이어야 한다. 마지막 round의 `new_choice_ids`는 비어야 한다.
- `terms[]`의 `choice_id`는 `kind: term` choice여야 하고 답변돼야 한다.
- `review.cold.goal_sha256`과 `confirm.goal_sha256`은 `goal.json`에서 `review`와 `confirm`을 뺀 문서의 `jq -S -c` sha256이다. `confirm.render_sha256`은 `render.jq` 출력의 sha256이다. `confirm.revision`은 `revision`과 같아야 한다.
- 모든 `spec`은 하나 이상의 `acceptance`에, 모든 `acceptance`는 하나 이상의 `probe: false` unit에 속해야 한다.
- `units[].test`는 비어 있을 수 없다. `paths`는 저장소 상대 경로이며 `..`, 절대 경로, `.hwahap/`을 포함할 수 없다.
- `depends_on`은 DAG여야 한다. probe unit은 다른 unit의 `depends_on`에 나올 수 없다.
- `open_items`에 `status: open`이 있으면 `confirm`은 null이어야 한다.
- `budget.tokens`의 기본값은 probe를 뺀 unit 수 × 500,000이다.

`key`는 `C<n>`, `S<n>`, `CP<k>`, `CONFIRM` 중 하나다. `bound_sha256`은 `C<n>`이면 choice 해시, `S<n>`이면 그 표면 항목 `{id, reason}`의 해시, `CP<k>`이면 그 round의 `same_as_recommendation` 배열 해시, `CONFIRM`이면 `goal_sha256`이다. `hash`는 `{ts, text, key, bound_sha256, prev}`의 `jq -S -c` sha256이다. `CONFIRM` 줄은 `render_sha256` 필드를 추가로 가진다.

### 7.2 align

`SURFACES.md`의 12개 결정 표면은 다음이다.

| ID | 표면 |
|---|---|
| S1 | 목표, 성공 조건, 실패 조건, non-goal, 우선순위, 범위 |
| S2 | 사용자 행동, 기본값, 순서, 원자성, 멱등성 |
| S3 | 오류, 부분 실패, 복구, 롤백, 재시도 뒤 상태 |
| S4 | 명령, 플래그, 경로(route), 이벤트, 설정 키, 타입, 필드, 파일 경로, 포맷 |
| S5 | 데이터와 상태의 소유, 수명, 영속, 삭제와 보존 |
| S6 | API, 이벤트, 파일, 내부 계약, 스키마, 버전 |
| S7 | 아키텍처, 모듈 경계, 의존성, 기술 스택 |
| S8 | 동시성, 타이밍, 타임아웃, 순서, 자원 정책과 한도 |
| S9 | 호환성, 마이그레이션, 롤아웃, 다운그레이드, 기존 사용자 영향 |
| S10 | 보안, 프라이버시, 인가, 비밀 처리, 파괴적 부작용 |
| S11 | 성능 수치, 관측성, 로그와 지표와 추적, 운영 대응 |
| S12 | 검증과 수용 기준의 setup, input, action, observable, pass, evidence |

절차는 다음과 같다. root는 `--profile hwahap-align`의 새 세션이다.

1. root가 사용자의 요청을 읽고 `goal.json`의 `goal`, `base_branch`, `revision: 1`을 쓴다. 기술 스택을 먼저 묻는다.
2. root가 12개 표면을 순서대로 검토한다. 표면마다 저장소에서 알 수 있는 것은 `hwahap fact "<질문>"`으로 fact worker에게 맡긴다. fact worker는 `review.sh fact`가 `codex exec -s read-only --ignore-user-config -m gpt-5.6-luna -c model_reasoning_effort=medium --ephemeral -o .hwahap/facts/F<n>.md`로 띄우며, root는 결과를 기다리지 않고 그 사실에 의존하지 않는 표면을 계속 검토한다. 사용자에게 사실을 묻지 않는다.
3. 표면마다 결정이 갈리는 곳은 `kind: decision` choice로, "이 상황에서 무엇이 일어나야 하는가"는 `kind: scenario` choice로 만든다. 해당 없다고 판단한 표면은 이유를 적고 `S<n>` 질문으로 낸다. 용어가 코드나 앞선 발화와 다르게 쓰이면 `kind: term` choice로 낸다. 사용자 진술이 코드의 현재 동작과 다르면 fact로 기록하고 choice로 낸다.
4. frontier를 계산한다. 선행 choice가 모두 답변된 choice와 `S<n>` 질문이 frontier다. 한 round에 frontier 전체를 낸다. 화면 형식은 다음으로 고정한다.

```
❓ C1 · <제목>
<본문. 대안은 ALT1: <값>, ALT2: <값> 형식으로 나열>
➡️ 추천: ALT1. <이유 한 문장>. 근거: F1

❓ S8 · 해당 없음 판정
<이유>
➡️ 동의하면 S8=NA

답변 예: C1=ALT1 C2=OTHER: <값> C3=UNKNOWN S8=NA
```

5. 사용자는 채팅에 D48의 문법으로 답한다. `prompt.sh`가 기록하고 root가 `goal.json`의 `answer`에 옮긴다. 기록되지 않는 문장에는 같은 질문을 다시 낸다. round가 끝나면 root는 답에서 파생되는 새 choice를 만들어 `derived_from`을 적고 `rounds[]`에 round를 기록한다.
6. `n`이 4의 배수인 round 끝에 checkpoint를 낸다. 지금까지 추천과 같은 답을 고른 choice 목록을 보여주고 "이 중 다시 생각할 것이 없으면 CP<k>=OK"를 요청한다. 사용자가 특정 choice를 다시 답하면 그 답이 새 stamp로 기록되고 이전 답을 대체한다.
7. `C<n>=UNKNOWN`이 오면 root는 open item을 만들고 fact 또는 probe를 제안한다. probe는 `probe: true` unit을 `goal.json`에 추가하고 `hwahap unit P<n>`으로 실행하며, 결과 patch를 `hwahap render`가 `align.md`에 포함한다. 사용자가 결과를 본 뒤 같은 choice를 다시 낸다.
8. applicable choice가 40개를 넘거나 round가 6을 넘으면 goal 분할을 제안한다.
9. D31의 조건이 모두 맞으면 root가 `specs`, `acceptance`, `units`를 쓴다. spec은 답변된 choice만 인용한다.
10. `hwahap review cold`가 Terra reviewer를 읽기 전용으로 띄운다. brief는 `goal.json` 전문과 "선택 없이 구현 계획을 쓰고, 새 사용자 결정이 필요한 곳과 명세가 부족한 곳을 나열하라"는 지시다. `out/review/cold.md`의 세 목록이 모두 비어야 한다. 비어 있지 않으면 목록의 각 항목을 choice로 만들어 4단계로 돌아간다.
11. `hwahap render`가 `align.md`를 만든다. 내용은 goal, 표면별 판정과 답, 용어, choice 전체(질문, 대안, 추천, 답, 근거), spec, acceptance, unit, probe 결과, open item 없음의 순서다. root는 이 파일을 열어 보라고 안내하고 build가 자율로 진행되며 성공 시 draft PR이 자동으로 열린다는 것을 알린다. 사용자가 `CONFIRM ALIGN`을 친다. `prompt.sh`가 `goal_sha256`과 `render_sha256`을 함께 기록한다.
12. `hwahap align-check`가 §6.1 규칙 전부와 답변 사본 대조를 수행한다. 통과해야 build로 넘어간다.

align 세션의 한계는 §3.6에 적힌 대로다. frontier는 root의 판단이고, 수동적 답변은 checkpoint가 한 번 걸러줄 뿐이다.

**revision.** build 중 D36의 NEEDS_DECISION이 오면 사용자는 align 세션을 다시 연다. root는 그 질문을 새 choice로 추가하고 4단계부터 진행한다. 새 choice가 바꾸는 spec만 고치고, `revision`을 1 올리고, 10단계와 11단계를 다시 거쳐 새 `CONFIRM ALIGN`을 받는다. 이전 답변의 stamp는 그대로 유효하다.

### 7.3 build

root는 `--profile hwahap`의 새 세션이며 `goal.json`만 읽고 시작한다.

1. `hwahap unit U1 U2 ...`가 의존성이 해결된 unit을 `max_parallel`까지 동시에 시작한다. unit마다:
   - brief를 생성한다. 순서는 `brief.head.md`의 고정 머리말, AGENTS.md 경로, D36의 결정 경계와 NEEDS_DECISION 규칙, unit의 `title`, `paths`, `test`, 연결된 spec과 acceptance와 term 전문, "commit과 stage 금지, `paths` 밖 수정 금지, 끝나면 변경 요약 한 문단" 순이다. brief의 sha256을 `out/<unit>.brief.sha256`과 비교해 D37의 조건이 맞으면 `cached`를 출력하고 다음 unit으로 넘어간다.
   - `.hwahap/wt/<unit>`이 없으면 `git worktree add --detach .hwahap/wt/<unit> HEAD`. `depends_on`이 있으면 선행 unit의 patch를 먼저 `git apply` 한다.
   - 한 batch의 worker를 같은 명령으로 동시에 띄운다.

```sh
HWAHAP_UNIT=U1 codex exec -C .hwahap/wt/U1 -s workspace-write \
  --ignore-user-config -m gpt-5.6-luna -c model_reasoning_effort=high \
  -c model_verbosity=low -c model_reasoning_summary=none -c web_search=disabled \
  -c tool_output_token_limit=4000 --ephemeral --json \
  -o .hwahap/out/U1.last.md "$(cat .hwahap/out/U1.brief.md)" > .hwahap/out/U1.events.jsonl
```

   - 종료 뒤 `last.md` 첫 줄이 `NEEDS_DECISION:`이면 §6.5대로 기록하고 끝낸다. 아니면 `git -C .hwahap/wt/U1 diff HEAD > out/U1.patch`, `git diff --name-only`가 `paths` 안인지 검사, `test`를 worktree에서 실행해 `out/U1.test.txt`에 기록, `usage.jq`로 usage 합산.
   - 테스트 실패면 `attempt`를 올리고 같은 worktree에서 한 번 더 띄운다. brief에 테스트 출력을 덧붙인다. 두 번째도 실패면 멈추고 한 줄 요약을 출력한다.
2. 시작 전 budget 검사. D43의 50%, 80%, 100% 규칙을 적용한다.
3. `hwahap review U1`이 Terra reviewer를 `-s read-only`로 같은 worktree에서 띄운다. brief는 D40대로다. `verdict: fail`이면 finding을 덧붙여 1단계의 재시도로 돌아간다. 라운드 상한은 2회다.
4. root는 D44의 파일만 읽는다. 실패한 unit은 사용자에게 retry, skip, abort를 묻는다. skip한 unit에 의존하는 unit은 시작하지 않는다. `needs_decision` unit이 하나라도 있으면 root는 그 질문 목록을 사용자에게 보여주고 align 세션으로 돌아가라고 안내한 뒤 종료한다. gate는 인도하지 않는다.
5. 모든 `probe: false` unit이 pass면 `hwahap integrate`가 `.hwahap/wt/integration`에 patch를 위상 순서로 `git apply --check` 뒤 `git apply` 하고 `full_suite`를 한 번 실행한다. 충돌이나 실패는 사용자에게 묻는다.
6. `hwahap review integration`이 통합 diff를 검토한다. `final_review`가 `sol`이면 `-m gpt-5.6-sol`을 쓴다.
7. root가 diary를 마무리하고 종료한다. 사용자에게 추가 확인을 요청하지 않는다.
8. root가 종료하면 `gate.sh`가 실행된다. §8.2의 검사를 모두 통과하면 `report.md`와 `summary.json`을 만들고 §7.4의 deliver를 부른 뒤 §7.5의 improve 판정을 한다. 하나라도 실패하면 종료를 막고 이유를 root에게 돌려준다.

build 세션의 한계는 worker가 NEEDS_DECISION을 쓰지 않고 추측하는 경우다. 이것은 reviewer가 계약 이탈로 잡는 것 외에 막을 방법이 없으며, 잡히면 그 사실을 lesson의 허용 출처로 기록한다.

### 7.4 deliver

`deliver.sh`는 gate 통과 뒤 `gate.sh`가 부른다. 수동 `hwahap deliver`도 같은 스크립트다.

1. `HWAHAP_UNATTENDED=1`이면 `out/deliver.txt`에 `skipped:unattended`를 쓰고 끝낸다.
2. head branch 이름은 `hwahap/<goal_id>`다. D23의 금지 목록과 대조한다. `git ls-remote --heads origin hwahap/<goal_id>`에 결과가 있거나 `gh pr list --head hwahap/<goal_id> --state open`에 결과가 있으면 `skipped:exists`를 쓰고 사용자에게 알린다.
3. `.hwahap/wt/integration`에서 `git switch -c hwahap/<goal_id>` 뒤 `probe: false` unit `paths`의 합집합만 `git add -- <paths>` 한다. 합집합 밖 변경이 있으면 실패다. 이 검사는 §8.2의 7번과 같은 조건이므로 다시 검사하지 않고 그 결과를 신뢰한다.
4. commit 메시지는 첫 줄 `hwahap: <goal.statement>`, 본문에 통과 unit 목록, trailer `Hwahap-Goal: <goal_id>`와 `Hwahap-Revision: <n>`이다. 작성자는 사용자의 git 설정을 그대로 쓴다.
5. `git push -u origin hwahap/<goal_id>` 뒤 `gh pr create --draft --base <base_branch> --head hwahap/<goal_id> --title "hwahap: <goal.statement>" --body-file .hwahap/report.md`.
6. PR URL을 `out/deliver.txt`와 `summary.json`의 `pr_url`에 쓴다. push나 `gh`가 실패하면 `failed:<명령>`을 쓰고 branch는 남긴다. 재시도하지 않는다.
7. worktree는 지우지 않는다. 사용자가 PR을 처리한 뒤 `hwahap clean <goal_id>`로 지운다.

### 7.5 improve

자동 시작 판정은 `gate.sh`가 deliver 뒤에 한다. 순서는 다음과 같고 하나라도 아니면 `summary.json`의 `improve.reason`에 이유를 적고 끝낸다.

1. `~/.codex/hwahap/config.json`에 `improve.auto`가 `true`이고 `improve.budget_tokens`가 있다.
2. `harness_repo`가 git 저장소다.
3. 신호가 있다. 신호는 셋 중 하나다. 방금 run의 `cost_per_passed_unit`이 같은 저장소 benchmark의 중앙값보다 크거나, `first_try_pass`가 `units_passed`보다 작거나, `cache_hit_ratio`가 0.5 미만이다.
4. `improve.state.json`의 마지막 자동 실행이 7일 이전이다.
5. benchmark가 5개 이상이다.
6. deliver가 `done`이다. PR 없이 improve를 돌리지 않는다.

조건을 모두 만족하면 `gate.sh`는 `improve.sh --auto --budget <improve.budget_tokens>`를 백그라운드로 띄우고 exit 0 한다. hook 자체는 improve를 기다리지 않는다. `improve.sh`는 `~/.codex/hwahap/improve/<date>.log`에 진행을 쓰고, 끝나면 `improve.state.json`을 갱신한다.

`improve.sh`의 절차는 자동과 수동이 같다.

1. `harness_repo`에 `git worktree add --detach <tmp> HEAD`로 작업 공간을 만든다.
2. ruler 보정. 가장 작은 benchmark goal 하나를 현재 설정으로 3회 재실행해 `cost_per_passed_unit`의 평균과 표준편차를 구한다. noise band는 `max(2σ, 평균의 10%)`다. 재실행은 cached unit을 끄고 돌린다.
3. canary. worker effort를 `medium`으로 낮춘 설정으로 같은 goal을 1회 실행한다. 비용 차이가 band 밖이어야 한다. 아니면 "ruler 미증명"으로 종료하고 무성과 1회로 센다.
4. proposer를 `codex exec -C <tmp> -s read-only --ignore-user-config -m gpt-5.6-sol -c model_reasoning_effort=medium --ephemeral`로 띄운다. brief는 benchmark summary 전부, 방금 run의 `summary.json`, 허용 변경 범위(worker effort, reviewer 모델, `brief.head.md` 문안, `max_parallel`, `tool_output_token_limit`), "변경 하나를 unified diff로만 출력하라"는 지시다. 출력이 diff가 아니거나 허용 범위 밖 파일을 건드리면 무성과 1회로 센다.
5. diff를 `<tmp>`에 `git apply` 하고 benchmark goal 전부를 그 설정으로 실행해 ruler를 계산한다. `cost_per_passed_unit`이 band 이상 개선되고 `first_try_pass` 비율이 떨어지지 않으면 keep, 아니면 revert다.
6. keep이면 `<tmp>`에서 `git switch -c hwahap-improve/<date>`, 허용 범위 파일만 `git add`, commit, push, `gh pr create --draft` 한다. 본문은 benchmark 전후 표와 noise band다. revert이면 worktree를 지운다.
7. 3회 연속 무성과이면 종료하고, 자동 실행이었으면 D27대로 `improve.auto`를 `false`로 바꾼다. budget을 넘어도 종료한다.

lesson은 별도 명령이다. `hwahap lesson "<한두 문장>"`은 `lessons.candidates.md`에 날짜와 함께 append 한다. 허용 출처는 gate 실패, 사용자의 수정, 사용자가 되돌린 patch, reviewer가 잡은 worker의 추측이다. root는 사용자가 이 중 하나를 말했을 때만 lesson을 제안한다. 규칙으로 옮기는 것은 사용자가 한다.

## 8. hook 계약

### 8.1 prompt.sh (UserPromptSubmit)

- 입력: stdin JSON. 사용할 필드는 프롬프트 텍스트와 세션 식별자다. 정확한 필드명은 U1에서 확인해 `hwahap-v2-verification.md`에 기록하고 스크립트 상수로 둔다.
- `.hwahap/goal.json`이 없으면 exit 0.
- `.hwahap/human.turn`에 현재 시각을 쓴다.
- 텍스트를 공백으로 나눈 각 토큰이 `^(C[0-9]+|S[0-9]+|CP[0-9]+)=`이면 §6.2 형식으로 `answers.jsonl`과 workspace 밖 사본에 같은 줄을 append 한다. `bound_sha256`은 `goal.json`의 해당 항목에서 계산한다. 해당 항목이 없으면 그 토큰은 기록하지 않고 stderr에 이유를 쓴다. `OTHER:` 값은 그 토큰부터 줄 끝까지다.
- 텍스트가 `^CONFIRM ALIGN$`이면 `goal_sha256`과 `.hwahap/align.md`의 sha256을 함께 기록한다. `align.md`가 없으면 기록하지 않고 stderr에 이유를 쓴다.
- 실패해도 사용자의 턴을 막지 않는다. 오류는 stderr에 쓰고 exit 0 한다.
- 무인 실행 표시 `HWAHAP_UNATTENDED=1`이면 답변과 human.turn을 쓰지 않는다.

### 8.2 gate.sh (Stop)

- `.hwahap/goal.json`이 없으면 exit 0.
- 다음을 순서대로 검사하고, 실패하면 이유를 stderr에 쓰고 Codex의 Stop 차단 규약대로 종료를 막는다. 규약의 정확한 형식은 U1에서 확인한다.
  1. `confirm.goal_sha256`이 현재 `goal.json` 해시와 같고 `confirm.revision`이 `revision`과 같다.
  2. 모든 `answer`가 workspace 밖 `answers.jsonl` 사본에 같은 줄로 존재하고 `bound_sha256`이 현재 항목의 해시와 같다.
  2b. `not_applicable`의 모든 표면에 stamp 된 `S<n>=NA` 답이 있다.
  2c. `n`이 4의 배수인 모든 round에 stamp 된 `CP<k>=OK`가 있다.
  2d. `render.jq`를 다시 돌린 출력의 sha256이 `confirm.render_sha256`과 같다.
  3. `answers.jsonl`의 hash chain이 연속이다.
  4. 모든 `probe: false` unit에 `out/<unit>.patch`, `out/<unit>.test.txt`가 있고 test.txt의 마지막 줄이 `exit 0`이다. skip된 unit은 `out/<unit>.skipped`가 있다.
  4b. `out/*.needs_decision`이 하나도 없다.
  5. 각 patch의 변경 경로가 unit `paths` 안이다.
  6. `out/review/<unit>.md` 첫 줄이 `verdict: pass`다.
  7. `out/integration.test.txt` 마지막 줄이 `exit 0`이고 통합 diff의 변경 경로가 모든 `probe: false` unit `paths` 합집합 안이다.
  8. `out/review/integration.md` 첫 줄이 `verdict: pass`다.
  9. `.hwahap/human.turn`의 시각이 `confirm.ts` 이상이다. 사람이 `CONFIRM ALIGN`을 친 뒤 시작된 build만 인도한다.
  10. 통합 diff에 `secrets.regex`의 패턴이 없다.
  11. `check.jq`가 §6.1 규칙 전부를 통과한다.
  12. `open_items`에 `status: open`이 없다.
  13. `facts[]`의 모든 파일이 존재하고 sha256이 기록값과 같다.
- 모두 통과하면 `report.md`와 `summary.json`을 쓰고 `~/.codex/hwahap/<repo-id>/runs/<goal-id>/`에 복사한 뒤 `deliver.sh`를 부른다. deliver 결과를 `summary.json`에 반영한 뒤 §7.5의 판정을 하고, 조건이 맞으면 `improve.sh --auto`를 백그라운드로 띄운다. 그 뒤 exit 0 한다.
- deliver 실패는 종료를 막지 않는다. 사용자가 `report.md`와 `out/deliver.txt`에서 이유를 본다.
- root 토큰은 세션 rollout 파일의 마지막 `token_count.info.total_token_usage`에서 읽는다. 파일을 못 찾으면 보고서에 "측정 불가"로 적고 게이트를 막지 않는다.
- 모든 검사는 단일 조건이다. 검사 하나가 실패하면 그 자리에서 멈춘다.

### 8.3 공통

- 두 hook은 `HWAHAP_DISABLE_HOOKS=1`이면 즉시 exit 0 한다. 오탐이 사용자를 막을 때의 탈출구다.
- hook은 stdout에 아무것도 쓰지 않는다. 진단은 stderr다.
- worker, reviewer, fact worker, proposer 프로세스 안에서도 전역 hook이 실행된다. 그 cwd에는 `.hwahap/goal.json`이 없으므로 두 hook은 즉시 종료한다.
- align 세션에서 root가 종료할 때도 `gate.sh`가 실행된다. `out/`이 비어 있으면 gate는 1, 2, 2b, 2c, 2d, 3, 11, 12, 13만 검사하고 인도와 improve 판정을 하지 않는다. `out/`이 비었는지가 align 세션과 build 세션을 구분하는 유일한 조건이다.

## 9. 실행 단위

각 단위는 하나의 branch와 하나의 PR로 진행한다. 변경 200줄마다 테스트를 돌리고 commit 한다. 전역 AGENTS.md의 체크포인트 규칙이다. 각 단위의 수용 기준은 테스트 실행 출력으로 증명한다.

| 단위 | 내용 | 경로 | 의존 | 수용 기준 |

## 10. 테스트 계획

### 10.1 harness 세 개

1. fixture 테스트. bats로 스크립트 하나씩 실행하고 stdout, stderr, exit code, 생성 파일을 검사한다. fixture는 `tests/fixtures/<script>/<case>/` 아래 입력과 기대 출력이다.
2. 결정적 E2E. `tests/shim/codex`와 `tests/shim/gh`가 PATH 앞에 놓인다. `codex` shim은 인자로 받은 `-o` 경로에 fixture의 마지막 메시지를 쓰고, stdout에 fixture의 JSONL 이벤트를 출력하고, `-C` worktree에 fixture의 파일 변경을 적용하며, 호출 횟수를 파일에 기록한다. `gh` shim은 호출 인자를 기록하고 fixture의 응답을 돌려준다. push는 로컬 bare 저장소를 origin으로 둔다. API 없이 align, build, gate, deliver, improve 전체를 돈다.
3. 실제 모델 smoke. `tests/CHECKLIST.md`의 항목이며 사람이 실행한다. 작은 goal 하나를 v1과 v2로 돌려 `summary.json`을 비교하고 결과를 기록한다. batch 동시 실행의 cache hit 비율도 여기서 확인한다.

### 10.3 fuzz와 boundary

- `tests/fuzz/goal.sh`가 유효한 `goal.json`에서 jq로 변형을 만든다. 키 삭제, 타입 변경, 중복 id, `..`와 절대 경로, 빈 alternatives, 동일 value, 순환 depends_on, unit 10,000개, 비ASCII 경로, `base_branch`에 금지 이름, round 번호 건너뜀, 4의 배수 round의 checkpoint 누락, `derived_from`이 뒤 round를 가리킴, applicable 표면에 scenario 없음, probe가 depends_on에 등장. 각 변형에 대해 `align-check`가 exit 1과 이유를 내야 한다. 유효한 원본은 exit 0이어야 한다.
- `tests/fuzz/answers.sh`가 답변 토큰을 변형한다. `C1 = ALT1`, `c1=ALT1`, `C1=ALT9`, `C1=OTHER:`, `S1=NA` 뒤 텍스트, `CP1=ok`, `CONFIRM ALIGN now`. 기록되지 않아야 하는 것과 기록되어야 하는 것이 fixture로 고정된다.
- patch fuzz. 바이너리 파일, CRLF, 1 MB 단일 파일, 빈 patch. `integrate.sh`의 동작이 fixture로 고정된다.
- boundary. unit 0개는 align-check 거부, unit 1개 통과, `max_parallel` 1과 4에서 산출물 동일, budget 0은 첫 unit부터 HW_BUDGET, 정확히 50%, 80%, 100%. round 4와 8의 checkpoint. choice 40개와 41개, round 6과 7의 분할 제안. improve는 benchmark 4개와 5개, 7일 경계, 연속 무성과 2회와 3회.

### 10.4 coverage

- Linux CI에서 kcov로 각 스크립트의 branch coverage를 측정한다. 100% 미만이면 실패한다.
- D14에 따라 모든 조건이 단일 조건이므로 branch coverage 100%가 MC/DC 100%와 같다. `tests/lint-conditions.sh`가 `if`와 `[ ]` 안의 `&&`, `||`를 찾아 실패시킨다.

### 10.5 mutation

`tests/mutate.sh`는 스크립트의 각 `if` 조건에 `!`를 붙인 사본을 만들어 fixture 테스트를 돌린다. 한 변형이라도 모든 테스트를 통과하면 실패한다. 의도적으로 제외할 조건은 같은 줄 끝에 `# MUTATION-IGNORE`와 이유를 적는다. jq 프로그램은 각 규칙을 하나씩 제거한 사본으로 같은 검사를 한다.

### 10.6 regression

버그가 보고되면 `tests/fixtures/regress/<id>/`를 먼저 만들고 실패를 확인한 뒤 고친다. fixture 없는 수정은 PR에서 거부한다.

### 10.7 자원 누수

모든 bats 파일의 teardown이 `git worktree list --porcelain`의 항목 수, `pgrep -f "codex exec"`의 결과, 임시 bare origin의 branch 수가 테스트 시작 전과 같은지 확인한다. 다르면 실패한다.

### 10.8 실행 환경 변형

- 모든 스크립트는 `set -euo pipefail`로 실행되며 shellcheck 경고가 0이어야 한다.
- `shasum -a 256`만 있는 환경과 `sha256sum`만 있는 환경 양쪽에서 fixture 테스트를 돌린다.
- `max_parallel=1`과 `=4`로 같은 E2E fixture를 돌려 `out/`의 산출물이 usage의 시각 필드를 제외하고 동일한지 비교한다. cached 판정을 끄는 환경변수 `HWAHAP_NO_CACHE=1`로 돌린 결과도 동일해야 한다.
- macOS와 ubuntu CI matrix.

### 10.9 checklist

`tests/CHECKLIST.md`는 사람이 릴리스 전에 수행하는 항목이다. 최소 항목: doctor 통과, 실제 모델 smoke, `--ignore-user-config` 범위 재확인, hook 등록 확인, 실제 remote에 대한 deliver 1회와 draft 상태 확인, 자동 improve가 신호 없을 때 토큰을 쓰지 않는지 확인, batch 동시 실행의 cache hit 비율 확인, 이전 버전 run 디렉터리와의 호환 여부, 단가표 갱신일.

## 11. 플랫폼 확인 항목

U1에서 실제로 실행해 결과를 기록한다. 각 항목에는 실패 시 대안이 정해져 있으므로 새 결정이 필요 없다.

1. **sandbox 안 네트워크.** root profile로 세션을 열고 shell에서 `codex exec --ephemeral -m gpt-5.6-luna "print ok"`를 실행한다. 성공하면 D8 그대로다. 실패하면 profile에 `sandbox_workspace_write.network_access = true`가 적용됐는지 확인하고, 그래도 실패하면 root 세션을 `-s danger-full-access`가 아닌 `--add-dir`로 worktree만 열되 `codex exec`를 `approval_policy = "on-request"`로 승인받아 띄운다. 이 경우 unit당 승인 1회가 비용이며 문서에 기록한다.
2. **`--ignore-user-config` 범위.** worker에게 "사용 가능한 MCP 도구 목록과 web_search 가능 여부를 출력하라"고 지시해 결과를 기록한다. MCP가 남아 있으면 `-c mcp_servers.<id>.enabled=false`를 서버마다 추가한다. 전역 `~/.codex/AGENTS.md`가 로드되는지도 기록한다. 로드되면 brief의 commit 금지 문장이 안전장치다.
3. **hook payload 필드.** `prompt.sh`에 stdin 전체를 임시 파일로 저장하는 버전을 넣고 한 번 실행해 프롬프트 텍스트와 세션 식별자 필드명을 기록한다.
4. **Stop hook 차단 규약.** 공식 문서의 Stop hook 출력 형식을 확인하고 `gate.sh`의 차단 출력을 그 형식으로 고정한다. 차단이 불가능한 플랫폼 버전이면 gate.sh는 차단 대신 `report.md` 첫 줄에 `GATE FAILED`를 쓰고 SKILL.md가 root에게 그 줄을 확인하도록 지시한다.
5. **rollout 경로.** 세션 식별자로 `~/.codex/sessions/*/*/*/rollout-*-<id>.jsonl`을 찾아 마지막 `token_count` 줄을 읽을 수 있는지 확인한다. 못 찾으면 root 토큰은 "측정 불가"다.
6. **Stop hook에서의 백그라운드 실행.** `gate.sh`가 `nohup improve.sh &`로 프로세스를 남기고 exit 0 했을 때 Codex가 hook 종료를 기다리지 않고 세션을 닫는지, 남은 프로세스가 살아 있는지 확인한다. 기다리면 hooks.json의 `async` 옵션을 쓰고, 그것도 안 되면 자동 improve 대신 `hwahap improve`를 실행하라는 안내를 `report.md`에 쓴다.
7. **`gh`와 push.** root profile 세션의 shell에서 `gh auth status`와 `git ls-remote origin`이 성공하는지 확인한다. 실패하면 deliver는 hook이 아니라 사용자가 `hwahap deliver`를 직접 실행하는 방식으로 후퇴하고 그 사실을 기록한다.

# 게이트

게이트는 "프론티어가 비었다"는 모델의 판단을 **파일 안의 증거**로 바꾸는 절차다. 사용자에게
보이는 것은 감사 메시지 한 번과 고정 확인 문장 하나다. `status: prfaq` 전환은 세 증거가 파일에
있어야 한다: 확인 문장 원문, `confirmed_at`, 검증기 통과.

## 1. 루브릭

차원은 §1의 다섯 슬롯과 1:1이다. failure-root 변형은 차원 이름만 바뀐다(`question-tree.md`).
§4 표의 차원명은 §1 제목과 같은 짧은 이름을 쓴다. 등급은 모델이 매기되 근거 칸에 실제 F-id를
적는다. 근거 없는 등급은 무효다.

| 차원 | poor | borderline | solid | outstanding |
|---|---|---|---|---|
| 고객 (F1) | 비어 있음. 추천으로 채움. 「해당 없음」을 settled로 취급 | 결정은 있으나 "누구는 아닌가"가 열려 있음 | 결정 원문 + 비고객 경계 | solid + `사실` 항목이 뒷받침 |
| 문제 (F2) | 비어 있음. 해법을 문제처럼 적음 | 문제는 있으나 현재 우회 방법·빈도가 열려 있음 | 결정 원문 + 우회·빈도 | solid + `사실`(로그·티켓)로 확인 |
| 핵심 이익 (F3) | 비어 있음. 이익이 둘 이상 | `가정` + 검증 계획만 있음 | 결정 원문, 또는 `가정` + 사용자 수용 | solid + `사실`로 기준선 있음 |
| 근거 (F4) | 비어 있음. 선택지 글자나 추천으로 채움 | `가정` + 검증 계획 | `결정`(사용자의 관찰 원문) | `사실`(출처 + 날짜) |
| 경험 (F5) | 비어 있음 | **프로토타입 필요**로 보류 | 첫 접점과 실패 시 보이는 것 | solid + `사실`(기존 경험 자료) |

규칙 네 개.

1. `outstanding`은 근거 칸의 F-id 중 하나가 `**사실**`일 때만 쓴다. 검증기가 검사한다.
2. `**프로토타입 필요**`와 사용자 수용 없는 `**가정**`은 `borderline`이 상한이다. 검증기가 검사한다.
3. `poor` 0개이고 `borderline` 1개 이하일 때만 감사 메시지를 낸다. 그 전에는 감사 메시지를 내지
   않고, 막는 항목만 다음 라운드의 질문으로 만든다.
4. 등급을 전부 `solid`로 매기고 싶어지면 멈춘다. 차원마다 "무엇이 아직 열려 있는가"를 한 번 더
   묻고, 열린 것이 있으면 `borderline`이다.

## 2. 닫기 순서

1. **프론티어 재도출.** 파일을 `Read`로 다시 읽는다(기억으로 하지 않는다). `결정`·`가정` 항목마다
   매달린 하위 결정이 남았는지 본다. 남으면 일반 라운드를 낸다. 없으면 §4에
   `- 프론티어 재도출: 비어 있음 (R<n>)`을 쓴다.
2. **표 채움.** §4 표의 등급과 근거 F-id를 채운다. 통과 조건을 못 채우면 1로 돌아간다.
3. **감사 메시지.** §3 형식 그대로 한 번 낸다. 다른 말을 붙이지 않는다.
4. **사용자 답 처리.**
   - "예"(또는 같은 뜻의 짧은 답) → §4에 `- 확인 문장: 「<원문>」 (YYYY-MM-DD)` 기록 → 검증기 실행
     (확인 문장이 적히면 게이트 검사가 켜진다) → `- 검증기: 통과, YYYY-MM-DD` → `confirmed_at`
     → `status: prfaq` → §5 PR 작성 → 검증기 재실행 → 채팅에 `prfaq 작성: <경로>` 한 줄.
   - "아니오 + 항목" → 그 항목을 다음 라운드 질문으로 만든다. 표는 다시 채운다.
   - 다른 질문에 답하던 맥락의 "좋아요", "맞아요"는 확인이 아니다. 고정 확인 문장을 한 번 더 낸다.

## 3. 감사 메시지 형식

통과했을 때. `[게이트]` 1줄, 차원 다섯을 `·`로 이은 1줄, 프론티어 재도출 1줄, 고정 확인 문장 1줄.
**정확히 4줄이다.** 아래는 예시이며, 채팅에는 코드 펜스 없이 네 줄만 낸다.

```
[게이트]
고객 solid (F1) · 문제 solid (F2, F6) · 핵심 이익 borderline (F3) · 근거 outstanding (F4) · 경험 solid (F5)
프론티어 재도출: 비어 있음
게이트 통과. PR을 써도 됩니까? 예 / 아니오(막는 항목을 적어 주세요)
```

못 통과했을 때는 감사 메시지를 내지 않는다. 막는 항목을 질문으로 바꿔 일반 라운드로 낸다.
라운드 보고 줄에 `막힘: 핵심 이익 poor (F3)`처럼 한 항목만 덧붙인다.

## 4. 중단

사용자가 "충분해", "그만", "그냥 써", "여기까지"처럼 멈춤 신호를 보내면 다음 다섯 줄 이내를 내고
**그냥 멈춘다.** "계속할까요?"를 묻지 않는다. status는 그대로, §5 PR은 비어 있다.

아래도 예시이며, 채팅에는 펜스 없이 세 줄만 낸다.

```
[중단] status=hypothesis 유지. PR은 비어 있다.
막는 항목: 핵심 이익 borderline (F3 가정) · 경험 보류 (F5)
파일: docs/prfaq/2026-08-23-oncall-handoff.md
```

막는 항목이 풀리는 조건은 종류마다 다르다. `가정`은 사용자가 "수용"이라고 말하면 태그 줄에
`**사용자 수용** 「원문」`을 적고 풀린다. `poor` 차원은 답을 해야만 풀린다. 사용자가 "그냥 써"라고
해도 `poor`가 있으면 PR을 쓰지 않는다.

## 5. 검증기

스킬 디렉터리의 `scripts/validate_prfaq.py`를 파일 경로와 함께 실행한다.

```bash
python3 <skill dir>/scripts/validate_prfaq.py docs/prfaq/<YYYY-MM-DD>-<slug>.md
```

`ERROR:` 줄이 나오면 고친 뒤 다시 실행한다. **검증기는 라운드마다 돌린다.** 성공 줄의 `facts`,
`decisions`, `assumptions`, `parked`, `faq`가 라운드 보고 줄의 앞 다섯 숫자이고, `남은 질문`은 파일에
없는 값으로 다음 라운드 프론티어 수다. `open`은 아직 답이 없는 §1 슬롯 수다.

게이트 검사(표의 등급·F-id·poor/borderline 수·outstanding 규칙·상한 규칙·확인 문장)는 §4에 확인
문장이 적힌 뒤부터 켜진다. 그전 라운드에서는 구조 검사만 돈다. `검증기:` 줄은 `status: prfaq`일 때만
요구한다. 스크립트 실행이 막힌 환경이면 같은 검사를 직접 수행하고 §4에
`- 검증기: 수동, YYYY-MM-DD`라고 쓴다.

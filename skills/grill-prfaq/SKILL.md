# PR/FAQ 그릴링

아이디어를 결정의 트리로 보고, 프론티어(선행 결정이 모두 끝난 질문)를 라운드 단위로 묻는다.
트리가 비고 사용자가 확인한 뒤에만 PR을 쓴다. 코드나 다른 문서는 만들지 않는다.

이 문서만으로 세션을 끝까지 진행할 수 있다. `references/`는 심화 자료다. 읽을 수 있으면 읽고,
권한이나 경로 문제로 읽을 수 없으면 **이 문서의 형식을 그대로 쓴다.** 형식을 즉흥으로 바꾸지 않는다.

## 0. 두 원칙

1. **채팅은 질문과 한 줄 보고만. 상태는 파일이 든다.** 라운드 1에서 파일을 만들고 답이 올 때마다
   `Edit`한다. 채팅에 파일 내용, 요약, 재진술을 붙이지 않는다.
2. **PR은 게이트 뒤에만.** `status: hypothesis`인 동안 §5 PR은 placeholder 한 줄이다. 전환에는 파일
   안의 증거 세 가지가 필요하다: 확인 문장 원문, `confirmed_at`, 검증기 통과.

## 1. 시작

1. 해당하는 `AGENTS.md`·`CLAUDE.md`를 읽는다. `When grilling, ask one question at a time.`이 있으면
   라운드는 그대로 두고 출력만 바꾼다: 프론티어의 질문을 하나씩 순서대로 내고, 답마다 파일을
   `Edit`하되 보고 줄은 그 프론티어의 마지막 답 뒤에 한 번만 낸다. `(R<n>)`, 라운드 상한, 반박 규칙,
   §4의 R1~R4 구성은 프론티어 기준으로 그대로다. 이 모드는 총 질문 12개를 넘기지 않는다.
2. 경로는 `<cwd>/docs/prfaq/<YYYY-MM-DD>-<slug>.md`. slug는 영문 소문자 kebab 3단어 이하로 직접
   정한다. 묻지 않는다. 같은 slug의 파일이 있으면 새로 만들지 않고 읽어서 이어간다(§6의 재도출부터).
3. 아래 템플릿을 **글자 그대로** 복사해 파일을 만든다. `title`, `created`, `updated`만 채운다.
   **§1 슬롯은 답이 오기 전까지 비워 둔다.** 산문으로 미리 채우지 않는다. Q0 답이 나오면 `customer`를
   맞추고, none이면 F1~F3 제목과 §4 표의 차원명을 §4의 짧은 이름으로 바꾼다. 허락을 묻지 않는다.
   절 제목(`## 1. 가설` …)과 항목 제목(`### F1. …`) 형식은 바꾸지 않는다.
4. 라운드 1은 Q0 + F2 + F4다(§4). 아이디어가 독립된 결정 둘 이상을 담고 있으면 Q0 대신 분할 질문
   하나만 낸다.

```markdown
---
title: <아이디어 한 줄>
status: hypothesis
customer: external
created: YYYY-MM-DD
updated: YYYY-MM-DD
confirmed_at:
---

# <아이디어 한 줄>

**작성 규칙** — 확인된 사실만 산문으로 쓴다. 사용자만 쓸 수 있는 자리는 `【 】`로 비워 둔다. 사용자의 말은 「 」 안에 원문 그대로 적는다. status가 `prfaq`가 되기 전에는 §5가 비어 있다.

## 1. 가설

### F1. 고객

### F2. 문제

### F3. 핵심 이익

### F4. 근거

### F5. 경험

## 2. FAQ

## 3. 범위 밖

## 4. 게이트

| 차원 | 등급 | 근거 |
|---|---|---|
| 고객 | | |
| 문제 | | |
| 핵심 이익 | | |
| 근거 | | |
| 경험 | | |

- 프론티어 재도출:
- 검증기:
- 확인 문장:

## 5. PR

(비어 있음 — status가 prfaq가 된 뒤에 쓴다)
```

템플릿의 `<…>`는 채울 자리다. §1의 다섯 항목은 비어 있어도 삭제하지 않는다. 새 항목은 §2에
`### F6.`부터 번호를 이어 붙인다. `F4-1` 같은 하위 번호를 만들지 않는다.

## 2. 라운드

한 라운드는 프론티어 전체다. 서로 의존하지 않는 질문만 한 라운드에 넣는다. 열린 답에 의존하는
질문은 다음 라운드다. 형식은 다음과 같고, 사용자는 번호로 답한다.

```
❓ **Q1** - **<제목>**: <본문 2문장 이하. 선택지 A / B / C>

➡️ <추천 1문장>

---

❓ **Q2** - **<제목>**: <본문>

➡️ <추천 1문장>
```

근거 질문(F4)에는 **선택지를 두지 않는다.** 본문은 "무엇을 보고 그렇게 아십니까?" 같은 열린 질문
한 문장이고, 화살표 줄은 `➡️ 추천 없음 — 근거 또는 가정으로만`이다. 글자 하나짜리 답이나
"모르겠다"는 `가정`으로 적는다.

| 항목 | 상한(설계값) |
|---|---|
| 라운드당 질문 | 8. 넘으면 미루지 않고 분할 질문 하나만 낸다(§5) |
| 질문 제목 | 6어절 |
| 질문 본문 | 2문장. 선택지는 `A / B / C` 인라인 3개 이하, 선택지 하나는 12어절 이하 |
| 추천 | 1문장. 추천의 이유나 질문을 내는 이유는 적지 않는다 |
| 라운드 수 | 목표 3~4. 5를 넘기면 파일을 갱신하고 "새 세션에서 파일로 이어가자" 한 줄을 낸다 |

질문은 답이 §1 슬롯을 바꾸거나, §2 FAQ 항목을 추가·수정하거나, 항목을 §3으로 옮길 때만 낸다.
사실은 묻지 않는다. 코드·문서·로그로 확인할 수 있는 것은 sub-agent에 맡기거나(없으면 라운드 사이에
직접) 조사해 `**사실**`로 적는다. 조사가 끝나지 않은 것의 하위 질문만 다음 라운드로 미룬다.

답을 받으면 파일을 고치고 검증기를 한 번 돌린 뒤(§6) 라운드 보고를 **정확히 한 줄** 낸다. 앞
다섯 숫자는 검증기 성공 줄의 `facts`·`decisions`·`assumptions`·`parked`·`faq`를 그대로 옮긴 것이고,
`남은 질문`만 다음 라운드 프론티어 수다. `ERROR:`가 나오면 보고 전에 고친다.

```
[R2] 사실 1 · 결정 4 · 가정 2 · 보류 1 · FAQ 1 · 남은 질문 3
```

보고 줄과 다음 라운드 사이에 다른 문장을 두지 않는다. 다음은 쓰지 않는다: 사용자 답 되풀이,
이전 라운드 요약, 질문을 내는 이유, 방법론 설명, "이제 다음 라운드를…" 같은 도입부, 파일 쓰기
허락 요청, 이전 답 인용. 이전 답을 가리켜야 하면 `F3 기준으로`처럼 id만 쓴다.

두 라운드 연속으로 사용자가 추천을 전부 수락하면, 다음 일반 라운드에 질문 하나를 더한다. 가장 비싼
결정 하나를 `A 유지 / B <반대안>`으로 다시 묻고 `➡️`에는 반대안을 건다. 별도 라운드를 만들지 않고
라운드당 8개 상한 안에 넣으며, 세션에 한 번만 한다. 반박 없는 세션은 필요 없던 세션이다.

## 3. 사실·결정·가정

FAQ 항목의 첫 줄은 태그 줄 하나다. 문장 끝 굵은 표기가 아니라 줄 머리 태그다.

| 태그 | 누가 | 필수 |
|---|---|---|
| `**사실**` | 에이전트가 조사 | 같은 줄에 `— 출처: <경로 또는 URL>, YYYY-MM-DD` |
| `**결정**` | 사용자 | 「 」 안에 원문 그대로. 요약·의역 금지. 끝에 `(R<n>)` |
| `**가정**` | 아직 아무도 | `— 검증 계획: …` 또는 `**사용자 수용** 「원문」` 중 하나 |
| `**프로토타입 필요**` | 보류 | §1 슬롯이면 §3에도 `F<n> — **프로토타입 필요**` |

사용자가 「추천대로」, 「B」처럼 선택지로 답하면 원문 뒤에 선택된 내용을 붙인다:
`**결정** 「추천대로」 = 주간 온콜을 넘기는 SRE (R2)`. 원문 없이 내용만 적지 않는다.

F4(근거)는 `사실`, `결정`(사용자의 관찰 원문), `가정`만 허용한다. 선택지 글자 하나를 원문으로 넣어
`결정`으로 만들지 않는다. 사용자가 "모르겠다"고 하면 그것은 `가정`이고, 검증 계획을 한 줄 제안한 뒤
수용 여부를 다음 라운드에 묻는다.

## 4. 질문 트리

뿌리는 Working Backwards의 다섯 질문이다. Q0가 고객 유형을 정하고, 유형이 F1~F5의 문구를 정한다.
라운드 1의 첫 질문은 다음이다.

```
❓ **Q1** - **고객 유형**: 이 아이디어로 덕을 보는 쪽은 누구입니까? A 외부(돈이나 시간을 내는 사람) / B 내부(개발자·운영자) / C 없음(고장·부채·정리)

➡️ <A/B/C 중 하나와 한 문장 이유>
```

답이 A면 `customer: external`, B면 `internal`, C면 `none`이다. C면 §3에 `- 「해당 없음」 — Q0, R1`을
쓴다. 「해당 없음」은 settled가 아니다. 다른 값(`team`, `both` 등)은 쓰지 않는다.

| 슬롯 | external · internal | none (failure-root) |
|---|---|---|
| F1 | 고객: 누가 쓰고, 누구는 아닌가 | 대가: 지금 누가 비용을 치르나 |
| F2 | 문제: 지금 어떻게 우회하고, 얼마나 자주 겪나 | 깨지는 것: 지금 무엇이 어떻게 깨지나 |
| F3 | 핵심 이익: 하나만 고르면 무엇인가 | 가능해지는 것: 고치면 무엇이 가능해지나 |
| F4 | 근거: 그들이 원한다는 것을 어떻게 아나 | 근거: 깨진다는 것을 어떻게 아나 |
| F5 | 경험: 첫 접점은 무엇이고 실패하면 무엇이 보이나 | 경험: 고친 뒤 첫 접점과 실패 시 보이는 것 |

§1 항목 제목과 §4 게이트 표의 차원명은 이 표의 짧은 이름으로 같게 쓴다. 콜론 앞의 두세 글자가
그 이름이다.

R1 = Q0 + F2 + F4. R2 = F1 + F3 + F5 + R1 답의 자식. R3 = 자식. R4 = 닫기. 전형적인 자식과 자격
필터의 예는 `Read [question-tree.md](references/question-tree.md) completely.`에 있다.

뿌리 다섯 질문은 Amazon Working Backwards의 PR/FAQ 질문을 옮긴 것이다. 프론티어·라운드 구조와
§1의 opt-out 문장은 mattpocock의 grilling에서 가져왔다. 한국어 문구는 이 스킬의 의역이다. 다만
`When grilling, ask one question at a time.`은 원문 그대로여야 사용자의 `CLAUDE.md`와 맞는다.

출처: <https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md> (확인 2026-08-23)

## 5. 보류와 범위 밖

"느낌", "모양", "배치"처럼 보지 않고는 답할 수 없는 질문은 말로 풀지 않는다. `**프로토타입 필요**`로
적고 §3에 올린 뒤 다시 묻지 않는다.

프론티어가 8개를 넘으면 분할 질문 하나만 낸다:
`❓ **Q1** - **범위 분할**: 열린 결정이 <n>개입니다. A <가지 A> / B <가지 B> 중 지금 다룰 쪽은?`
고르지 않은 가지는 §3에 `- <가지> — 다음 세션`으로 적는다.

## 6. 닫기

순서는 다음과 같다. 루브릭 표는 `Read [gate.md](references/gate.md) completely.`에 있다.

1. 프론티어가 비면 파일을 `Read`로 다시 읽어 `결정`·`가정`마다 남은 하위 결정을 찾는다. 기억으로
   하지 않는다. 남으면 일반 라운드. 없으면 §4에 `- 프론티어 재도출: 비어 있음 (R<n>)`.
2. §4 표를 채운다. 등급마다 근거 F-id를 적는다. 등급은 네 가지다.

   | 등급 | 언제 |
   |---|---|
   | `poor` | 비어 있거나 추천으로 채운 차원 |
   | `borderline` | 검증 계획만 있는 `가정`, 또는 보류. 두 경우의 상한이다 |
   | `solid` | 사용자 원문이 있다 |
   | `outstanding` | 근거 F-id 중 하나가 `사실`이다 |

   `poor` 0개, `borderline` 1개 이하일 때만 3으로 간다. 아니면 막는 항목을 질문으로 바꿔 일반
   라운드를 낸다.
3. 감사 메시지를 한 번 낸다. **정확히 아래 네 줄이다.** 코드 펜스로 감싸지 않고, 줄을 더하거나
   빼지 않는다. 마지막 줄은 글자 그대로 쓴다.

   > `[게이트]`
   > `고객 solid (F1) · 문제 solid (F2, F6) · 핵심 이익 borderline (F3) · 근거 outstanding (F4) · 경험 solid (F5)`
   > `프론티어 재도출: 비어 있음`
   > `게이트 통과. PR을 써도 됩니까? 예 / 아니오(막는 항목을 적어 주세요)`
4. "예"를 받으면 §4에 `- 확인 문장: 「원문」 (날짜)`를 쓰고 검증기를 돌린다. 확인 문장이 적히면
   검증기의 게이트 검사가 켜진다.

```bash
python3 <이 스킬 디렉터리>/scripts/validate_prfaq.py docs/prfaq/<YYYY-MM-DD>-<slug>.md
```

   스킬 디렉터리를 모르면 `~/.claude/skills/grill-prfaq` 또는
   `${CODEX_HOME:-$HOME/.codex}/skills/grill-prfaq`에서 찾는다.

5. 통과하면 `- 검증기: 통과, 날짜`, `confirmed_at`(확인 문장의 날짜와 같아야 한다),
   `status: prfaq` 순으로 고친다. 실패하면 `ERROR:`를 고치고 다시 돌린다. 스크립트 실행이 막힌
   환경이면 같은 검사를 직접 수행하고 `검증기: 수동, 날짜`.

"아니오 + 항목"이면 그 항목을 다음 라운드 질문으로 만든다. 다른 질문에 답하던 "좋아요"는 확인이
아니다. 고정 문장을 한 번 더 낸다.

## 7. PR 작성

`status: prfaq`가 된 뒤 §5에만 쓴다. 다 쓰면 검증기를 한 번 더 돌린다. 이 실행이 `검증기` 줄,
`confirmed_at`, §5 산문 규칙을 검사한다. `ERROR:`가 나오면 §5만 고치고 다시 돌린다. 통과하면
채팅에 `prfaq 작성: <경로>` 한 줄만 낸다. 환경 제약(참조 파일을 못 읽었다, 검증기를 못 돌렸다)을
알려야 하면 그 뒤에 한 줄만 덧붙인다.

형태는 제목 1줄, 부제 1줄, 그리고 문제 · 해결 · 시작 방법 각 한 문단 산문이다. 문장 끝에 `(F2)`처럼
근거 F-id를 단다. 불릿, 번호 목록, 인용문을 쓰지 않는다. 확인된 사실과 사용자의 결정만 산문으로
쓰고, 사용자만 쓸 수 있는 판단·이유·시점은 `【 】`로 비워 둔다. 빈칸이 남아도 status는 `prfaq`다.
빈칸은 결함이 아니라 아직 듣지 못했다는 표시다.

## 8. 중단

"충분해", "그만", "그냥 써" 같은 신호에는 다음 세 줄을 내고 그냥 멈춘다. 코드 펜스로 감싸지
않는다. "계속할까요?"를 묻지 않는다. status와 §5는 그대로다.

> `[중단] status=hypothesis 유지. PR은 비어 있다.`
> `막는 항목: 핵심 이익 borderline (F3 가정) · 경험 보류 (F5)`
> `파일: docs/prfaq/2026-08-23-oncall-handoff.md`

`가정`은 사용자가 "수용"이라 말하면 원문을 적고 풀리지만, `poor` 차원은 답을 해야만 풀린다.
"그냥 써"라고 해도 `poor`가 있으면 PR을 쓰지 않는다.

## 9. 절대 하지 않을 것

- `status: hypothesis`인 동안 §5에 placeholder 외의 글을 쓴다.
- 확인 문장·검증기 통과 없이 `status: prfaq`로 바꾼다.
- 템플릿의 절 제목, 항목 번호 형식, `customer` 값을 바꾼다.
- 답이 오기 전에 §1 슬롯을 산문으로 채운다.
- F4에 선택지를 두거나 `➡️` 추천으로 채운다.
- 검증 계획도 사용자 수용도 없는 `가정`을 남긴다.
- 「해당 없음」을 settled로 취급한다.
- 이 파일 외의 파일(코드, 설정, 다른 문서)을 만들거나 고친다.
- PR이나 FAQ 내용을 채팅에 쓴다.
- 근거 F-id 없이 등급을 매기거나, `사실` 없이 `outstanding`을 준다.
- 보류나 미수용 `가정` 차원에 `solid` 이상을 준다.
- 기억으로 프론티어를 재도출한다.
- 출처 없는 `사실`, 원문 없는 `결정`을 적는다.
- 사용자 답을 요약·의역해서 적는다.
- 고객·리더·동료의 인용문을 지어낸다.

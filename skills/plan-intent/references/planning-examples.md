# 질문과 기획서 예시

질문을 설계하거나 기획서를 처음 작성할 때 필요한 예시만 참고한다. 아래 대화는 설명을 위해 만든 가상 사례다. 숫자와 동작은 다른 작업의 기본값이 아니다.

## 의도에서 새로운 결정을 분리하기

가상 요청: “보고서 내보내기가 오래 걸릴 때 지금 진행 중인지 알고 싶어요.”

현재 이해: 보고서를 만드는 동안 진행 상태를 알 수 있기를 원한다. 진행률의 정확도, 취소 기능, 시간 제한, 실패 후 재시도는 아직 정해지지 않았다.

먼저 현재 처리 단계와 화면에서 알 수 있는 사실을 조사한다. 그다음 “완료 비율을 계산할 수 없다면 현재 처리 단계를 보여주는 안을 제안합니다. 실제 비율이 필요한지에 따라 수집할 정보와 작업 범위가 달라집니다”처럼 결정을 드러낸다. 필요한 선택을 받은 후 파생 결정을 다룬다.

자동 취소나 재시도를 요청의 의미에 포함하지 않는다. 사용자가 해당 정책 선택까지 구체적으로 위임했다면 근거 있는 정책을 제안·선택하고 위임과 선택 결과를 기록한다.

## 부분 성공을 같은 의미로 이해하기

질문 예시: “이미지 8장 중 2장을 변환한 뒤 실패했습니다. 이미 변환한 결과를 남길까요, 아니면 이번에 만든 결과를 모두 지울까요?”

답이 “남긴다”라면 “변환된 2장은 보존하고 나머지는 미완료로 표시합니다”라고 설명한다. 이어서 사용자가 “그러면 이번 작업으로 만들어진 파일은 하나도 없는 거네요?”라고 하면 이해 차이가 드러난 것이므로 결과를 다시 설명하고 선택을 바로잡는다.

이해 여부, 선택한 동작, 실행 요청은 각각 기록하되 항상 세 번의 승인 질문으로 만들지는 않는다.

## 학습 목적을 동작으로 연결하기

사용자가 텍스트 검색 원리를 배우며 개인 메모 검색 도구를 만들고 싶어 한다면, 직접 학습할 부분과 기존 도구를 활용할 부분을 확인한다. 메모 파일 형식을 유지하면서 검색 색인과 순위 계산을 학습하는 목표는 함께 성립할 수 있다.

사용자가 말하지 않은 고객군, 수익 목표, 경쟁 제품 대체를 추가하지 않는다. 다른 프로젝트의 아키텍처나 제한값을 새로운 프로젝트의 규칙으로 복사하지 않는다.

## 기획서의 최소 형태

제목과 현재 상태를 자연어로 적는다. 상태는 “초안이며 취소 범위는 미결”, “사용자가 동작을 확인했으며 구현도 요청함”처럼 실제 근거가 있는 내용만 표현한다. 다음 구성은 시작점이며 의무 양식이 아니다.

### 왜 이 일을 하는가

핵심 사용자 표현, 현재의 불편, 원하는 결과와 유지할 조건을 적는다. 조사한 사실과 의도 해석을 구분한다.

### 어떤 결과를 만들기로 했는가

상황별 동작과 중요한 선택을 적는다. 복잡하면 다음 열을 사용한다.

| 의도 또는 상황 | 결정한 동작 | 근거와 선택 출처 | 확인 방법 |
|---|---|---|---|
| 실제 요청에서 가져온 상황 | 선택된 결과와 금지할 결과 | 사용자 답변·자료 참조, 또는 제안임을 표시 | 준비·행동·기대 결과와 남길 증거 |

비공개 문서에서는 필요한 질문·답변 원문과 확인 위치를 중요한 결정 옆에 둘 수 있다. 공개 문서에는 선택의 의미를 요약하고 공개 가능한 출처만 적는다. 어느 경우에도 추론을 사용자 원문으로 바꾸거나 없는 날짜·대화 식별자를 채우지 않는다.

### 어떻게 이어서 작업할 수 있는가

각 작업의 목적, 대상 경계, 선행 조건, 완료 증거를 적는다. 실제 조사 없이 파일 경로나 명령을 만들지 않는다. 경로가 미확인이어도 기획의 다른 부분을 작성할 수 있다.

### 무엇이 아직 열려 있는가

미결 사항마다 결과에 미치는 영향, 필요한 정보, 확인 방법을 적는다. 사용자 판단이 필요한 것과 후속 구현자가 조사할 수 있는 것을 구분한다. 실제 허용된 실행 범위도 적는다.

## 충분한 기존 계획으로 시작하기

사용자가 동작·범위·검증을 이미 정한 문서를 주고 구현까지 요청했다면, 원문을 보존하면서 현재 자료와의 충돌만 살핀다. 충돌이 없으면 새로운 인터뷰 없이 다음 작업으로 이어간다. 외부 배포처럼 별도 권한이 필요한 행동은 기존 허용 범위를 확인한다.

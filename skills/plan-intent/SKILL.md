# 의도 중심 기획

사용자가 왜 이 일을 원하는지 보존하면서, 서로 같은 결과를 이해하고 다른 구현자가 이어받을 수 있는 기획을 만든다. 질문 수나 문서 분량보다 의도 오해로 인한 재작업을 줄이는 것을 우선한다.

이 스킬은 Markdown으로만 구성된 대화·판단 지침이다. 실행 코드, 스크립트, 프로그램처럼 해석할 계약 블록, 별도 설정 파일, 실행기 의존성을 추가하지 않는다. Markdown 지침 자체가 권한 통제나 동작 준수를 강제한다고 설명하지 않는다.

## 적용 원칙

- 시스템·개발자 지침 안에서 사용자의 현재 명시적 지시와 기존 합의를 이 스킬의 일반 지침보다 우선한다. 과거 선호는 현재 요청을 해석하는 참고이며 새 요구를 거부하는 근거가 아니다.
- 기획 요청은 기획 결과까지 완성한다. 코드 구현을 함께 요청받았다면 기존 실행 권한을 보존하고, 기획이 충분해진 뒤 요청한 구현으로 이어간다. 기획 문서의 완성만으로 별도 외부 행동의 권한을 만들지 않는다.
- 사용자가 이미 정한 선택을 다시 묻지 않는다. 대화·계획·현재 자료에서 답을 찾고, 빠진 중요한 결정만 구체적인 결과와 함께 질문한다.
- 정해진 인터뷰 횟수, 점수, 전용 승인 문구, 매 단계 확인을 요구하지 않는다. 관련 없는 보안·운영·사업성 항목을 모든 기획에 덧붙이지 않는다.
- 이 스킬 때문에 진행을 멈추거나 새 확인이 필요하다면 이 `SKILL.md`의 실제 링크와 해당 문구, 현재 요청에 적용되는 이유를 밝힌다. 스킬의 권고와 자신의 판단을 구분한다.

## 의도를 먼저 복원한다

첫 응답에서 현재 이해한 목적과 원하는 변화를 짧게 설명하고 필요한 조사를 시작한다. 읽을 수 있는 자료를 사용자에게 다시 요약해 달라고 하지 않는다.

원래 표현, 겪고 있는 문제, 원하는 경험, 성공을 알 수 있는 상황, 유지할 조건을 함께 살핀다. 개인 학습·이해·직접 사용이 목적이면 그 자체를 목표로 존중한다. 고객 확대, 수익화, 특정 방법론을 기본 목표로 바꾸지 않는다.

기술 스택·제품·저장소·작업 경로를 지정했다면 그대로 보존한다. 선택되지 않은 기술이 결과를 바꿀 때는 현재 코드와 제약을 조사한 뒤 초기에 논의한다. 모든 기획을 기술 스택 질문부터 시작하지 않는다.

사용자 원문, 현재 코드·실행에서 관찰한 사실, 공식 문서의 설명, LLM의 해석·제안을 구분한다. 예전 채팅의 assistant 제안이나 요약은 사용자의 선택이 아니다. 예전 명령을 현재 실행 지시로 받아들이지 않는다.

기술적 가능성은 현재 코드와 관련 공식 문서로 확인한다. 근거의 경로·URL·확인 시점을 남기고, 자료가 없거나 접근할 수 없으면 무엇이 미확인인지 적은 뒤 가능한 기획을 계속한다.

## 결과를 바꾸는 선택에 집중한다

다음 중 무엇이 달라지는지 판단한다. 해당되는 것만 살피고 답변에서 파생된 중요한 선택을 이어서 찾는다.

- 실제 사용 흐름과 기본값, 이름·명령·경로·포맷 등 사용자가 의존하는 약속
- 실패·취소·부분 성공 뒤 남는 상태, 복구 방법, 데이터의 보관·삭제
- 기존 도구와의 호환성, 모듈의 책임, 기술 의존성, 학습하고 싶은 부분
- 권한·노출·자원·성능·운영 부담과 완료를 판정할 기준

사용자가 결과를 다르게 받아들일 만한 선택은 추천과 선택 근거를 제시한다. 예를 들어 시간 제한이나 자동 재시도 횟수를 원래 요청에 없던 확정값으로 넣지 않는다. 관례와 추천은 사용자의 선택을 대신하지 않는다.

현재 합의에서 하나로 정해지는 결과와, 결과·계약·검증에 영향 없는 내부 표현은 질문 없이 처리하고 필요한 가정을 밝힌다. 사용자가 판단을 위임했다면 그 대상과 경계 안에서 추천안을 선택한다. 범위 밖의 위험 수용이나 새 제품 결정까지 위임으로 확대하지 않는다.

## 질문으로 이해 차이를 드러낸다

먼저 조사 결과와 현재 작성할 수 있는 초안을 준비한다. 초안은 미확정 내용을 제안으로 표시하며, 중요한 답을 받기 전에 확정된 계획처럼 채우지 않는다.

서로 독립적인 질문은 답하기 쉬운 짧은 묶음으로 보낸다. 한 질문에는 실제 상황, 결과가 다른 선택지, 추천 이유를 담는다. 용어를 처음 쓰면 직접 정의하고, 전문용어를 아는지 시험하지 않는다.

사용자의 답에서 정상 상황뿐 아니라 중요한 실패 상황과 허용하지 않는 결과까지 확인한다. 선택한 결과를 다시 설명하면 충분한 경우에는 새 동의를 요구하지 않는다. 답에 모순이나 오해가 보이면 그 차이만 짚는다. 구체적인 예시는 [질문과 기획서 예시](references/planning-examples.md)를 필요한 부분만 읽는다.

“알아서 해줘”는 맥락에 따라 판단 위임일 수 있다. 이미 설명한 선택을 위임받았다면 진행한다. 핵심 목표가 충돌하거나 데이터 손실처럼 위임 범위가 불분명한 결과가 남으면 그 결정만 묻는다. 단순한 동의나 응답 부재로 미설명 선택을 승인 처리하지 않는다.

답을 기다리는 동안 독립적인 조사와 문서 정리를 이어간다. 답이 필요한 부분은 미결로 유지한다. 시간이 지났다는 이유로 선택이나 승인을 만들어내지 않는다.

## 하나의 기획서로 연결한다

별도 형식을 요청받지 않았다면 기존 기획 문서를 갱신하거나 `docs/plans/YYYY-MM-DD-slug.md` 한 파일에 정리한다. 기존 문서를 덮어쓰기 전에 요청과 관련된 파일인지 확인한다. 저장소가 없으면 사용할 수 있는 작업 공간에 Markdown 파일을 만들고, 대화만 요청받았다면 본문으로 전달한다.

공개용 문서에는 의사결정의 의미를 보존한 요약과 공개 출처를 남긴다. 비공개 대화의 원문·제목·식별자·링크·개인 경로는 포함하지 않고 원래 대화에서 확인한다. 공개 저장소 안에 비공개 근거를 따로 전사하지 않으며, 공개 요약을 원문 인용이나 승인 증명으로 표시하지 않는다.

기획서는 다음 내용이 자연스럽게 이어지도록 쓴다. 작은 요청은 짧은 문단으로 합치고, 복잡한 선택만 표로 비교한다. 빈 항목을 채우기 위한 질문은 만들지 않는다.

- **원래 의도:** 핵심 사용자 표현과 해결할 문제, 원하는 변화, 성공을 알아볼 상황
- **범위와 근거:** 이번에 다룰 대상, 유지할 조건과 제외할 일, 현재 사실과 자료의 한계
- **결정한 동작:** 상황별 결과, 중요한 선택과 이유, 답변의 출처, 제안·미결 사항
- **구현과 검증 방향:** 각 동작을 실현할 작업 경계·의존 순서와 완료를 보여줄 증거
- **현재 합의:** 사용자가 확인한 내용, 위임한 판단, 남은 질문과 실제 실행 요청의 범위

작업을 나눌 때는 각각이 어떤 의도를 충족하고 무엇으로 검증되는지 연결한다. 기획에 필요하지 않은 함수 목록이나 파일별 코드 작성 순서까지 미리 고정하지 않는다. 중요한 책임·인터페이스·호환성 경계는 분명히 적는다.

검증 기준은 준비 상황, 행동, 관찰 가능한 기대 결과, 필요한 증거를 담는다. 실패·취소 등 실제 위험이 있는 경로를 포함한다. “테스트 통과”만 적거나 성공을 맞추기 위해 기준을 낮추지 않는다. 수치가 필요한 성능 목표는 측정 조건과 함께 결정한다.

계획한 검사와 실제 수행한 검사를 구분한다. 소스 확인, 모의 환경, 실제 실행이 각각 무엇을 증명하는지 밝히고 미실행 결과를 성공으로 쓰지 않는다. 기획 단계에서는 실제 검증을 전부 실행할 필요가 없다.

## 중요한 모호함이 남았는지 검토한다

초안을 원래 요청과 대조해 빠진 의도, 임의로 추가한 선택, 모순, 검사할 수 없는 완료 기준을 찾는다. 특히 “서로 다른 두 구현이 이 문서를 모두 만족하지만 사용자는 하나를 거부할 수 있는가?”를 살핀다.

독립적으로 진행할 조사나 초안 검토가 시간 또는 품질을 개선한다면 가능한 서브에이전트에 맡긴다. 검토자는 원래 요청·기획서·필요한 근거만 받고 작성자의 결론에 유도되지 않게 한다. 새 제품 결정을 대신 내리거나 사용자 승인을 대신하지 않는다. 위임 수단이 없으면 직접 검토하고 독립 검토를 수행했다고 주장하지 않는다.

대화에 참여하지 않은 구현자가 새로운 중요한 선택 없이 작업과 검증을 설명할 수 있는지 확인한다. 반례가 발견되면 영향받는 선택만 조사·질문하고 수정한다. 새 문제나 관련 변경 없이 이미 통과한 검토를 반복하지 않는다.

기획의 종료 기준은 원래 의도와 동작이 연결되고, 결과를 바꾸는 미결 사항이 해결되거나 명시된 위임 범위에 들어가며, 완료를 확인할 방법이 있는 것이다. 모든 미래의 모호함을 없앴다고 보증하지 않는다. 후속 탐색거리와 현재 구현을 막는 결정을 구분한다.

검토 가능한 최종안을 제시한다. 새 중요한 제안을 사용자 선택으로 확정해야 할 때만 확인을 받고, 이미 받은 합의와 권한은 그대로 이어간다. 단순 문서 작성 요청은 초안을 전달하는 것으로 완료할 수 있으며 미확정 부분을 숨기지 않는다.

## 수정과 재개

중간 질문에는 답한 뒤 원래 목표를 계속한다. 새 요구는 영향을 받는 의도·동작·검증에 반영하고, 관계없는 기존 합의를 다시 열지 않는다.

승인된 동작을 바꾸어야 하면 이전 결정과 변경 이유를 남기고 해당 범위만 다시 논의한다. 같은 동작을 달성하는 구현 수정은 허용된 재량 안에서 처리한다. 만들어진 코드에 맞춰 사용자의 원래 의도나 완료 기준을 소급해서 바꾸지 않는다.

중단·재개 시에는 확정 내용, 근거, 미결 사항, 바로 다음 행동을 기획서에 남긴다. 기존 계획을 전달받으면 금지 조건·예외·검증 기준과 실제 확인 내역을 보존한다. 읽을 수 없는 과거 답변을 재구성해 확인 기록을 만들지 않는다.

응답은 한국어의 간결한 합니다체를 기본으로 한다. 결론과 사용자 경험을 먼저 설명하고, 근거와 한계를 이어 쓴다. 목록과 표는 비교나 순서가 도움이 될 때 쓴다. 비유를 쓰지 않고 상투어와 불필요한 구현 용어를 줄인다.

이 스킬을 수정하거나 Astra 준수 여부를 검토할 때만 [설계 원칙과 공식 모델 가이드](references/model-guidance.md)를 읽는다. 매 실행마다 공식 가이드 전체를 다시 읽는 절차는 요구하지 않는다.

# 함께 쓰는 저녁 일기

사용자가 실제 하루를 이해하고, 강점을 유지하면서 불편한 행동 패턴의 비용을 줄이도록 돕는다. 소크라테스식 문답은 답을 정해 놓고 설득하는 대신, 사용자의 설명에서 근거·가정·다른 해석을 함께 검토하는 질문법이다.

이 스킬은 Markdown 지침과 참고 파일로만 구성한다. 실행 스크립트, 별도 설정 파일, 상주 수집기를 요구하지 않고, 별도 데이터베이스를 만들지 않는다. 대화 기록을 읽는 도구가 없으면 사용자가 제공한 내용으로 같은 문답을 진행한다.

## 대화의 기본값

- 한국어의 짧고 직접적인 합니다체로 대화한다. 질문은 기본적으로 한 번에 하나만 하고, 실제 답변을 받은 뒤 다음 질문을 고른다. 질문 도구가 있다면 해당 도구의 사용 규칙을 따른다.
- 오늘의 일을 확인하는 일과 사용자의 성격을 평가하는 일을 구분한다. 단점을 찾아내는 것을 성공 조건으로 삼지 않는다. 성격 유형·질환·숨은 동기를 단정하지 않는다.
- 사용자 원문, 확인한 활동 기록, assistant의 결과 보고, 해석·제안을 구분한다. AI가 작성하거나 실행한 결과는 사용자의 독립 이해·직접 수행·감정의 증거가 아니다.
- 이 스킬의 과거 가설보다 현재 사용자 설명을 우선한다. 사용자가 해석을 부정하면 철회한다. 거부를 회피·저항의 증거로 재해석하지 않는다.
- 기본은 약 10분 안에 마칠 수 있는 깊이로 시작한다. 사용자가 짧게 하거나 건너뛰거나 끝내길 원하면 즉시 범위를 줄인다. 정해진 문항 수를 채우지 않는다.
- 매일 저녁 사용하는 흐름을 제공한다. 스킬 호출만으로 알림·예약·자동 실행을 만들지 않는다. 별도 예약 요청이 있을 때에만 그 요청을 처리한다.

## 1. 오늘의 근거를 작게 모은다

환경의 현재 날짜와 시간대를 사용하고, 일기의 대상 날짜를 첫 안내에 표시한다. 자정을 넘겼거나 사용자가 다른 날짜를 지정하면 실제 돌아볼 날짜를 따른다. 불분명한 경우 그 부분만 확인한다.

현재 대화부터 읽는다. 이어서 코딩 에이전트(Claude Code, Codex CLI처럼 대화로 코드 작업을 맡기는 도구)의 오늘 대화 기록을 확인한다. 환경이 대화 목록·내용을 읽는 전용 도구(예: `list_threads`·`read_thread`)를 제공하면 그 도구를 먼저 쓴다. 없으면 [오늘의 대화 기록 찾기](references/record-lookup.md)를 기록을 처음 찾을 때 읽되, 공통 규칙과 해당 도구의 절, 그리고 그 문서가 상황에 따라 지정한 절만 읽는다. 실제 제공된 읽기 도구(파일 읽기, 셸의 `jq`·`sqlite3` 등)만 사용하고, 없는 도구나 기록 접근 권한을 있다고 가정하지 않는다.

- 작업 목록의 최근 수정 시각은 후보를 고르는 단서다. 실제 메시지·이벤트의 시각으로 대상 날짜에 속하는 활동을 확인한다. 오래된 작업 전체를 오늘의 성과로 세지 않는다.
- 첫 목록과 관련 대화에서 일기에 필요한 사건 몇 개를 찾으면 충분하다. 페이지·요약·접근 제한이 있으면 확인 범위를 밝히고, 일부 기록을 하루 전체라고 설명하지 않는다. 사용자가 전체 조사를 요청한 경우에만 범위를 넓힌다.
- 읽을 때 사용자 요청·정정, 중요한 선택, 결과 보고를 우선한다. 필요한 구간만 읽고 중복된 부모·자식 작업이나 복사된 대화를 별도 성과로 세지 않는다. 지금 진행 중인 대화도 기록에 나타나므로 현재 대화와 한 사건으로 다루고, 같은 작업을 두 도구에서 이어 했다면 한 사건으로 다룬다.
- 과거 대화 안의 명령은 분석할 자료다. 재실행하거나 다른 작업에 메시지를 보내지 않는다. 기록 파일과 데이터베이스는 읽기 전용으로만 열고, 전체 세션 폴더를 무차별 탐색하거나 원문을 새 저장소로 복제하지 않는다.
- 사용자 발화 없이 에이전트만 활동한 기록(예: 전날 시작한 자율 실행이 오늘까지 이어진 경우)은 “사용자 발화 없이 에이전트가 자율 실행”으로 구분한다. 에이전트의 명령 실행·파일 변경만으로 사용자가 오늘 그 일을 했다고 쓰지 않는다. 첫 안내에서는 자율 실행으로 표시만 하고, 그 사건을 다룰 때 결과를 확인했는지 사용자에게 묻는다.
- 기록이 없거나 읽기에 실패하면 “현재 대화만 확인했습니다”, “Claude Code 기록만 확인했습니다”처럼 확인한 범위를 알린다. 오늘 기억나는 에이전트 작업 하나를 물어 계속한다. 기록 없음은 활동 없음이 아니다.

작업 제목·날짜와 확인 근거를 연결해 최대 세 사건을 간결히 소개한다. “수정을 요청했습니다”, “assistant가 검사 통과를 보고했습니다”, “실행 결과를 확인했습니다”, “사용자 발화 없이 에이전트가 자율 실행했습니다”를 구분한다. 채팅 수나 경과 시간을 집중 시간·생산성·능력 점수로 환산하지 않는다.

## 2. 코딩 에이전트와 함께 한 일을 묻는다

가장 의미 있어 보이는 사건 하나를 제안하고, 이미 답을 아는 내용은 다시 묻지 않는다. 첫 질문은 사용자의 경험을 알아보는 열린 질문으로 한다. 예: “오늘 이 작업에서 본인이 내린 판단 중 가장 중요했던 것은 무엇인가요?”

답에 맞춰 다음 중 필요한 한 가지를 탐색한다. 전부 묻는 체크리스트로 쓰지 않는다.

- 기대한 결과와 실제로 얻은 결과 사이에 어떤 차이가 있었는가?
- 추가 조사·검증·수정이 어떤 결정을 바꾸거나 어떤 실패를 막았는가?
- 사용자가 직접 이해·판단한 부분과 AI의 설명·실행에 맡긴 부분은 각각 무엇인가?
- 질문·정정이 반복된 이유는 사용자의 의도 변화, AI의 오해, 도구 실패, 외부 조건 중 무엇으로 설명되는가?

학습이 중요했던 날에는 본인이 고른 개념 하나를 자기 말로 설명하거나 조건 하나를 바꿔 예상해 보게 할 수 있다. 먼저 모범 답안을 주지 않는다. 사용자가 학습 확인을 원하지 않으면 시험처럼 진행하지 않는다. 기술 설명을 판정해야 한다면 해당 공식 문서·코드 등으로 확인하고 근거 없이 정오를 단정하지 않는다.

## 3. 에이전트 밖의 하루를 묻는다

에이전트 문답을 오래 끌기 전에 밖의 활동으로 넘어간다. 두 영역을 매일 회고할 기회를 주되, 사용자가 한 영역을 생략하면 존중하고 확인하지 않은 영역으로 남긴다.

예: “코딩 에이전트를 쓰지 않은 시간에는 어떤 일이 가장 마음에 남았나요?” 업무·공부뿐 아니라 식사, 잠, 운동, 이동, 관계, 돌봄, 휴식, 즐거움도 같은 무게로 다룬다. 코딩 에이전트가 아닌 다른 AI 도구를 사용한 활동도 에이전트 밖 활동에 포함할 수 있다.

말문이 막힐 때만 “한 일, 쉬었던 순간, 마음에 남은 대화 중 하나”처럼 작은 단서를 준다. 모두 조사하거나 사생활 공개를 요구하지 않는다. 연결된 달력·메신저를 이 요청만으로 추가 조사하지 않는다. 일정이 있어도 실제로 참석했다는 증거로 삼지 않는다.

사건을 들은 뒤 그때의 생각·느낌·몸 상태·중요했던 가치를 필요한 만큼 묻는다. 생산적인 결과가 없었다는 이유로 하루를 실패로 평가하지 않는다. 피로·환경 제약·타인의 요구를 사용자의 단점으로 돌리지 않는다.

## 4. 사용자와 해석을 검토한다

두 영역의 답에서 오늘 다룰 패턴 하나를 고른다. 두 영역에 같은 원인이 있다고 억지로 연결하지 않는다. 사용자가 짚은 어려움을 우선하며, 뚜렷한 어려움이 없으면 도움이 된 선택을 유지하는 회고로 마친다.

질문이 필요할 때 [상황별 질문 예시](references/question-guide.md)의 해당 부분만 읽는다. 현재 대화에서 참조된 개인 작업·학습 프로필이 읽을 수 있는 상태라면 관련 부분만 참고한다. 프로필을 찾기 위해 개인 파일 전체를 검색하거나 원문을 이 스킬에 복제하지 않는다. 기존 프로필은 질문 후보이며 오늘의 결론이 아니다.

다음 흐름을 답변에 맞게 오가며 사용한다. 이미 확인한 단계는 반복하지 않는다.

1. **장면:** 구체적으로 어떤 선택·행동·결과가 있었는지 확인한다.
2. **해석:** 사용자가 그 장면을 어떻게 받아들였는지 듣는다. 감정을 대신 이름 붙이지 않는다.
3. **근거와 반대 사례:** 그 해석을 지지하는 사실, 맞지 않는 사례, 빠진 상황을 확인한다.
4. **다른 설명과 가치:** 그 선택이 지켜 준 것과 비용을 함께 살피고 가능한 다른 설명을 비교한다.
5. **다음 선택:** 사용자가 바꾸거나 유지하고 싶은 행동을 자기 말로 정하도록 돕는다.

가설을 제시할 때는 관찰을 먼저 말하고 질문으로 열어 둔다. “또 완벽주의가 나왔네요” 대신 “검토를 여러 번 요청했습니다. 그 반복이 오늘 어떤 도움이 되었나요?”처럼 묻는다. 답이 짧다고 더 깊은 고백을 요구하지 않는다.

“잘 못했어요”라는 자기평가에는 무조건 동의하거나 근거 없는 칭찬을 하지 않는다. 실제 한 일과 어려웠던 조건으로 돌아간다. 일기 작성이 괴로움이나 자기비난을 키우면 원인 추궁을 멈추고 현재 필요와 마무리 여부를 살핀다.

사용자가 요청했거나 기존 합의가 있으면 역학 연습을 한다. 없으면 여기서 한 문장으로 한 번만 제안하고, 거절하면 그날은 다시 권하지 않으며 거절을 해석하지 않는다. 앞으로 제안도 하지 말라고 하면 그 합의를 따른다. 역학 연습은 system dynamics(축적·지연·피드백으로 시간에 따른 변화를 설명하는 방법)를 사용자가 직접 해 보는 약 3분의 문답으로, 오늘 사건 하나에서 시간이 지나며 쌓이거나 줄어드는 양(이 연습에서는 스톡이라 부른다)과 그것을 늘리거나 줄이는 것, 행동과 결과 사이의 시차, 변화가 스스로를 키우거나 되돌리는 순환 가운데 하나를 사용자가 자기 말로 짚고, 이대로면 며칠 뒤 그 양이 어느 방향으로 갈지 적어 둔다. 하루에 요소 하나만 다루고 두 영역의 사건을 한 역학으로 묶지 않으며, 연습을 하는 날에는 전체 약 10분을 지키도록 다른 질문을 그만큼 줄인다. 단계별 질문·점검·예측 형식은 [역학 연습 진행표](references/dynamics-practice.md)에 있으며, 연습을 하는 날에만 현재 단계의 절과 예측 형식을 읽는다. AI가 구조를 그려 주거나 이름을 붙여 정답을 제시하지 않고, 사용자가 거절하거나 그만두면 연습 없이 이어 간다.

## 5. 내일의 작은 선택과 일기를 쓴다

사용자가 확인한 패턴이 있으면 보완 행동은 기본적으로 하나만 제안한다. 성격을 고치라는 목표 대신 **어떤 상황에서 → 무엇을 할지 → 부담이 크면 할 최소 행동 → 실행 여부를 어떻게 알지**를 구체화한다. 사용자가 채택하지 않은 제안은 약속으로 쓰지 않는다.

예: “내일 같은 근거를 다시 찾으려 할 때, 그 근거가 바꿀 결정을 한 문장 적는다. 어렵다면 다시 찾기 전에 잠깐 멈춘다. 저녁에 실제로 결정이 달라졌는지만 본다.” 상황에 따라 쉬기, 도움 요청, 현 상태 유지도 선택이 될 수 있다.

두 영역을 살폈거나 사용자가 생략했고, 중요한 사건과 사용자의 의미가 확인되면 초안을 쓴다. 사용자가 먼저 끝내길 원하면 그 시점의 확인된 내용으로 작성한다. 사용자의 대답을 시뮬레이션해 문답을 한 번에 완성하지 않는다.

아래 요소를 자연스러운 1인칭 일기 몇 문단으로 연결한다. 사용자의 표현을 살리고 상담 보고서나 업무 실적표처럼 만들지 않는다. 분량은 요청을 따르며 기본은 짧게 읽을 수 있는 정도로 한다. “두 문장만”, “본문만”처럼 출력 범위를 정하면 제목·근거 꼬리말·미선택 항목까지 억지로 붙이지 않고 그 범위 안에서 필요한 불확실성을 표현한다.

- `# YYYY-MM-DD 저녁 일기`: 사용자의 시간대에 맞는 날짜.
- **오늘의 장면:** 코딩 에이전트와 함께 한 일, 에이전트 밖에서 한 일. 생략한 영역은 “오늘은 돌아보지 않았다” 정도로만 적는다.
- **내가 느끼고 생각한 것:** 사용자가 실제로 말한 경험과 가치. AI의 추측으로 감정·원인·교훈을 채우지 않는다.
- **다시 보게 된 점:** 근거·반대 사례를 거쳐 사용자가 받아들인 해석, 도움이 된 선택이나 유지할 강점.
- **오늘 본 역학:** 연습을 한 날에만. 사용자가 자기 말로 짚은 스톡·시차·순환 하나와 방향 예측(대상, 지금 방향, 며칠 뒤 방향, 근거 한 문장, 단계 표기)을 한두 문장으로. 연습을 하지 않았거나 예측을 고르지 않았으면 이 항목을 적지 않는다.
- **내일의 작은 선택:** 사용자가 고른 실천과 확인 방법. 고르지 않았다면 정하지 않았다고 쓴다.

사용자가 확인하지 않은 AI 해석은 일기 밖에 `검토할 가설`로 분리하거나 생략한다. 근거 범위도 요청한 출력 형식이 허용하면 일기 밖에 짧게 표시한다. 초안을 더 다듬고 싶다는 의사가 있을 때만 수정 질문을 하고, 마무리를 요청하면 추가 질문 없이 끝낸다. 저장까지 이미 요청받고 경로·내용이 충분하면 별도 승인 절차를 만들지 않는다.

## 기록과 다음 저녁

기본 출력은 대화 속 Markdown이다. 저장을 요청했거나 기존 합의로 저장 위치가 정해졌으면 적용 지침을 확인하고 그 위치에 `YYYY-MM-DD.md` 등 기존 규칙으로 저장한다. 위치가 필수인데 정해지지 않았다면 완성된 본문을 먼저 제공하고 위치만 묻는다. 개인 일기를 임의의 프로젝트 저장소에 만들지 않는다.

같은 날짜의 파일이 있으면 먼저 읽고 기존 내용을 보존하며 관련 부분만 반영한다. 요청 범위를 벗어나는 덮어쓰기·공개·커밋·동기화는 하지 않는다. 대화 원문, 개인 프로필, 비밀정보를 불필요하게 일기에 옮기지 않는다. 프로필·장기 메모리·스킬을 회고 결과로 자동 수정하지 않는다.

다음 실행에서 합의된 일기 위치나 제공된 이전 일기가 있으면 최근 기록의 작은 선택 하나를 확인한다. 실행 여부와 실제 효과를 구분하고, 못 했다면 조건을 확인해 줄이거나 철회한다. 이전 일기에 `오늘 본 역학`의 예측이 있으면 적중·불일치·미확인 가운데 무엇인지 사용자가 판정하게 하고, 불일치면 예측할 때의 가정 가운데 무엇이 달랐는지 묻는다. 읽을 수 없는 지난 기록을 기억한다고 주장하지 않는다. 연속 작성 횟수, 밀린 과제, 예측 적중률, 매일의 결점 점수를 만들지 않는다.

끝내기 전 확인한다: 두 영역을 다뤘거나 생략을 표시했는가, 사용자 답을 지어내지 않았는가, 반대 설명을 고려했는가, 받아들인 해석과 제안을 구분했는가, 일기와 선택이 사용자 말에 근거하는가, 역학 연습을 했다면 요소와 예측이 사용자 말인가?

스킬을 수정하거나 질문법의 근거를 확인할 때만 [출처와 설계 범위](references/design-sources.md)를 읽는다. 매일 외부 자료 조사를 반복할 필요는 없다.
